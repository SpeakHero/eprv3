# 全局缓存与前后端职责边界强制标准

> **版本**：v1.3
> **日期**：2026-10-24
> **效力**：全平台强制约束标准。适用于所有后端（C# / .NET）与前端（Vue3 / TS）开发，代码评审（Code Review）与架构测试必须逐条核对；任何模块方案文档与本文件不一致时，以本文件为准。
> **关联文档**：`.trae/rules/global-csharp-standard.md`（C# 编码规范）
> **规则编号约定**：`C-x` 缓存规范、`B-x` 前后端职责边界、`V-x` 数据校验、`N-x` 业务编码生成、`E-x` 执行与审计。评审记录中引用编号（如「违反 B-2」）。

---

## 一、缓存规范（C-x）

### C-1 唯一入口

1. 所有缓存读写**必须**经 `Qlx.BuildingBlocks.Caching.ICacheService`（Cache-Aside 封装）。禁止业务代码直引 `StackExchange.Redis`、`IDistributedCache`、`IMemoryCache` 等提供方 SDK。
2. 缓存键必须经 `QlxCacheKey` 构建：租户级 `tenant:{tenantId}:{modulePrefix}:{businessKey}`（`BuildTenantKey`）；门户/平台级使用保留租户码 `_portal`；Redis 物理键自动附加实例名前缀（`CacheOptions.InstanceName`）；禁止散装字符串拼 key。
3. 新缓存提供方只能经 DI + `config/common/cache.json` 的 `provider` 节整体替换，业务零改动。

### C-2 防击穿（热点 key 并发回源）

1. 所有「读不到就查库」的读路径**必须**使用 `ICacheService.GetOrCreateAsync`（读穿 + 并发合并），禁止手写「Get → null → 查库 → Set」裸序列。
2. 多实例部署下互斥必须跨实例：Redis `SET key:lock token NX EX 5` 分布式锁；未获锁者短退避（50~150ms 随机）后重读缓存，禁止全部回源。
3. 回源工厂内禁止再触发同 key 的 `GetOrCreateAsync`（防重入死锁）。

### C-3 防穿透（查询不存在的数据）

1. 查询结果为「不存在」时必须写入**空值缓存**：统一 `NullMarker` 哨兵值，TTL 30~60 秒。
2. 读到 `NullMarker` 按「不存在」处理，不再回源。
3. 空值缓存的 TTL 必须显著短于正常值 TTL。

### C-4 防雪崩（大量 key 同时过期）

1. 所有 TTL 必须经统一抖动封装（公共层 TTL 抖动助手）：基线 TTL ± 10%~20% 随机偏移。
2. 禁止在同一时刻批量写入相同 TTL 的大批 key（如批量预热必须加抖动并分批）。
3. 禁止永不过期的缓存项（`TimeSpan.Zero` / 无 TTL 一律评审驳回）。

### C-5 一致性与原子化（防脏读）

1. **失效优先（Invalidation-first）**：写路径**只删缓存、不写缓存**。顺序固定为：先提交数据库事务 → 提交成功后 `RemoveAsync` / `RemoveByPrefixAsync` → 后续读请求经 `GetOrCreateAsync` 重建。
2. **禁止双写**（写库同时写缓存）、禁止「先更新缓存再写库」、禁止「先删缓存再提交事务」。
3. 删缓存与重建的并发竞态由 `GetOrCreateAsync` 互斥消除；任何时刻读到的值必须是完整旧值或完整新值，禁止半截数据（序列化/反序列化必须原子，单 StringSet/StringGet）。
4. 用户级/版本敏感数据使用**版本化 key**（key 中内嵌数据版本号，如实体的版本字段/并发戳），版本变更后旧 key 自然失效，杜绝「旧值覆盖新值」。
5. 删缓存失败的漂移窗口必须有 TTL 兜底；安全敏感判定不得依赖缓存值（鉴权等安全判定以令牌声明 / 数据库为准，缓存只服务于性能路径）。

### C-6 定期清理任务

1. 每个缓存域必须定义无效缓存的判定规则与清理任务，任务经后台任务中心（`IJobScheduler` + Manifest `IJobHandler`）注册，禁止进程内定时器。
2. 清理任务要求：SCAN 分批（≤500/批）+ 批次间让出，**禁止 KEYS**；任务幂等、重入安全；执行结果落 `job_executions` 审计。
3. TTL 是第一道兜底，清理任务是第二道；不允许「只靠 TTL」作为唯一回收手段的缓存域（版本化 key 残留、下线租户残留必须可主动清除）。

### C-7 缓存内容约束

1. 缓存值必须是**可重建的派生数据**；权威数据源永远是数据库。禁止把缓存当作唯一存储。
2. 缓存值禁止包含展示态拼接结果（见 B-2）：树形结构、格式化字符串、枚举中文名等展示产物不得进缓存；缓存的是扁平原始数据。
3. 禁止缓存敏感明文（密码、密钥、未脱敏的个人敏感信息）。

## 二、前后端职责边界（B-x）

### B-1 总原则

后端职责：**鉴权过滤 + 业务规则 + 原始数据供给**。前端职责：**一切仅服务于界面呈现的数据加工**。
判定准则：「这段计算是否仅服务于界面展示？换一种 UI（App/报表/导出）是否还需要？」——仅服务展示 → 前端；多客户端/多通道共用 → 后端。

### B-2 后端禁止的展示类计算（非穷尽清单）

1. 树形结构数据的组装与层级计算（菜单树、组织树、分类树——后端只下发扁平列表 + parent 原始字段）。
2. 人民币大小写转换、金额/日期/数字的显示格式化。
3. 列表展示格式化（合并单元格、序号列、合计行展示格式、展示用排序/截断，如「快捷入口取前 N 个」）。
4. 展示用字符串拼接（如 `部门 / 姓名`、`编码 - 名称` 显示列）。
5. 枚举/状态 → 中文文案/图标/颜色的映射（枚举一律以数值/代码下发，映射字典在前端公共层维护）。
6. 分页之外的「展示分页」（如把同一份数据按 tab 预切分）。

### B-3 后端必须保留的职责

1. 安全过滤（权限裁剪、数据范围、字段级权限）——不可见数据**不下发**，这不是展示逻辑。
2. 业务规则计算（金额、税额、库存、状态机流转、审批分支求值）。
3. 原始字段透传与必要的类型转换（如逗号字段拆分数组、ID 混淆收发），但不得做展示拼装。

### B-4 前端必须承担的职责

1. 树/分组/层级组装（独立纯函数，可单测）。
2. 全部显示格式化与展示映射（格式化工具、枚举字典、i18n 文案）。
3. 展示排序/截断/挑选、空态/占位展示。
4. 公共展示逻辑必须落位前端公共层复用，禁止页面内重复实现。

### B-5 存量清理

1. 存量后端接口中的展示类计算按模块出迁移清单，随对应批次迁移至前端公共层。
2. 迁移后后端响应必须回归「扁平原始字段」，前端验收渲染一致性。

## 三、数据校验（V-x）

### V-1 双层校验强制

1. **前端校验（UX 层）**：提交前完成格式、必填、规则、合法性校验并即时反馈；目的是体验，**不构成安全边界**。
2. **后端校验（安全层）**：对前端提交的业务数据**必须再次执行独立的完整校验**——参数类型化绑定 + 输入校验（长度/范围/格式/枚举合法性）+ 业务规则复核（状态机、金额、越权、引用完整性）。
3. 后端校验**不得依赖、不得读取、不得信任**前端校验结果；绕过前端直调 API（curl/脚本）必须被后端完整拦截（400/403/409）。

### V-2 安全相关校验只在后端可信

1. 权限、越权、金额上限、状态机流转、并发版本（RowVersion/各类版本戳）校验只能以服务端为准。
2. 前端隐藏/禁用（按钮级权限指令等）只是体验层，不能替代后端授权拦截与服务层校验。

### V-3 边界外说明

1. B-2 的约束**仅针对展示类数据**；前端提交的业务数据不受「后端不做计算」限制——后端必须做完整业务校验与业务计算。
2. 校验失败响应必须携带统一错误码与可读消息（不得泄露内部实现细节）。

## 四、业务编码自动生成规范（N-x）

### N-1 唯一入口与禁止前端传码

1. 所有业务编码（角色编码、门户编码、租户编码、岗位编码及后续所有需编码的业务实体）**必须**由后端经 `Qlx.BuildingBlocks.Numbering.IEncodingGenerator` 自动生成，禁止前端在新建/编辑请求中提交编码字段。
2. 前端表单**不得**出现编码输入框；编码仅作为只读展示字段回显。
3. 业务服务的创建请求 DTO 中**不得**声明编码字段；更新请求同理不允许修改编码（编码一经生成不可变）。
4. 禁止业务代码绕开 `IEncodingGenerator` 手写拼音/序号逻辑；拼音提取统一走 `IPinyinConverter`。

### N-2 生成规则

1. 编码基础来源于业务名称字段的拼音：优先拼音首字母（`PinyinMode.Initials`，如「管理员」→ `gly`），长名称或易冲突场景可配完整拼音（`PinyinMode.Full`，如「管理员」→ `guanliyuan`）。
2. 生成流程固定为：提取拼音 → 规范化（统一小写、过滤非法字符、压缩连续分隔符）→ 拼接前缀 → 按 `MaxLength` 截断 → 唯一性校验 → 冲突追加递增序号。
3. 允许字符集：小写字母、数字、短横线（`-`）、下划线（`_`）、点（`.`）；其余字符（空格、标点、声调符号等）一律丢弃。
4. 非中文字符（ASCII 字母/数字）按原样保留并参与编码。

### N-3 重复处理与全局唯一

1. 当生成的基础编码已存在时，**必须**经 `ISerialSequenceStore` 原子取号，追加 `{Separator}{Serial:000}` 格式的递增序号去重（如 `role-cw-001`、`role-cw-002`）。
2. 序号键按 `encoding:{scope}:{base}` 隔离，不同业务域（`scope`）与不同基础编码的序号互不干扰。
3. 序号位数由 `SequenceDigits` 配置（默认 3 位），不足左补零；`MaxRetries`（默认 100）防止极端冲突死循环，耗尽时抛 `InvalidOperationException`。
4. 唯一性校验委托（`uniquenessChecker`）由业务方提供，通常查询数据库唯一索引；返回 `true` 表示冲突、`false` 表示可用。

### N-4 配置化与复用

1. 编码生成参数通过 `EncodingGenerationOptions` 配置化传入：`Prefix`（前缀）、`PinyinMode`（拼音模式）、`SequenceDigits`（序号位数）、`MaxLength`（最大长度）、`Separator`（分隔符）、`Lowercase`、`KeepNonChinese`、`MaxRetries`。
2. 各业务域按需配置：租户编码用完整拼音 + 无前缀；角色编码用首字母 + `role-` / `portal.` 前缀；岗位编码用首字母 + `pos-` 前缀。
3. `IEncodingGenerator` 与 `IPinyinConverter` 均注册为 Singleton，业务服务通过构造函数注入，禁止 `new` 实例。

### N-5 存量清理

1. 存量接口中的手动编码输入/生成逻辑必须迁移至 `IEncodingGenerator`，前端移除编码输入字段。
2. 迁移后新建请求 DTO 不再包含编码字段；后端响应 DTO 仍可回显编码（只读展示）。

## 五、执行与审计（E-x）

### E-1 代码评审检查点

1. 凡涉及缓存的 PR：核对 C-1（唯一入口/键规范）、C-2（GetOrCreateAsync/互斥）、C-3（空值）、C-4（TTL+抖动）、C-5（写路径只删不写/版本化 key）、C-6（清理任务）。
2. 凡涉及 API 响应的 PR：核对 B-2（无展示类计算）、B-3（安全过滤在后端）、V-1（后端独立校验）。
3. 凡涉及业务编码的 PR：核对 N-1（前端不传码/唯一入口）、N-2（拼音规则/字符集）、N-3（序号递增去重/全局唯一）、N-4（配置化/复用）。
4. 违反任一条目一律驳回，评审记录引用规则编号。

### E-2 架构测试守护

1. 架构测试断言：业务程序集不引用缓存提供方 SDK（C-1-1）；后端响应 DTO 不含树形嵌套展示结构（B-2-1）。
2. 缓存相关组件（互斥、抖动、空值、清理任务）必须有单元测试；失效优先与并发一致性必须有集成/压测验证。
3. 编码生成组件（`EncodingGenerator`、`PinyinConverter`）必须有单元测试，覆盖拼音提取、序号递增去重、最大长度截断、重试耗尽异常等场景。

### E-3 文件维护

1. 本文件变更必须经产品经理 + 架构负责人评审通过，并更新版本头（版本号 + 日期）。
2. 各模块方案文档中的缓存项矩阵、校验清单、编码生成配置必须与本文件保持一致并回链本文件。
