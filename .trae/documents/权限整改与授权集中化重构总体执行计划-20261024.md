## 三、自查自纠修订点（v3 → v4，强制执行）

### 修订 1：D-10 机制经 ASP.NET Core release/10.0 源码佐证，差异确认成立

- `ControllerActionDescriptorBuilder.AddEndpointMetadata`：端点元数据**仅**来自 `SelectorModel.EndpointMetadata`（即方法/控制器特性）。
- `ActionEndpointFactory.AddActionDataToBuilder`：只搬运 `action.EndpointMetadata`，**不搬运 Filters**。
- `AuthorizationApplicationModelProvider`：`EnableEndpointRouting == true`（本项目即此）时**明确不将 `[Authorize]` 转为过滤器**，由 AuthorizationMiddleware 代劳。
- 结论：现状 `[Authorize]` 由 UseAuthorization 在 `UseTokenBlacklist`/`UseModuleLicenseFilter` **之前**评估；convention 注入的 `AuthorizeFilter` 在 MVC 过滤器管线（二者**之后**）评估。v3 D-10 的三点影响论证（黑名单仍 401 / 许可先行仅泄露低敏 404 / 已认证判定一致）成立，冒烟验证逐项比对状态码。
- 附加确认：`AuthorizeFilter.OnAuthorizationAsync` 的 `HasAllowAnonymous` 含 `endpoint.Metadata.GetMetadata<IAllowAnonymous>()` 兜底，`[AllowAnonymous]` 逃生舱在注入过滤器下仍生效。

### 修订 2（阻塞性）：Portal 匿名登录端点必须显式豁免，否则登录 401

全库 17 个控制器中 16 个有类级 `[Authorize]`，唯一例外 `AuthorizationController`（`POST ~/connect/token` 登录端点，无 `[Authorize]` 无 `[AllowAnonymous]`，现状靠「无元数据即放行」匿名可达）。v3 的「目录 miss → 注入仅认证兜底」会把登录打成 401。
→ `PortalEndpointPolicyMap` 覆盖 **9 个控制器**（非 v3 的 8 个）：追加 `Authorization` 控制器规则 `Action = "Exchange", AllowAnonymous = true`。

### 修订 3：Support 映射补 MessageStreamController

v3 §3.3 写「5 个控制器共 45 条」遗漏 `MessageStreamController`（类级仅认证 scheme 标注，SSE 长连接）。→ Support 映射为 **6 个控制器**：45 条动作级权限码 + MessageStream 控制器级空规则（仅认证，显式声明供覆盖率断言）。

### 修订 4：标注计数修正

- 方法级 `Permission:` 标注实测 **71 处**（v3 写 72）：TenantAdmin 26 + Support 45（File 12 / Job 7 / Message 5 / Approval 15 / Print 6）。
- 类级标注实测 **16 个控制器**（v3 写 13）：Bas 2 + Support 6 + Portal 8。
- v3 §3.5「6 个 Bas/Support 控制器」修正为「**8 个**」；清理范围 = 16 控制器（含 Portal 8 个的类级）。

### 修订 5：authorization.json 写路径与配置目录解析一致

Catalog 生成默认 JSON 的落盘路径必须复用 `QlxConfigurationExtensions.AddQlxConfiguration` 的目录解析结果（contentRoot/config），禁止自行 `Path.Combine(ContentRootPath, ...)` 拼死路径；若解析器为 internal，执行时将其目录定位逻辑提取为公共层可复用成员。
