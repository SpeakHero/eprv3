## 一、执行摘要

本次黑盒测试共发现 **1 项严重（Critical）、2 项高危（High）、3 项中危（Medium）、5 项低危/提示（Low/Info）** 安全问题。

**核心结论：存在可直接获取系统最高权限的完整攻击路径。** Redis 缓存服务未启用任何认证且绑定全网卡（0.0.0.0:6379，局域网可直接访问），攻击者可读写全部缓存数据——包括权限判定缓存与登录锁定状态。通过「删除锁定键 → 无限爆破管理员口令」或「直接篡改权限缓存提权」两条路径均可获取门户最高管理权限，全过程无需任何先验凭证。

应用层（API / 认证 / 授权）本身的防护质量良好：JWT 伪造、SQL 注入、未授权访问、CORS 跨域等测试全部通过；主要风险集中在**基础设施层（Redis 裸奔）**与**认证交互的细节设计**（锁定消息可枚举账号、输入直拼缓存键）。

## 三、漏洞清单

### 【严重】V-01 Redis 未授权访问（读写全开放 + 网络暴露）

- **风险等级**：Critical（CVSS 3.1 估算 9.8）
- **位置**：`0.0.0.0:6379`（含局域网接口 192.168.2.165）
- **验证证据**：
  - 无密码直接执行 `PING → +PONG`、`INFO server`、`CONFIG GET requirepass`（返回空）、`DBSIZE → 53`、`SCAN` 枚举全部键
  - **写权限验证**：`SET qlx:pentest:probe vulnerable → +OK`（测试后已 DEL 清理）
  - 可从局域网接口直接连接，无需任何凭证
- **可读取的敏感数据**：
  - 权限判定缓存：`auth:permission:user:287151958945435648:resource:*`（含管理员 userId 与资源 ID 映射）
  - 认证参数：`qlx:_portal:params:auth.max_password_fail_attempts = "5"`、`auth.password_fail_window_minutes`
  - 登录锁定状态：`qlx:auth:lockout:admin = "locked"`
  - 旧版本匿名路径清单：`auth:anonymous_paths`（泄露历史 API 攻击面，含 `/api/cache/clear`、`/api/test/init-*` 等敏感端点名，当前实例均为 404 属残留数据）
- **附加风险**：Redis 3.0.504 为 2015 年发布的停止维护版本（Windows 非官方移植），`CONFIG` 命令未禁用，存在 `CONFIG SET dir/dbfilename + SAVE` 写任意文件的潜在利用面（本次未做破坏性验证）
- **修复建议**：
  1. 立即设置 `requirepass` 强密码，或改用 `protected-mode yes` + 绑定 `127.0.0.1`
  2. 生产环境通过 `config/common/cache.json` 配置连接串密码，密码入密钥管理（不得硬编码）
  3. 重命名/禁用 `CONFIG`、`KEYS`、`FLUSHALL` 等高危命令
  4. 升级至受支持的 Redis 版本（≥7.x），Windows 环境建议使用容器化部署
  5. 防火墙入站规则阻断 6379 对外开放

### 【高危】V-02 基于缓存提权的最高权限获取路径（攻击链已验证可行）

- **风险等级**：High（依赖 V-01，单独存在）
- **攻击路径 A（权限缓存直接篡改，需任一低权限账号）**：
  1. 连接无认证 Redis，`SCAN` 枚举获得管理员 `auth:permission:user:{管理员uid}:resource:{资源id}` 键结构
  2. `SET auth:permission:user:{攻击者uid}:resource:{资源id} "true"`
  3. 攻击者持自身合法 Token 调用管理端点，权限校验命中被篡改缓存 → 获得门户管理权限
- **攻击路径 B（解除锁定 + 无限爆破管理员）**：
  1. `DEL qlx:auth:lockout:admin`、`DEL qlx:auth:pwfail:admin`
  2. 对 `admin` 账号无限制爆破口令（锁定机制被旁路）
  3. 命中后经 `portal_identity` grant 获取 `qlx_portal_admin=true` 的身份 Token → 进入门户管理
- **根因**：权限判定与锁定状态等安全敏感数据存放于无任何访问控制的缓存中，违反「安全敏感判定不得依赖缓存值」（缓存规范 C-5-5）的兜底要求——当前权限校验链路以 Redis 缓存为性能路径但缓存本身可被任意改写
- **修复建议**：以 V-01 修复为前提；同时将权限缓存值增加服务端签名/HMAC 校验（缓存值被外部篡改后可识别并拒绝），锁定计数键增加写保护

### 【高危】V-03 账号锁定机制设计缺陷：用户枚举 + 拒绝服务

- **风险等级**：High
- **位置**：`POST /connect/token`（`portal_identity` grant）
- **验证证据**：
  - 同一口令错误时：不存在账号与存在账号均返回 `账号或密码错误`（✔ 无枚举）
  - 但连续失败 5 次触发锁定后，响应变为 **`账号已锁定，请稍后再试`**（✘ 与不锁定账号的响应可区分）→ 攻击者通过「撞 5 次看消息变化」即可确认任意账号是否存在
  - 任何人均可**恶意锁定任意账号**（对 admin 连续 5 次错误尝试即锁定约 13 分钟，实测锁定 TTL 779 秒），形成针对管理员的持续 DoS
- **修复建议**：
  1. 锁定后对外仍返回统一 `账号或密码错误`（或统一「账号或密码错误，或账号已被锁定」）
  2. 锁定时长内正确口令是否放行需产品决策；建议叠加 IP 维度限流（当前仅账号维度，跨账号分布式爆破不受限）
  3. 管理员账号锁定支持告警通知（监控告警渠道已有基础）

### 【中危】V-04 登录账号未过滤直接拼接 Redis 缓存键（缓存键注入）

- **风险等级**：Medium
- **验证证据**：提交 `login_account` 为 `admin' AND SLEEP(2)--`、`admin'; DROP TABLE sys_users--` 等载荷后，Redis 中出现键 `qlx:auth:pwfail:admin' AND SLEEP(2)--`、`qlx:auth:pwfail:admin'; DROP TABLE sys_users--`
- **影响**：① 攻击者可向 Redis 任意写入键（垃圾键膨胀内存）；② 载荷原样落键名，后续若有基于键名的模式操作（`KEYS pwfail:*`、批量删除前缀）可能被利用绕过锁定计数；③ 违反缓存键统一构建规范（C-1-2，`QlxCacheKey` 之外的散装拼键）
- **修复建议**：失败计数键对账号做哈希/规范化（如 SHA256(account) 前缀截断），禁止原始输入直接入键

### 【中危】V-05 超大表单触发未处理异常 500（鲁棒性）

- **风险等级**：Medium（偏低）
- **验证证据**：提交 5MB 的 `login_account` → 响应 `500 INTERNAL_ERROR / Form key length limit 2048 or value length limit 4194304 exceeded`（框架默认限制 4MB，异常未被业务层捕获转 400）
- **影响**：可被用作低成本异常洪水（写错误日志膨胀）；响应虽无堆栈泄露，但暴露了框架内部限制细节
- **修复建议**：入口处对 `login_account`/`password` 做长度上限校验（如 ≤128 字符），超限直接 400；全局异常中间件兜底表单解析异常为 400

### 【中危】V-06 全链路 HTTP 明文（开发环境基线问题）

- **风险等级**：Medium（生产部署前必须闭环）
- **证据**：OIDC `issuer` 为 `http://localhost:5002/`，Token 端点、账号口令均为 HTTP 明文传输
- **修复建议**：生产强制 HTTPS + HSTS，`issuer` 与 `token_endpoint` 使用 https 地址；部署清单中增加 TLS 检查项

### 【低危/提示】V-07 ~ V-11

| 编号 | 等级 | 问题 | 说明与建议 |
| --- | --- | --- | --- |
| V-07 | Low | OIDC 发现文档公开自定义 grant 结构 | 标准行为，但 `/.well-known/openid-configuration` 暴露了内部授权设计；生产环境属可接受，知悉即可 |
| V-08 | Low | API 缺少安全响应头 | `X-Content-Type-Options`/`X-Frame-Options`/`CSP` 均缺失；API 场景影响小，建议前端生产构建补 `X-Content-Type-Options: nosniff`、`frame-ancestors` |
| V-09 | Info | Vite Dev Server 暴露源码 | `/@fs/` 已正确限制（项目外文件 403；`win.ini` 的 200 为 SPA fallback 非文件泄露）；仅限开发环境，生产构建不受影响 |
| V-10 | Info | `TRACE /health` 返回 200 | Kestrel 路由匹配返回健康检查体，**无请求头回显**，非 XST 漏洞，无需处理 |
| V-11 | Info | Redis 残留旧版本 `auth:anonymous_paths` 数据 | 泄露历史 API 命名（含旧缓存管理/测试初始化端点名），建议随 V-01 整改时清理残留键 |

## 四、攻击路径复现（获取最高管理权限）

**前置条件**：与目标同网段（或 Redis 端口对攻击者可达），无任何账号密码。

```
步骤1  确认 Redis 暴露
       redis-cli -h <目标IP> PING            → +PONG（无认证）

步骤2  解除管理员爆破防线
       redis-cli -h <目标IP> DEL qlx:auth:lockout:admin
       redis-cli -h <目标IP> DEL qlx:auth:pwfail:admin
       （每次触发锁定后重复执行，锁定机制永久失效）

步骤3  爆破 admin 口令
       POST /connect/token
       grant_type=urn:qlx:grant:portal_identity&client_id=erp-web
       &login_account=admin&password=<字典>
       （无 IP 限流，仅账号级锁定且已被步骤2旁路）

步骤4  命中后响应携带 qlx_portal_admin=true 与身份级 access_token
       → 调用 /api/portal/admin/* 全部管理端点（租户/用户/角色/许可）
```

替代路径（已持任意低权限账号）：连接 Redis → `SET auth:permission:user:{本人uid}:resource:{管理资源id} "true"` → 权限校验命中篡改缓存直接放行。

## 五、通过项（防护良好的方面）

| 测试项 | 结果 |
| --- | --- |
| 未授权访问 | 全部业务端点无凭证一律 401；动词篡改 405 |
| JWT 伪造 | alg=none / HS256 算法混淆（公钥作 HMAC 密钥）/ 伪造签名全部 401 |
| SQL 注入（登录参数） | 各类载荷统一响应、无时间盲注特征、无报错注入面 |
| CORS | 严格白名单（仅 localhost:5173），恶意源无 ACAO；允许凭证但未配 `*` |
| 错误处理 | 统一错误包装，无堆栈/内部细节泄露；Host 头注入不影响 issuer |
| Swagger/调试端点 | 生产实例已关闭（404） |
| 账号锁定 | 存在 5 次/窗口期 锁定机制（但存在 V-03 设计缺陷） |
| `/connect/revoke` | 公开客户端免密吊销符合 RFC 7009 |
| 前端 `@/fs/` | 项目外文件读取被拒（403） |

## 六、整改优先级建议

| 优先级 | 事项 |

| P0（立即） | V-01 Redis 认证 + 绑定回环 + 防火墙；V-04 失败计数键规范化 |
