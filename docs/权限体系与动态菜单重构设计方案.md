# 权限体系与动态菜单重构设计方案

> **版本**：v1.6（定稿，自审通过）
> **日期**：2026-10-23
> **作者**：产品经理 / 架构设计
> **适用范围**：全平台权限、菜单、模块数据持久化
> **v1.3 修订**：修正权限旁路作用域缺陷——移除「门户管理员在租户上下文自动放行」通道。权限旁路只认**当前上下文自身**的角色 claim：租户上下文只认 `member_role=TenantAdmin`，门户身份 claim（`is_portal_admin`）在租户内不产生任何特权。同一用户在门户与租户、租户与租户之间的权限完全独立，在租户内一律受该租户权限体系约束（例：门户管理员在租户 X 仅是普通成员时，进入租户 X 后仅享有其租户角色权限）。
> **v1.4 修订**：**门户管理端纳入同一套细粒度权限体系**——新增 `por_roles` / `por_role_permissions` / `por_user_roles` 三表，门户权限点（`portal.*`）由 Portal Manifest 声明落库；`IsPortalAdmin` 保留为门户超级管理员标记（零计算旁路，与租户 `TenantAdmin` 同构），普通门户用户经角色聚合权限写入门户身份 Token 的 `permissions` claim；门户菜单持久化并新增 `/api/portal/menus` 动态下发；`[AuthorizePermission]` 门户上下文从「全量放行」改为「超管零计算 + 普通用户精确匹配」，与租户上下文逻辑完全同构。
> **v1.5 修订**：**全面集成缓存应用并强制前后端职责边界**——权限/菜单全链路缓存基于现有 `ICacheService` 通用缓存层（不新建），落实防击穿（读穿互斥）、防穿透（空值缓存）、防雪崩（TTL 抖动）、失效优先的一致性方案（禁双写、版本化 key）与定期清理任务；**菜单 API 改为只下发「鉴权过滤后的扁平数据」，树形组装/层级计算/快捷入口挑选等展示类逻辑全部移至前端 menuStore**；新增全局强制规则文件 `.trae/rules/global-cache-layering-standard.md`（缓存规范 + 前后端职责边界 + 双层校验），本方案与其不一致时以规则文件为准。
> **v1.6 修订（自审定稿）**：**代码事实交叉验证 + 技术细节修正**——① 修正 `PermissionKind` 枚举名：原设计文档多处误写 `PermissionKind.DataScope`，实际代码值为 `PermissionKind.Data`；② **全面对齐 QlxCacheKey 缓存键规范**（C-1）：原散装键格式 `{tenantCode}:perm:menus:...` / `portal:perm:*` 全部改为经 `QlxCacheKey.BuildTenantKey(long tenantId, "perm", ...)` / `QlxCacheKey.BuildPortalKey("perm", ...)` 构建，物理键分别为 `tenant:{tenantId}:perm:...` 与 `_portal:perm:*`（`_portal` 为门户保留租户码带下划线前缀）；③ 修正 §5.4 权限拦截器代码示例的常量引用错误：`QlxAuthConstants.Claims.IsPortalAdmin`（不存在）→ `QlxClaimConstants.PortalAdminFlag`，claim 值 `"true"` → 实际签发值 `"1"`；④ 修正 §5.5.1 Claim 常量定义：`MemberRole` 已存在（值 `"member_role"`），不是新增；`DataScope` / `DataScopeDeptId` 为需新增到 `QlxClaimConstants` 的常量；⑤ 全文术语统一性扫查：`tenantCode` vs `tenantId` 在缓存键上下文中明确区分（缓存键用 long `tenantId`）；`tv_u` / `tv_m` 统一引用 `QlxClaimConstants.UserTokenVersion` / `MemberTokenVersion`；⑥ 代码示例中 `PortalAdminFlag` 与 `TenantAdmin` 值常量化建议补充到 Abstractions 层。

## 1 概述

### 1.1 问题背景

当前系统阶段二开发已完成支撑模块（审批/信息/任务/文件/打印），但**权限、菜单、数据持久化**三条基础链路尚未打通，直接阻塞后续业务模块开发与上线。三个问题根因同属一处：**权限数据未持久化、菜单未对接动态接口、细粒度权限判定缺失**。

| #  | 核心问题           | 影响范围                                                             | 阻塞程度            |
| -- | -------------- | ---------------------------------------------------------------- | --------------- |
| P1 | 模块数据硬编码、无持久化   | 前端菜单 340 行静态配置；权限定义仅 1 条种子数据                                     | 所有业务模块无法上线      |
| P2 | 菜单静态写死、未对接权限体系 | 菜单可见性仅靠模块许可过滤，无法按角色细粒度控制                                         | 权限形同虚设          |
| P3 | 权限粒度仅到模块级      | RolePermission 表已建但未接入签发；`CurrentUserService.Permissions` 硬编码空数组 | 按钮、数据、字段级权限均未生效 |

### 1.2 设计目标

| 目标                    | 验收口径                                                                                                                                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **数据持久化**             | 权限点、菜单项、导航分组三类元数据全部落库，模块启动时种子初始化而非硬编码                                                                                                                                                                                 |
| **动态菜单**              | 前端菜单从 `/api/tenant/menus` 按需拉取，后端按"模块许可 ∩ 角色权限 ∩ 菜单 RequiredPermission"过滤下发，前端零静态菜单配置                                                                                                                                 |
| **细粒度权限**             | 权限覆盖 Module → Menu → Action → DataScope → Field 五层；后端 `[AuthorizePermission("xxx")]` 特性拦截；前端 `v-permission` 指令隐藏禁用按钮；**门户/租户同构**——门户超管（IsPortalAdmin）与租户 TenantAdmin 同为零计算旁路，普通用户（门户/租户）均经角色聚合 permissions claim 精确匹配 |
| **数据范围（DataScope）机制** | Token 携带 data\_scope claim + EF Core IQueryFilter 基类，业务模块继承实现即可获得行级过滤能力（本次提供基类与参考实现，逐模块落地后续批次）                                                                                                                        |
| **高效权限判定**            | TenantAdmin 零计算（仅租户上下文 member\_role claim 直接放行；门户身份 claim 在租户内无任何特权）；普通成员 Token 签发时单次聚合 + Redis 缓存（key=tenant:member:tokenVersion，角色变更自动失效）                                                                           |
| **数据防篡改**             | por\_\* 定义表应用层强制只读（无写 API）+ EF SaveChanges 拦截器拒绝非 Manifest 来源的写入 + 审计日志全量记录                                                                                                                                           |
| **兼容现有架构**            | 四层库拓扑不变；模块互引禁令不突破；双层权限（门户/租户）不破坏                                                                                                                                                                                      |

### 1.3 设计范围

**In Scope（本次批次）**：

- 新增 `por_module_menus`（菜单表）、`por_navigation_groups`（顶级导航分组表）
- 补全 `por_permission_definitions` 种子（各模块 Manifest 声明的权限点自动落库）
- **定义跨库查询契约** **`ITenantRolePermissionQuery`**（Abstractions 接口，Bas 实现，Portal 消费）
- Token 签发：TenantAdmin → 只写 `member_role=TenantAdmin` claim（**零计算权限码**）；普通成员 → 单次查询聚合权限列表写 `permissions_claim`（逗号分隔紧凑字符串）
- 后端新增 `/api/tenant/menus` 菜单树 API + `[AuthorizePermission]` 权限特性
- **DataScope 机制层**：Token `data_scope` claim + `QlxTenantDataScopeQueryFilter` EF Core 基类 + 参考实现
- 前端 auth store 新增 `permissions` state + 动态菜单 store + `v-permission` 指令
- 角色变更 → TenantMember.TokenVersion +1（租户侧）/ PortalUser.TokenVersion +1（门户侧，复用现有字段）
- **数据防篡改**：EF SaveChanges 拦截器（`ManifestDefinitionReadOnlyGuardInterceptor`）禁止 por\_\* 定义表非 Manifest 来源的写入 + 审计日志
- **门户细粒度权限（v1.4 新增）**：`por_roles` / `por_role_permissions` / `por_user_roles` 三表 + 门户身份 Token 权限聚合签发 + `/api/portal/menus` + 门户角色管理 API + 现有门户控制器补 `[AuthorizePermission]` 标注

**Out of Scope（后续批次）**：

- DataScope 的逐业务模块实际 IQueryFilter 实现（采购订单查"本部门"vs"全部"等）
- Field 字段级权限的前端表单控制（本次只打通 PermissionKind.Field 声明与 Token 签发，前端字段禁用/隐藏待业务模块实现）

## 3 设计原则

| #   | 原则                            | 说明                                                                                                                                                                                                                                         |
| --- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P-1 | **元数据驱动 + 防篡改**               | 菜单和权限点的权威数据源是各模块 `IModule.Manifest`，启动时自动 Upsert 到 Portal 库；应用层**禁止提供写 API**；EF SaveChanges 拦截器拒绝非 Manifest 来源的写入                                                                                                                          |
| P-2 | **Portal 权威、租户消费**            | 权限点定义、菜单定义、模块定义全部由 Portal 库 `por_*` 表管理（控制面）；租户库只存角色-权限分配（数据面）                                                                                                                                                                             |
| P-3 | **最小权限 + 上下文内零计算**            | TenantAdmin 的全权限不枚举写入 Token，改为 `member_role=TenantAdmin` claim + AuthorizePermission 过滤器直接放行；普通成员单次登录聚合写入 permissions claim。**旁路作用域严格限定当前上下文**：租户上下文只认 `member_role`，门户身份 claim（如 `is_portal_admin`）在租户内不产生任何特权——同一用户在门户与租户、租户与租户之间的权限完全独立 |
| P-4 | **Token 权限快照 + Redis 缓存**     | 登录时一次性聚合角色权限 → 紧凑逗号分隔字符串写入 Token；角色变更时 TokenVersion +1 → 版本化缓存 key 自动失效；菜单生成也按 tokenVersion 缓存（全部缓存读写走 ICacheService，防护与一致性细则见 §16）                                                                                                        |
| P-5 | **前端菜单纯后端下发，无兜底**             | 前端不维护任何静态菜单配置；API 失败时显示 loading/error 状态（**禁止回退到硬编码菜单**，防止显示用户没有权限的项）                                                                                                                                                                      |
| P-6 | **渐进迁移**                      | Manifest 自动种子先跑 Support + Bas 两个已落地模块，后续业务模块逐个接入                                                                                                                                                                                           |
| P-7 | **展示逻辑前端化 + 双层校验**（v1.5）      | 后端只下发鉴权过滤后的**扁平原始数据**（枚举/状态以代码下发），树形组装、层级计算、格式化、人民币大小写、展示字符串拼接、快捷入口挑选等一切仅服务于界面呈现的逻辑**禁止进入后端**，统一由前端实现；前端提交的业务数据执行「前端 UX 校验 + 后端独立完整校验」双层校验，后端不得依赖前端校验结果。细则见 `.trae/rules/global-cache-layering-standard.md`                                |
| P-8 | **缓存统一走 ICacheService**（v1.5） | 权限/菜单/定义字典等全部缓存读写只经 `ICacheService`（Cache-Aside），禁止直引提供方 SDK；防击穿（读穿互斥）、防穿透（空值缓存短 TTL）、防雪崩（TTL 抖动）、失效优先（写后删缓存禁双写）+ 版本化 key + 定期清理任务，细则见 §16 与规则文件                                                                                           |

## 4 数据模型设计

### 4.1 新增表

#### 4.1.1 `por_module_menus`（菜单定义表）

门户库 `por_` 前缀，模块启动时从 Manifest 自动同步。

| 字段                       | 类型            | 约束                                          | 说明                          |
| ------------------------ | ------------- | ------------------------------------------- | --------------------------- |
| `Id`                     | bigint        | PK，雪花 Id                                    | 继承 Entity                   |
| `ModuleCode`             | nvarchar(64)  | FK → por\_module\_definitions.ModuleCode，索引 | 所属模块                        |
| `MenuCode`               | nvarchar(64)  | 唯一索引 (ModuleCode, MenuCode)                 | 模块内唯一菜单编码                   |
| `ParentCode`             | nvarchar(64)  | 可空，索引                                       | 父菜单编码；空 = 顶级                |
| `GroupName`              | nvarchar(128) | 可空                                          | 分组名（用于同模块菜单分组展示）            |
| `DisplayName`            | nvarchar(128) | NOT NULL                                    | 菜单显示名                       |
| `Route`                  | nvarchar(256) | NOT NULL                                    | 前端路由路径（如 `/module/bas/org`） |
| `Icon`                   | nvarchar(64)  | 可空                                          | Element Plus 图标标识           |
| `RequiredPermissionCode` | nvarchar(128) | 可空，索引                                       | 访问所需权限点编码；空 = 仅需模块许可即可见     |
| `SortOrder`              | int           | NOT NULL，默认 0                               | 同级排序                        |
| `IsVisible`              | bit           | NOT NULL，默认 1                               | 是否显示（隐藏但路由仍可访问）             |
| `OpenMode`               | tinyint       | NOT NULL，默认 1                               | 1=当前标签页，2=新标签页              |
| `IsDeprecated`           | bit           | NOT NULL，默认 0                               | Manifest 已移除标记，不物理删除        |

**索引**：

- `(ModuleCode, ParentCode, SortOrder)` — 菜单树查询主路径
- `(RequiredPermissionCode)` — 权限反向查找

**种子来源**：`IModule.Manifest.Menus`，启动时 `IModuleManifestSyncService.SyncModuleMenusAsync()` Upsert 对齐。

#### 4.1.2 `por_navigation_groups`（顶级导航分组表）

跨模块顶级导航（工作台/业务办理/财务票据/...）。

**种子来源决策**：由于顶级导航分组是跨模块的平台级配置，不属于任何业务模块，指定由 **Portal 模块的 Manifest**（`Qlx.Modules.Portal.IModule.Manifest.TopNavigationGroups` 属性）声明。

**ModuleManifest 接口变更说明**（§15.3 风险）：当前 `Qlx.Abstractions.Modules.ModuleManifest` 是 `sealed record`，没有 `TopNavigationGroups` 属性。需要在 Abstractions 层**新增一个带默认值的 init 属性**：

```csharp
// Qlx.Abstractions.Modules.ModuleManifest 新增
public IReadOnlyList<NavigationGroupDefinition> TopNavigationGroups { get; init; } = [];
```

此变更是**向后兼容**的：现有所有模块的 Manifest 声明代码**无需修改**即可编译通过（默认空数组），仅 Portal 模块需要显式赋值。

| 字段             | 类型            | 约束            | 说明                                                        |
| -------------- | ------------- | ------------- | --------------------------------------------------------- |
| `Id`           | bigint        | PK            | 雪花 Id                                                     |
| `GroupCode`    | nvarchar(32)  | 唯一            | 导航分组编码（workbench/business/finance/people/basedata/system） |
| `GroupName`    | nvarchar(64)  | NOT NULL      | 显示名                                                       |

### 5.3 Token 权限签发流程（**TenantAdmin 零计算版**）

```
租户上下文登录成功
    │
    ▼
获取当前 TenantMember + 该租户已启用模块列表
    │
    ├── TenantMember.Role == TenantAdmin?
    │       │
    │       ├── YES（零计算通道）
    │       │   ├── member_role_claim = "TenantAdmin"  ← 仅写这一个 claim
    │       │   ├── data_scope_claim = "All"           ← TenantAdmin 天然全数据范围
    │       │   └── 完成！不查权限表、不枚举、不聚合
    │       │
    │       └── NO（普通成员）
    │           ├── ITenantRolePermissionQuery.ListMemberPermissionCodesAsync()
    │           ├── 模块过滤（移除未授权模块的权限码）
    │           ├── permissions_claim = string.Join(",", 去重后权限码)
    │           │    （逗号分隔紧凑字符串，避免 JSON 数组开销）
    │           ├── data_scope_claim = Role.DefaultDataScope.ToString()
    │           └── 写入 Token
    │
    ▼
写入 Token claims:
    ├── modules_claim (已有，来自 por_tenant_modules)
    ├── member_role_claim (新增)
    ├── [permissions_claim] (普通成员有，TenantAdmin 无)
    ├── data_scope_claim (新增)
    └── tenant_id / member_id / sub / token_version (已有)
```

**关键设计**：

- **TenantAdmin 零计算**：只写 `member_role=TenantAdmin` claim，不查权限表、不枚举、不聚合。`[AuthorizePermission]` 过滤器检测到该 claim 直接返回 SuccessRequirement。菜单 API 检测到后返回全量菜单（仅按已启用模块过滤）。
- **上下文隔离（v1.3 修正）**：租户上下文 Token **不签发门户级特权 claim**，且消费侧（权限过滤器 / 菜单 API / 前端指令）在租户上下文**不读取门户身份 claim**。`member_role` 是租户内权限旁路的**唯一**依据。示例：某用户是门户管理员，同时在租户 X 中仅是普通成员——进入租户 X 换发租户 Token 后 `member_role=OrdinaryMember`，仅享有 `permissions_claim` 列举的权限，受租户权限体系完全约束；只有当其在该租户的成员角色为 TenantAdmin 时才走零计算通道。该用户若需租户 X 的全量权限，须由租户 X 的管理员将其成员角色调整为 TenantAdmin，而非依赖门户身份。
- **普通成员单次登录聚合**：通过 `ITenantRolePermissionQuery` 单条查询聚合所有关联角色的权限码，去重 + 模块过滤后写逗号分隔字符串。**这只发生在 Token 签发时**（登录/续期，低频操作），不是每次请求都计算。
- **JWT 大小估算**：实际权限码数量经估算不会超过 50 个（Bas \~20 + Support \~15 + 其他业务模块上线后逐模块递增，初期约 35-50）。50 码 × \~15 字符 × 1.33 base64 ≈ **1KB** payload，远低于 RFC 7519 建议的 JWT 总 ≤ 8KB 上限。**本版方案不再预留 role\_ids 降级通道**——如未来业务模块暴增导致权限码数超 200，届时单独追加（当前阶段这是假想问题，优先保持方案简洁）。
- **角色变更 → TokenVersion +1**：强制下次登录重新签发新 Token（新权限集合）。

### 5.3.1 门户身份 Token 权限签发（v1.4 新增，与租户同构）

```
门户身份认证成功（Phase 1 / refresh）
    │
    ▼
获取当前 PortalUser
    │
    ├── PortalUser.IsPortalAdmin == true?
    │       │
    │       ├── YES（零计算通道）
    │       │   ├── is_portal_admin = "1"   ← 仅写这一个 claim（现状保持）
    │       │   └── 完成！不查角色表、不枚举、不聚合
    │       │
    │       └── NO（普通门户用户：平台运维/客服/审计员等）
    │           ├── 单条查询：por_user_roles ⨝ por_role_permissions
    │           ├── 聚合去重 PermissionCode（portal.*）
    │           ├── permissions_claim = string.Join(",", 权限码)
    │           └── 写入 Token
    │
    ▼
写入门户身份 Token claims:
    ├── sub / name / login_account / tv_u (已有)
    ├── is_portal_admin (超管有，普通用户无)
    └── [permissions_claim] (普通门户用户有，超管无)
```

**关键设计**：

- **门户/租户完全同构**：`IsPortalAdmin` ↔ `TenantAdmin`（零计算旁路）；`por_roles` ↔ `bas_roles`（自定义角色）；门户 `permissions_claim` ↔ 租户 `permissions_claim`（逗号分隔、签发时单次聚合、同名 claim——两类 Token 互不携带对方 claim，无冲突）。
- **门户权限点命名规范**：`portal.{资源}.{操作}`，如 `portal.tenant.view` / `portal.tenant.create` / `portal.tenant.disable` / `portal.tenant.license` / `portal.user.view` / `portal.user.reset-password` / `portal.role.view` / `portal.role.assign` / `portal.parameter.edit` / `portal.audit.view`。全部由 Portal 模块 Manifest 声明，随 §7.1 同步落库；具体清单在实施阶段一按现有门户控制器逐个梳理确定。
- **角色变更 → PortalUser.TokenVersion +1**：复用现有 `tv_u` 失效机制（门户角色/权限分配变更、用户被移除角色时，对受影响用户批量 +1），下次续期自动签发新权限集合。
- **DataScope 不适用门户侧**：平台级数据无「部门/个人」维度，门户 Token 不签发 data\_scope claim。

### 5.4 后端权限拦截

新增 `[AuthorizePermission("pur.order.approve")]` 特性（继承 `[Authorize]`），**过滤器核心逻辑**：

```csharp
public class PermissionAuthorizationHandler : AuthorizationHandler<PermissionRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, PermissionRequirement requirement)
    {
        // 上下文分流：旁路只认当前上下文自身的角色 claim，跨上下文身份一律不产生特权。
        var tenantId = context.User.FindFirstValue(QlxClaimConstants.TenantId);

        if (tenantId is not null)
        {
            // ── 租户上下文 ────────────────────────────────────────────
            // 1. TenantAdmin 零计算放行（租户内唯一旁路）
            var memberRole = context.User.FindFirstValue(QlxClaimConstants.MemberRole);
            // TODO: 建议在 Qlx.Abstractions 补充 MemberRole 值常量（TenantAdmin/OrdinaryMember）
            if (memberRole == "TenantAdmin")
            {
                context.Succeed(requirement);
                return Task.CompletedTask;
            }

            // 2. 普通成员：permissions_claim 逗号分隔 Split → 精确匹配。
            //    注意：即使该用户是门户管理员（PortalAdminFlag="1"），
            //    在租户内也仅按其租户成员权限判定，无任何额外特权。
            var raw = context.User.FindFirstValue(QlxClaimConstants.Permissions);
            if (raw is not null &&
                raw.Split(',', StringSplitOptions.RemoveEmptyEntries)
                   .Contains(requirement.PermissionCode))
            {
                context.Succeed(requirement);
            }
            else
            {
                context.Fail();
            }
            return Task.CompletedTask;
        }

        // ── 门户上下文（无 tenant_id claim）──────────────────────────
        // 1. 门户超管零计算放行（门户内唯一旁路）
        //    PortalAdminFlag 是 QlxClaimConstants 常量，值为 "is_portal_admin"；
        //    签发时写入 claim 值 "1"（PortalAuthenticationService 已确认）
        if (context.User.FindFirstValue(QlxClaimConstants.PortalAdminFlag) == "1")
        {
            context.Succeed(requirement);
            return Task.CompletedTask;
        }

        // 2. 普通门户用户：permissions_claim Split → 精确匹配 portal.* 权限码
        var portalRaw = context.User.FindFirstValue(QlxClaimConstants.Permissions);
        if (portalRaw is not null &&
            portalRaw.Split(',', StringSplitOptions.RemoveEmptyEntries)
               .Contains(requirement.PermissionCode))
        {
            context.Succeed(requirement);
        }
        else
        {
            context.Fail();
        }
        return Task.CompletedTask;
    }
}
```

**通道分工（v1.4 门户/租户完全同构）**：

| 上下文                       | 零计算旁路（唯一）                 | 普通用户判定                                                                 |
| ------------------------- | ------------------------- | ---------------------------------------------------------------------- |
| 租户上下文（有 tenant\_id claim） | `member_role=TenantAdmin` | `permissions_claim` Split → 精确匹配租户权限码；**`is_portal_admin`** **在租户内无效** |
| 门户上下文（无 tenant\_id claim） | `is_portal_admin=1`       | `permissions_claim` Split → 精确匹配 `portal.*` 权限码                        |

原 v1.2 的「三通道」（TenantAdmin → PortalAdmin → 普通成员）存在越权缺陷：门户管理员以普通成员身份进入租户时，`is_portal_admin` 通道会绕过该租户的权限约束。修正后门户身份 claim 仅在门户上下文有效，租户内权限**唯一**由该租户的成员身份决定。零计算场景（租户上下文 TenantAdmin / 门户上下文 PortalAdmin）直接 return，不做任何 Split 或查询。

#### 5.5.2 EF Core IQueryFilter 基类

位置：`Qlx.BuildingBlocks.MultiTenancy.DataScope.QlxTenantDataScopeQueryFilter`

```csharp
/// <summary>
/// 数据范围查询过滤器基类。业务模块 DbContext 继承 TenantDbContext 后，
/// 覆写 OnModelCreating 调用 Apply<TEntity>，即可获得行级过滤能力。
/// 过滤器会自动读取当前 Token 的 data_scope claim 生成 IQueryFilter。
/// </summary>
public static class QlxTenantDataScopeQueryFilter
{
    /// <summary>
    /// 向 DbContext.ModelBuilder 注册 DataScope 全局查询过滤器。
    /// </summary>
    /// <typeparam name="TEntity">需要数据范围过滤的实体类型。</typeparam>
    /// <param name="modelBuilder">EF Core modelBuilder。</param>
    /// <param name="getScope">从当前 Token 获取 DataScope 的 Func。</param>
    /// <param name="deptIdExpr">实体的组织 Id 属性表达式。</param>
    /// <param name="ownerIdExpr">实体的所有者/创建者 Id 属性表达式。</param>
    public static void Apply<TEntity>(
        ModelBuilder modelBuilder,
        Func<DataScope> getScope,
        Expression<Func<TEntity, long?>> deptIdExpr,
        Expression<Func<TEntity, string?>> ownerIdExpr)
        where TEntity : class, ITenantEntity
    {
        // 过滤器逻辑：
        // - All: 无过滤
        // - DeptAndChildren: 实体组织 Id ∈ (当前部门 + 所有子部门)
        // - Dept: 实体组织 Id == 当前部门
        // - Self: 实体创建者 Id == 当前用户 Id
        // TenantAdmin 自动走 All（data_scope_claim=All）
        var filter = BuildFilter(getScope, deptIdExpr, ownerIdExpr);
        modelBuilder.Entity<TEntity>().HasQueryFilter(filter);
    }
}
```

**本次交付**：基类 + 单元测试验证四种 DataScope 生成正确。各业务模块的具体实体接入延后到模块开发批次。

## 6 动态菜单机制设计

### 6.1 后端菜单生成 API

**端点**：`GET /api/tenant/menus`

**认证**：租户级 Token（中间件已校验模块许可）

**请求参数**：无（从当前 Token 的 claims 自动推导）

**响应 DTO（v1.5 扁平化）**：

```typescript
// 后端只下发「鉴权过滤后的扁平原始数据」，不做任何展示类组装。
// 树形结构 / mega menu 分组 / 快捷入口挑选全部由前端 menuStore 组装（P-7）。
interface MenuDataResponse {
  navGroups: NavGroupItem[]       // 可见的顶级导航分组（扁平、已按 SortOrder 排序）
  menus: MenuItem[]               // 当前用户可见的菜单（扁平、含 ParentCode/GroupName/SortOrder 原始字段）
}

interface NavGroupItem {
  code: string                    // workbench / business / finance / ...
  name: string
  moduleCodes: string[]           // 原始逗号字段拆分后的数组（仅类型转换，非展示组装）
  sortOrder: number
}

interface MenuItem {
  moduleCode: string
  code: string
  parentCode: string | null       // 层级关系以原始编码字段下发，前端组装树
  groupName: string | null
  name: string
  route: string
  icon: string | null
  requiredPermission: string | null
  sortOrder: number
  openMode: number                // 1=当前标签 2=新标签，数值代码下发，展示映射在前端
}
```

**后端生成逻辑（只过滤，不组装）**：

```
1. 取当前 Token claims: member_role, modules[], permissions_claim, tokenVersion
2. 从 por_navigation_groups 取顶级导航分组（缓存，§16）
   → 过滤：该分组 moduleCodes 与 modules[] 交集非空才保留
3. 从 por_module_menus 取上述模块的全部菜单（IsDeprecated=0）（定义字典缓存，§16）
4. 逐菜单判定可见性（鉴权裁剪，属安全逻辑非展示逻辑）：
   ├── member_role == TenantAdmin
   │   └── 所有菜单可见（仅按模块过滤，不按权限过滤）  ← 零计算
   ├── Menu.RequiredPermissionCode == null
   │   └── 仅需模块许可 → 可见
   └── Menu.RequiredPermissionCode != null
       └── permissions_claim.Split(',') 包含 → 可见
5. 直接返回扁平结果（navGroups + menus 两个扁平数组）
   ⚠️ 禁止在后端做：按顶级分组→模块→GroupName 嵌套组树、快捷入口取前 N 个、
      mega menu 结构预拼装——这些全是展示类计算，由前端 menuStore 完成（P-7）
6. 用户级结果缓存（§16.2 M3）：key = `QlxCacheKey.BuildTenantKey(tenantId, "perm", $"menus:{memberId}:tv{tokenVersion}")`，
   TTL 10min + 抖动；经 ICacheService.GetOrCreateAsync 读穿，互斥防击穿
```

**关键设计**：

- TenantAdmin 分支不做权限码匹配，直接全部可见（仅按模块过滤），零计算
- 菜单可见性**只认租户上下文的 member\_role 与 permissions\_claim**：门户管理员以普通成员身份进入租户时，菜单同样按其租户权限裁剪，不因门户身份看到更多菜单
- 结果按 `tokenVersion` 版本化 key 缓存 → 角色变更后 TokenVersion +1 → 旧 key 自然失效（TTL 兜底 + 定期清理，§16.5）
- 菜单生成是**纯只读查询 + 鉴权过滤**，权限判定全部基于 Token claims；**零展示类计算**（v1.5）

### 6.1.1 门户菜单 API（v1.4 新增，与租户同构）

**端点**：`GET /api/portal/menus`

**认证**：门户身份 Token

**逻辑**：与 `/api/tenant/menus` 同构但更简单——

```
1. 取当前 Token claims: is_portal_admin, permissions_claim, tv_u
2. 从 por_module_menus 取 ModuleCode = "portal" 的全部菜单（IsDeprecated=0，定义字典缓存 §16）
   （门户菜单由 Portal Manifest 声明，随 §7.1 同步；不参与模块许可过滤——
    门户端无 tenant_modules 概念；不参与 por_navigation_groups——
    顶级分组是租户工作台概念，门户端分组展示由前端按 GroupName 组装）
3. 逐菜单判定可见性（鉴权裁剪）：
   ├── is_portal_admin == "1" → 全部可见（零计算）
   ├── Menu.RequiredPermissionCode == null → 可见
   └── permissions_claim.Split(',') 包含 → 可见
4. 直接返回扁平 MenuItem[]（与租户同构，不组树）
5. 用户级结果缓存：key = `QlxCacheKey.BuildPortalKey("perm", $"menus:{userId}:tv{tv_u}")`，TTL 10min + 抖动
   （PortalUser.TokenVersion +1 → 旧 key 自然失效）
```

### 6.2 前端菜单加载流程（**无兜底版**）

```
用户 enterTenant() 成功
    │
    ▼
auth.store enterTenant() 已有逻辑
    │
    ├── 从 Token 解析:
    │   ├── member_role_claim → auth.memberRole
    │   ├── permissions_claim → Split(',') → auth.permissions （TenantAdmin 此字段为空数组，由指令层 memberRole 放行）
    │   ├── data_scope_claim → auth.dataScope
    │
    ├── 调用 menuStore.fetchMenus()
    │       │
    │       ├── GET /api/tenant/menus → 扁平 MenuDataResponse（v1.5）
    │       │       │
    │       │       ├── 成功 → 前端组装（展示类逻辑，P-7）：
    │       │       │         ① 按 parentCode 组装菜单树（纯前端纯函数，可单测）
    │       │       │         ② 按 navGroups → moduleCode → groupName 组装 mega menu
    │       │       │         ③ 快捷入口：从可见菜单挑选前 12 个（前端排序/截断）
    │       │       │       → 写入 menuStore.topMenus / menuTree / quickEntries / allMenus
    │       │       │         → 触发动态路由注册（§6.3，用扁平 allMenus 原始数据）
    │       │       │
    │       │       └── 失败（网络错误 / 401 / 403 / 500）
    │       │               │
    │       │               ├── 401/403 → Token 无效，跳转登录
    │       │               │
    │       │               └── 其他错误 → 设置 menuStore.error
    │       │                   SiteHeader 渲染 "菜单加载失败，请重试" + 重试按钮
    │       │                   路由守卫拦截业务模块路由，显示错误页面
    │       │                   ⚠️ 不回退到 navigation.ts 兜底！
    │       │
    │       └── SiteHeader 监听 menuStore，重新渲染
    │
    └── 完成 → 路由守卫正常放行
```

**移除 navigation.ts 兜底的理由**：

1. **安全优先**：API 不可用时回退到硬编码菜单可能显示用户没有权限的菜单项（权限误判）
2. **用户体验**：API 失败 = 系统异常，应该让用户感知到并提示刷新，而不是静默降级到旧数据
3. **减少维护成本**：只维护一个数据源（后端 API），不需要同步两套菜单定义

**新增 Store**：`src/stores/menu.ts`（Pinia），包含 `topMenus`、`menuTree`、`allMenus`、`quickEntries`、`loading`、`error` 状态和 `fetchMenus() / retryFetch()` action；**树组装/mega menu/快捷入口挑选为独立纯函数**（`utils/menu-tree.ts`），配套 vitest 单测（v1.5，树组装属前端职责）。

### 6.3 前端模块路由与菜单的对接

**动态注册路由**：

```typescript
// menuStore.fetchMenus() 成功后
const routes = menuStore.allMenus.map(menu => ({
  path: menu.route,
  component: () => import(`@/views/modules/${menu.moduleCode}/${menu.code}.vue`),
  meta: {
    requiresPermission: menu.requiredPermission,
    title: menu.name,
    icon: menu.icon
  }
}))
router.addRoute({ path: '/module', children: routes })
```

**关键**：菜单 API 返回的 route 字段就是前端路由，不再硬编码路由表。旧的 `/module/:moduleCode/:itemCode` 通配路由**移除**（不再需要，会拦截动态注册的具体路由）。

### 7.1 Manifest 自动同步

```
Host.OnApplicationStarted()

遍历所有 IModule 实现（DI 容器已注册）

    │

        module.Manifest.TopNavigationGroups[] → Upsert por_navigation_groups
```

**安全约束**（详见 §15 数据防篡改）：

- Manifest 数据是**权威只读源**——运行时**不提供 API 写 por\_\* 定义表**
- Upsert 时保留数据库中已存在但 Manifest 已移除的记录，标记为 `IsDeprecated = true`（避免生产误删）
- Upsert 冲突处理：Manifest IsDeprecated=false 覆盖数据库 IsDeprecated=true 的同名记录（版本升级场景）

### 7.2 Bas 模块已有 CRUD 的对接

Bas 模块已有 `Role`/`RolePermission`/`MemberRole` 的完整 CRUD。

**需要补充**：

1. **角色变更后触发 TokenVersion +1**：`SaveRolePermissionsAsync` / `SaveRoleMembersAsync` / `DeleteRoleAsync` 执行后，查询该角色关联的所有 MemberRole → 批量 TenantMember.TokenVersion +1
2. TokenVersion +1 后 → 下次登录自动重新签发新 Token → 权限变更生效

TokenVersion +1 SQL：

```sql
UPDATE por_tenant_members SET token_version = token_version + 1 WHERE id IN (
    SELECT DISTINCT tenant_member_id FROM bas_member_roles WHERE role_id = @changedRoleId AND tenant_id = @tenantId
)
```

## 12 边界定义与兼容性

### 12.1 架构约束

| 约束           | 满足方式                                                                                    |
| ------------ | --------------------------------------------------------------------------------------- |
| 模块互引禁令       | Portal 通过 **Abstractions 契约** **`ITenantRolePermissionQuery`** 跨库查询 Bas 数据，由 Bas 实现     |
| 四层库拓扑        | 权限定义 + 菜单定义 + 导航分组 + **门户角色分配（v1.4）** → 门户库 `por_*`；租户角色权限分配 → Bas 租户库 `bas_*`；**不新增库** |
| 模块许可中间件优先    | ModuleLicenseMiddleware 是 L0 拦截；L1-L4 判定在其之后                                            |
| EF Core 查询铁律 | `ITenantRolePermissionQuery` 实现单条 SQL + Join；禁止 N+1                                     |
| ID 混淆        | RolePermission.PermissionCode 是字符串编码，不涉及雪花 ID                                           |
| Token JWT 大小 | TenantAdmin 零计算（不枚举权限码 → Token 最小）；普通成员 permissions\_claim 逗号分隔紧凑字符串                    |

### 12.2 向后兼容

| 场景                                                 | 处理                                                                               |
| -------------------------------------------------- | -------------------------------------------------------------------------------- |
| 旧 Token 无 permissions\_claim / member\_role\_claim | 降级：`CurrentUserService` 实时查库填充；\[AuthorizePermission] 检测无 claim 时走查库             |
| 旧门户 Token 无 permissions\_claim（v1.4）               | 超管（is\_portal\_admin=1）不受影响；普通门户用户续期时自动签发新 claim，续期前窗口期按「无 claim 查库兜底」处理，与租户侧同策略 |
| TenantAdminService 已有 CRUD                         | 不破坏现有 API，仅在三个入口后增加 TokenVersion +1 副作用                                          |
| 开发环境首次启动（空库）                                       | `IModuleManifestSyncService` 一次性初始化全部种子数据                                        |

### 12.3 安全边界

| 风险                                | 防护                                                                                |
| --------------------------------- | --------------------------------------------------------------------------------- |
| 普通用户伪造 permissions claim          | \[AuthorizePermission] 从 Token 签名验证，OpenIddict 签名密钥管理                             |
| TenantAdmin 伪造 member\_role claim | 同上，签名校验无法篡改                                                                       |
| 门户身份 claim 渗入租户上下文越权              | 双层防护：① 租户 Token 签发不复制门户特权 claim ② 租户上下文 Handler/菜单 API/前端指令均不读取 is\_portal\_admin |
| 前端禁用 v-permission = 绕过            | 后端 \[AuthorizePermission] 强制拦截，前端是 UX 增强不是安全边界                                    |
| Manifest 种子被生产环境手工修改              | **三层防护**：① 应用层不提供写 API ② EF SaveChanges 拦截器拒绝非 Sync 来源 ③ 每次启动 Upsert 对齐覆盖         |
| 权限变更后旧 Token 仍有效                  | TokenVersion +1 → 旧 Token 续期时被拒绝（续期服务校验 TokenVersion）                             |
| 跨库查询安全                            | Bas 实现内 TenantId 强制过滤，禁止查询其他租户数据；接口只读无写操作                                         |

### 13.3 E2E 冒烟

1. **租户管理员登录** → 全量菜单渲染 + 全部按钮可见 + Token 无 permissions\_claim（零计算）
2. **普通角色登录** → 菜单按权限裁剪 + 无权限按钮隐藏 + Token 有 permissions\_claim
3. **角色权限变更** → 重新登录后菜单更新（TokenVersion +1 生效）
4. **断网刷新** → 显示 "菜单加载失败，请重试"（**不降级到硬编码**）
5. **\[AuthorizePermission] 后端拦截** → curl 直接调 API 返回 403
6. **门户管理员进入其非管理租户** → 菜单/按钮按该租户普通成员权限裁剪，curl 直调无权限 API 返回 403（门户身份不旁路）
7. **门户超管登录** → 门户全量菜单 + Token 无 permissions\_claim（零计算）（v1.4）
8. **普通门户用户登录** → 门户菜单按 `portal.*` 裁剪 + 无权限按钮隐藏 + curl 直调无权限门户 API 返回 403；角色权限变更后 tv\_u +1，重新登录菜单更新（v1.4）

### 13.5 缓存与职责边界验证（v1.5）

| 场景        | 验证方式                                                      | 通过标准                                                  |
| --------- | --------------------------------------------------------- | ----------------------------------------------------- |
| 缓存击穿防护    | 并发 100 请求同时访问过期热 key（菜单/定义字典）                             | 回源工厂仅执行 1 次（跨实例部署下同样成立，分布式锁生效），其余请求获得一致结果             |

### 15.2 拦截器设计

```csharp
/// <summary>
/// Manifest 定义表只读保护拦截器。
/// 拦截 PortalDbContext 中对 ModuleDefinition / PermissionDefinition /
/// ModuleMenu / NavigationGroup 的越权写入，仅允许 IModuleManifestSyncService
/// 标记的安全上下文写入。
/// </summary>
public sealed class ManifestDefinitionReadOnlyGuardInterceptor : SaveChangesInterceptor
{
    /// <summary>
/// IModuleManifestSyncService 调用时设置此值为 true 跳过拦截器。
/// 使用 AsyncLocal 保证在 async/await 流中正确随上下文流动
/// （ThreadStatic 在 await 边界间无法正确传递，禁止使用）。
/// </summary>
public static readonly AsyncLocal<bool> BypassGuard = new();

    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        if (BypassGuard.Value || eventData.Context is not PortalDbContext db)
            return base.SavingChangesAsync(eventData, result, cancellationToken);

        var tracked = db.ChangeTracker.Entries()
            .Where(e => e.State is EntityState.Added or EntityState.Modified or EntityState.Deleted);

        foreach (var entry in tracked)
        {
            if (entry.Entity is ModuleDefinition or PermissionDefinition or ModuleMenu or NavigationGroup)
            {
                throw new InvalidOperationException(
                    $"禁止写入 Manifest 定义表 {entry.Entity.GetType().Name}。" +
                    "权限点/菜单/导航分组只能通过 IModuleManifestSyncService 由模块 Manifest 同步。");
            }
        }
        return base.SavingChangesAsync(eventData, result, cancellationToken);
    }
}
```

**注册位置**：PortalDbContext.OnConfiguring 内，`options.AddInterceptors(new ManifestDefinitionReadOnlyGuardInterceptor())`。

**绕过方式**（仅 `IModuleManifestSyncService.SyncAllAsync()` 使用）：

```csharp
ManifestDefinitionReadOnlyGuardInterceptor.BypassGuard.Value = true;
try
{
    await portalDb.SaveChangesAsync(ct);
}
finally
{
    ManifestDefinitionReadOnlyGuardInterceptor.BypassGuard.Value = false;
}
```

### 15.3 AsyncLocal 正确性说明

| 项目                      | 说明                                                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **为什么不用 ThreadStatic？** | ThreadStatic 在 async/await 流中 await 边界后可能切换线程，值丢失导致拦截器意外触发。SyncAllAsync 全程是 async 方法，内部有多次 await，ThreadStatic 不可靠 |
| **AsyncLocal 保证**       | AsyncLocal\<T> 值随 ExecutionContext 自动在 await 间流动；SyncAllAsync（async）内任意 await 后 BypassGuard.Value 仍为 true         |
| **并发安全**                | AsyncLocal 按异步执行上下文隔离，不跨请求/不跨 Scope；SyncAllAsync 串行化运行（Host.Startup SemaphoreSlim），无并发风险                          |
| **意外残留？**               | finally 块保证 SyncAllAsync 结束后恢复为 false；即使异常也不会泄漏到后续请求                                                              |

> 强制标准全文见 [.trae/rules/global-cache-layering-standard.md](file:///e:/ERPv2/eprv3/.trae/rules/global-cache-layering-standard.md)（缓存规范 + 前后端职责边界 + 双层校验）。本节是权限域的落地设计；与规则文件不一致时以规则文件为准。

### 16.2 缓存项矩阵（权限域全量）

- 租户级：`QlxCacheKey.BuildTenantKey(long tenantId, string modulePrefix, string businessKey)` → 物理键 `tenant:{tenantId}:{modulePrefix}:{businessKey}`（以 long 型 tenantId 构建，**不是** string tenantCode）
- 门户/平台级：`QlxCacheKey.BuildPortalKey(string modulePrefix, string businessKey)` → 物理键 `_portal:{modulePrefix}:{businessKey}`（`_portal` 是门户保留租户码，带下划线前缀）

| -- | -------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------- | ---------- | ---- | ----------------------------------------------------------------------------------------------------------------- |
| M1 | 权限点定义字典（门户侧，含租户侧消费只读投影）         | `QlxCacheKey.BuildPortalKey("perm", "defs")`                                                           | `_portal:perm:defs`                                 | 30min ±20% | 60s  | Manifest 同步（SyncAllAsync）完成后 `RemoveByPrefixAsync("_portal:perm:")`                                        |

### 16.3 一致性方案（失效优先，禁双写）

1. **写路径只删缓存不写缓存**：任何权限相关数据变更（Manifest 同步 / 角色分配 / 许可变更）先提交数据库事务，**提交成功后**再 `RemoveAsync` / `RemoveByPrefixAsync`；下一个读请求经 `GetOrCreateAsync` 重建。**禁止「先更新缓存再写库」「双写」「先删缓存再写库」**。
2. **删除与重建串行化**：重建只能经 `GetOrCreateAsync`（互斥），保证同一 key 只有一个加载者回源，其余等待后读新值——消除「删后并发重建竞态」产生的脏读窗口。
3. **版本化 key 天然隔离**：M3/M4/M5 内嵌 tokenVersion/tv\_u，角色/权限变更后新版本 key 与旧版本 key 物理隔离，不存在「旧值覆盖新值」。
4. **漂移窗口兜底**：若删缓存失败（Redis 抖动），旧值最长存活至 TTL 到期（≤10min/30min）；权限收紧场景同时依赖 tokenVersion +1（新 Token 换 key 立即生效），缓存漂移不影响安全边界（鉴权以 Token claim 为准，缓存仅服务于菜单/兜底路径）。

### 16.4 防护机制小结

| 风险                  | 机制                                                   |
| ------------------- | ---------------------------------------------------- |
| 缓存击穿（热点 key 过期并发回源） | `GetOrCreateAsync` 互斥 + B-16 跨实例分布式锁（SET NX + 短退避重读） |
| 缓存穿透（查询不存在的成员/定义）   | 空值缓存：NullMarker 短 TTL（30\~60s）                       |
| 缓存雪崩（大量 key 同时过期）   | TTL 基线 + ±10%\~20% 随机抖动；禁止批量同 TTL 写入                 |
| 脏读（写后读到旧值）          | §16.3 失效优先 + 版本化 key + 互斥重建                          |

### 16.5 定期清理任务

新增内置任务 `cache.permission.sweep`（随 Support 模块 Manifest 注册 `IJobHandler`，走后台任务中心管线）：

- **调度**：每日 04:30（六段 CRON `0 0 30 4 * *`）
- **职责**：SCAN 匹配 `_portal:perm:*`（门户侧）与各租户 `tenant:{tenantId}:perm:*` 前缀（租户侧，tenantId 从 por_tenant_members / 活跃租户列表动态获取），清理：① 旧 tokenVersion/tv\_u 残留 key（解析 key 中版本号，与 por\_users / por\_tenant\_members 当前版本比对，版本落后即删）② 已下线/已删除租户的 `tenant:*:perm:` 前缀 key ③ NullMarker 超期残留
- **防护**：SCAN 分批（500/批）+ 批次间让出，禁止 KEYS；任务本身幂等，重入安全
- **意义**：TTL 是第一道兜底，本任务是第二道，保证无效缓存**及时**回收，控制内存水位
