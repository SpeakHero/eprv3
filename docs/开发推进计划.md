## 总体推进策略

### 依赖优先级排序

```
横切基础设施（前置，所有模块依赖）
        ↓
支撑功能契约层（接口下沉 Abstractions，业务模块才能写审批/通知/附件）
        ↓
基础信息中心（bas_，所有业务模块的数据源底座）
        ↓
商品管理 → 物流管理（库存本体在商品，出入库由物流驱动）
        ↓
采购 + 销售（可并行，各依赖 基础信息 + 商品 + 物流）
        ↓
人员管理 + 合同管理（可并行，依赖 基础信息）
        ↓
票据管理（对接采购/销售/财务的票据三单匹配）
        ↓
财务管理（依赖票据核验、对接成本/凭证）
        ↓
项目管理（依赖 基础信息组织架构 + 合同额）
        ↓
设备与租赁管理（依赖 合同 + 财务 + 项目）
```

> **实施顺序**：**严格顺序不并行**：2A（契约下沉+状态机+Messaging，无数据库）→ 2B（Support 工程+文件中心）→ 2C（后台任务中心）→ 2D（信息中心+SSE+D13）→ 2E（审批中心）→ 2F（导入导出+打印+审计过滤+前端组件）。每子阶段 8 步门禁（restore→build 0 警告→新增测试全绿→架构测试→Host 冒烟→代码审查→ValidateOnStart→文档更新）全部通过才进下一个。
> **总体原则**：接口下沉 `Qlx.Abstractions`，实现集中在 `Qlx.Modules.Support`；业务模块只依赖接口，严禁直连支撑模块实现；业务阈值走 `por_parameters`，config 仅作默认兜底。
> **详细落地计划**：本文档以下仅保留关键决策摘要与变更说明，**2A~2F 子阶段的完整任务拆解、实体定义、验收清单、风险预案、交付矩阵等全部内容均在独立文档** [阶段二支撑功能开发方案-v2.md](阶段二支撑功能开发方案-v2.md)。

## 关键约束与注意事项

| # | 约束 | 违反后果 |
|---|------|---------|
| 1 | 模块间通信**只允许**事件总线 + Abstractions 同步查询接口 | 禁止跨模块 Join、禁止跨模块实现引用、禁止跨模块表直连 |
| 2 | 每个模块**独立 csproj + 独立 DbContext + 独立表前缀** | 模块无法独立部署、许可启停无法生效 |
| 3 | 业务单据编号**一律走 `IDocumentNumberGenerator`**，禁止模块自造 | 编号规则不统一、审计追溯困难 |
| 4 | 缓存**只依赖 `ICacheService`**，禁止直连 StackExchange.Redis | 提供方切换时改业务代码、与架构解耦原则冲突 |
| 5 | 对外 API ID **一律 Hashids 混淆**，内部/数据库只碰真实 long | 安全风险、外部可枚举 |
| 6 | 审批流**只依赖 `IApprovalService`**，禁止模块自建审批引擎 | 审批流程割裂、统一管控失效 |
| 7 | 财务凭证**必须由业务单据自动生成**，人工不可改 | 业财数据不一致、审计留痕断裂 |
| 8 | 配置**一律强类型 Options + ValidateOnStart**，禁止裸读 `IConfiguration["..."]` | 配置缺失运行时爆炸、类型安全丢失 |
| 9 | 所有代码**严格遵循** `.trae/rules/global-csharp-standard.md` | 编译警告即错误、CI 红线 |
| 10 | 模块 Manifest 的 `ModuleCode` **必须与** `tenant_modules.module_code` **一致** | 许可启停无法关联 |
| 11 | **租户路由全自研**（TenantContextMiddleware + ITenantDatabaseResolver + TenantDbContext），不引入 Finbuckle.MultiTenant | 第三方 ASP.NET Core 集成层已废弃，混用将导致与「独立数据库实例」冲突 |
| 12 | **PortalDbContext（固定连接串门户库）与 TenantDbContext（动态路由租户库）是两套独立 DbContext，禁止混用** | 门户/租户数据串库、多租户隔离崩塌 |
| 13 | **业务运行阈值一律走数据库参数表** `por_parameters`（经 `ISystemParameterProvider` 读取），config 同名值仅作兜底 | 阈值改一次要发版、系统管理无法在线维护 |
| 14 | **租户数据库模式（Shared/Isolated）只能由门户管理员人工决定（本期），且仅允许 Shared→Isolated 单向升级**；会员/套餐映射为预留能力，只产生推荐、**永不自动切换实际模式**；共享连接串只来自 `Qlx:Tenancy:SharedDatabase`，禁止在代码里硬编码库名/主机 | 自动切换会在付费体系未上线前误改租户数据归属；降级会丢隔离与审计链 |
| 15 | **任何数据访问必须经过三层隔离**：实体必含 `TenantId` + 唯一索引必含 `TenantId` + 走 `TenantDbContext`；禁止裸 SQL 绕过过滤，确需 Raw SQL 必须显式带租户谓词并由 RLS 兜底 | 租户共享库下漏一处即跨租户数据泄露 |
| 16 | **禁止对租户共享库执行 `DROP DATABASE`/`EnsureDeleted`**；租户共享库迁移必须在数据库级应用锁内只执行一次 | 一次误删即全共享租户数据丢失 |
| 17 | **固定四类库（共享库/门户库/租户共享库/独立租户库），禁止新增第五个库**；四库必须独立配置与独立账号；禁止跨库 Join/事务、禁止门户库承载业务表、禁止共用账号 | 控制面与数据面混在一起，租户侧账号即可触达路由与加密凭据 |
| 18 | **平台审计只审计平台对租户的管理动作**，租户内部操作只落本租户 `log_*`；日志两侧互不复制、不跨库直查；**平台公告/任务/消息只写共享库 `glb_*` 一份**，租户只读 + 本地状态叠加，禁止复制正文、禁止跨库 JOIN；全局项租户不可拒收/删除 | 审计边界混淆会把租户内部行为纳入平台责任；逐租户复制造成写放大与副本漂移 |
