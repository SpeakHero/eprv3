# 支撑功能详设：03 后台任务中心

> 对应《项目需求.md》五章支撑功能（系统管理能力扩展）｜ 版本 v1.1 ｜ 2026-10-20
> 平台级公共能力：统一承载定时调度与耗时后台任务。调度引擎采用 **Hangfire**（.NET 技术栈）；系统内置任务按**插件化 + 工厂 + 多态 + 统一接口**设计，用户可对内置任务自定义配置（启用/计划/参数）；耗时任务后台执行，完成后经《02-信息中心.md》SSE 通知用户。多租户机制、模块插件机制（IModule Manifest）与审计遵循《saas-architecture-spec.md》2.3。

## 2. 核心实体与字段明细

### 2.1 任务定义 task_definition（插件注册，系统内置）

| 字段 | 类型 | 必填 | 说明 / 校验 |
|------|------|------|------------|
| task_id | bigint PK | 是 | 主键 |
| task_code | varchar(64) | 是 | 任务编码，唯一（插件声明，如 `stock.alert.scan`） |
| task_name / category | varchar | 是 | 名称与分类（库存/财务/票据/系统等） |
| handler_type | varchar(256) | 是 | 处理器全限定类名（实现统一接口 IJobHandler，插件装配时注册） |
| param_schema | json | 否 | 参数 schema（配置页动态渲染表单用，字段/类型/必填/默认值） |
| default_cron | varchar(32) | 是 | 默认调度计划（六段式 CRON） |
| timeout_sec / retry_limit | int | 是 | 单次执行超时、失败重试上限 |
| is_system_locked | bit | 是 | 核心任务锁定标识（禁止停用，仅可调整计划，如审计归档） |

### 2.2 任务配置 task_config（用户自定义，租户级）

config_id、task_id（引用定义）、enabled、custom_cron（为空=用默认）、custom_params（json，按 param_schema 校验）、next_fire_at（系统计算）、updated_by/updated_at。
管控：配置变更留痕（旧值/新值/操作人/时间）；is_system_locked=1 的任务 enabled 不可改。

### 2.3 任务执行实例 job_execution

| 字段 | 类型 | 必填 | 说明 / 校验 |
|------|------|------|------------|
| exec_id | bigint PK | 是 | 主键（与 Hangfire JobId 映射） |
| task_code | varchar(64) | 是 | 冗余任务编码 |
| trigger_type | enum | 是 | SCHEDULE 计划 / MANUAL 手动 / RETRY 自动重试 / API 调用 |
| initiator_id | bigint | 否 | 发起人（手动/用户耗时任务） |
| params_json | json | 否 | 本次执行参数快照 |
| status | enum | 是 | QUEUED 排队 / RUNNING 执行中 / SUCCESS / FAILED / CANCELED |
| progress | int | 是 | 进度 0-100（耗时任务由处理器上报） |
| result_summary | varchar(512) | 否 | 结果摘要（如「导出 12,340 行」「预警扫描命中 5 条」） |
| result_file_id | bigint | 否 | 结果文件（导出类任务），经消息跳转下载 |
| error_detail | text | 否 | 失败堆栈摘要（完整日志进日志系统） |
| started_at / ended_at / duration_sec | - | 否 | 时序与耗时 |

### 2.4 执行日志 job_log

log_id、exec_id、level（INFO/WARN/ERROR）、content、created_at。按执行实例聚合，支持下载；保留期参数（默认 90 天）。

## 3. 任务框架设计规范

### 3.1 统一接口与插件化（多态 + 工厂）

- **统一接口** `IJobHandler`：`TaskCode` 标识、`ParamSchema` 参数描述、`ExecuteAsync(JobContext ctx)` 执行体（ctx 含租户上下文、参数、进度上报回调、取消令牌）、`OnCompleted / OnFailed` 可选钩子；
- **插件化注册**：任务处理器随业务模块装配（模块插件机制：实现 `IModule` Manifest 声明，宿主启动时扫描），启动时扫描实现 `IJobHandler` 的类自动注册 task_definition；模块停用（tenant_modules 许可关闭）时其任务自动暂停；
- **工厂分发**：`JobHandlerFactory` 按 task_code 从 DI 容器解析处理器实例，调度引擎只面向工厂与接口，不感知具体任务（新增任务=新增插件类，零改动框架）；
- **多态扩展**：提供基类 `ExportJobHandler`（导出走模板+文件落地）、`BatchJobHandler`（分批处理+进度上报）等，业务任务按需继承。

### 3.2 调度计划（Hangfire + 六段式）

- 表达式格式：`秒 分 时 日 月 周 [年]`（Hangfire 兼容 CRON 扩展，年段可选）；公共组件 **cron-builder** 可视化生成，支持「每天/每周/每月/自定义」快捷模式与原始表达式切换；
- 预览：配置时展示未来 5 次触发时间，避免误配；
- 时区：统一按租户所在时区（Asia/Shanghai）计算；
- 执行保障：Hangfire 持久化队列（租户库）、失败自动重试（指数退避，上限 retry_limit）、超时强制取消、服务器重启后任务恢复；同一 task_code 单实例防并发（分布式锁，租户维度）。

### 3.3 耗时任务后台化（用户触发类）

适用场景：大数据量导出、批量导入、批量算薪、报表汇总、凭证批量生成等。
规范：
1. 业务页面发起耗时操作 → 后端判定超同步阈值（参数，默认 3 秒）即转后台：创建 job_execution（trigger_type=MANUAL/API），立即返回 exec_id；
2. 前端跳转/引导至「我的后台任务」，不经轮询——进度由处理器上报，经信息中心 SSE 推送 `task.progress` 事件（进度变化≥10% 才推送，防风暴）；
3. 完成/失败 → 信息中心消息（msg_type=TASK，biz_ref=exec_id）：成功消息附 result_file_id 下载入口；失败消息附原因摘要与重试入口；
4. 取消：执行中任务授权用户可取消（协作式取消令牌）。

## 4. 业务规则与校验

| # | 规则 | 说明 |
|---|------|------|
| R1 | 租户隔离 | 任务定义平台共享，配置与执行实例严格按租户隔离；执行时注入租户上下文（独立数据库连接），禁止跨租户数据访问 |
| R2 | 模块许可联动 | 任务所属模块许可停用→该模块全部任务自动暂停并标识；重新开通后按配置恢复 |
| R3 | 配置生效 | 计划/参数修改即时生效于下一次触发；执行中实例不受影响 |
| R4 | 锁定任务 | is_system_locked=1 的核心任务（审计归档、会话清理等）禁止停用，仅可调整计划窗口 |
| R5 | 防并发 | 同一租户同一 task_code 禁止并发实例；到点有在途实例时跳过本次并记录 SKIPPED 日志 |
| R6 | 失败熔断 | 连续失败 N 次（参数，默认 5）自动暂停该任务并告警管理员，人工处理后恢复 |
| R7 | 手动触发权限 | 手动执行需「任务手动触发」按钮权限；触发参数按 param_schema 校验，触发记录留痕 |
| R8 | 进度推送节流 | 进度事件变化 <10% 不推送；终态（成功/失败/取消）必推 |
| R9 | 结果文件管理 | 导出类结果文件保留期参数（默认 7 天），过期自动清理；下载留痕 |
| R10 | 日志保留 | 执行日志按保留期归档清理；失败实例日志延长保留（参数，默认 180 天） |
| R11 | 审计 | 配置变更、手动触发、取消、熔断恢复全部进入租户内审计；锁定任务计划变更双人复核（系统管理参数） |

## 6. 权限点清单

**菜单**：后台任务（管理员）→ 任务定义 / 任务配置 / 执行监控 / 执行历史 / 告警配置；我的后台任务（全员）。

**按钮**：任务启用/停用、计划配置、参数配置、手动触发、取消执行、失败重试、日志下载、结果下载、告警接收人配置。

**数据权限**：任务管理仅管理员角色（集团/子公司管理员按组织范围）；「我的后台任务」仅本人发起的实例；监控与历史按管理员组织范围。

**字段权限**：error_detail 堆栈信息仅系统管理员可见；params_json 中含敏感参数（如薪月份）按角色脱敏。

## 7. 与其他模块联动

| 触发事件 | 目标模块 | 数据流 |
|---------|---------|-------|
| 进度/完成/失败通知 | 信息中心 | SSE `task.progress` 事件 + TASK 消息（模板渲染，biz_ref=exec_id，附结果下载） |
| 预警类任务命中 | 信息中心 | 按各模块预警模板生成 ALERT 消息 |

| 审计留痕 | 审计体系 | 配置/触发/取消/熔断事件入租户内审计，锁定任务变更入门户审计 |
| 阈值参数 | 系统管理 | 同步阈值、熔断次数、保留期等统一参数组 |

## 9. 落地偏差（2C）

以下为 2C 批次（调度引擎基座 + 任务实体/调度/服务 + 8 个支撑任务 + 迁移 + 测试）相对本文档前述设计的落地偏差与补充约定：

| # | 事项 | 偏差说明 |
|---|------|---------|
| 1 | 任务编码沿用 | 回收站清理任务落地编码为 `file.recycle.cleanup`（沿用 `FileTaskCodes` 既有编码族），方案稿中的 `file.recycle.purge` 不再采用；`file.chunk.assemble` / `file.format.convert` 本期保留桩实现（`FileStubHandlers`，返回明确未就绪提示），能力随文件中心后续批次落地 |
| 2 | 观测模式任务 | `message.archive.run` / `audit.archive` / `session.clean` 三个任务的目标持久能力尚未落地，Handler 以观测模式执行——仅输出统计日志并落 SUCCESS，不落 FAILED（避免调度周期性告警风暴）；能力落地后仅替换 Handler 实现，任务编码与定义不变 |
| 3 | 命名空间 | 系统任务物理目录 `Jobs/System/`，命名空间定为 `Qlx.Modules.Support.Jobs.SystemJobs`（避免与 BCL `System` 命名空间冲突） |
| 4 | 表名前缀 | Support 模块 DbContext 模块前缀为 `fil_`；4 张任务表经实体级 `[TenantTablePrefix("")]` 声明（空串 = 跳过前缀拼接，DbSet 名自带 `job_` 语义），最终表名 `job_definitions` / `job_configs` / `job_executions` / `job_logs`，迁移 `AddSupportJobTables` 与之一致 |
| 5 | 幂等守卫修复 | `SupportJobExecutionStore.TryTransitionAsync` 补状态机守卫（`JobStateMachine.CanTransition`），拒绝终态复活 / 跳级等非法转移，保证「已取消 / 终态任务跳过 Hangfire 执行」的幂等语义 |
| 6 | 依赖版本 | `Qlx.BuildingBlocks` 的 Newtonsoft.Json 升至 13.0.4（消除 NU1903 漏洞警告） |
| 7 | 测试策略 | `SupportJobExecutionLogQuery` 测试采用 InMemory 提供程序（SQLite 不支持 DateTimeOffset 比较翻译；生产 SQL Server 无此限制）；架构测试两处更新——模块程序集禁引 Hangfire 独立断言、租户表名归属断言放行实体声明的覆盖前缀 |
| 8 | 验证基线 | 构建 0 警告 0 错误；全量 534 个测试通过（Architecture 14 + BuildingBlocks 520），本批次新增 62 个（CRON 23 / 状态机 8 / 重试延迟 6 / 执行运行器 7 / 调度器 13 / 日志查询 4 / 架构守护 1） |
| 9 | ServiceJobs 服务任务 | Manifest 新增 `ServiceJobs`（`ServiceJobDefinition`）：file.upload/download/preview/metadata/list/delete/restore/recycle.list/acl.set（SYNC）+ file.export/file.import.batch（ASYNC）共 11 个**无调度按需任务**种子入 job_definitions（cron 空串、next_run_at 恒 NULL、Enabled 随模块许可），解决「处理器已注册但租户库无定义」导致 SubmitAsync 报 404 的问题；`JobDefinitionEntity` nextRunAt 改可空，调度候选查询不受影响。原 §9-5「按需任务不进 Manifest」（04-文件存储中心.md §9-5）由此条取代——按需任务改经 ServiceJobs 进定义表但仍不参与调度 |
| 10 | 运行期参数 RuntimeParameters | `TaskSubmitRequest` 新增 `RuntimeParameters`：仅内存传递、永不持久化/序列化，承载不可 JSON 序列化的值（如上传内容 Stream）；**SYNC 专属**，ASYNC 携带即被调度器拒绝（ValidationException），键冲突以运行期字典为准。原实现将 Stream 放入持久化 Parameters，提交序列化触发「Timeouts are not supported on this stream」 |
| 11 | 参数 JSON 往返还原 | 持久化参数经 JSON 序列化/反序列化后值一律为 JsonElement，处理器 `is string`/`is long` 判定全部失败（file.upload 409「缺少参数 fileName/sizeBytes」）；`JobExecutionRunner.BuildContext` 统一解包还原 string/long/double/bool/null，Object/Array 保持 JsonElement 由处理器自行反序列化。整数分支必须 `(object)l` 显式装箱——三元 `TryGetInt64 ? l : GetDouble()` 公共类型推断为 double 会导致 `is long` 恒假（已有回归测试锚定） |
| 12 | 定义查询懒种子兜底 | `SupportJobExecutionStore.GetDefinitionAsync` 拆为「查询 → 空则 EnsureTenantSeededAsync → 重查一次」，新租户/重建库首次提交即命中定义，不依赖 Host 启动期种子时序（启动期仅处理已激活租户） |
| 13 | 终态通知推送租户上下文 | 冒烟发现：调度器提交的 approval.timeout.scan 执行（Hangfire 重试），租户上下文未初始化（tenantId=0）时处理器与终态通知推送均抛「租户 Id 未初始化」；终态通知失败仅告警不阻断链路（PushSafeAsync 语义不变）。遗留：Hangfire 存量失败作业（旧 Host 会话入队的 tenantId=0 执行）将持续重试至额度耗尽，随 job.execution.clean 清理 |
