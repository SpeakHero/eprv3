## 1. 项目概述

### 1.1 项目定位

本项目是一套面向多租户场景的 SaaS 化 ERP 系统（以下简称 **ERPv3**），采用"门户统领全局 + 租户自主管理"的双层管理模型，为企业客户提供按需订阅、独立部署的企业资源规划解决方案。

### 1.2 核心设计原则

| 原则               | 说明                                                     |
| ---------------- | ------------------------------------------------------ |
| **门户统领、租户自治**    | 门户负责全局管控，租户内部管理完全自主                                    |
| **数据物理隔离（混合）**  | 默认落租户共享库（`TenantId` + 三层隔离），有隔离诉求的租户由门户人工升级为独立库；门户库始终独立 |
| **统一身份、多租户主**    | 一个自然人先在门户完成身份注册/认证，再可被多个租户关联为成员（参考电子税务局模式）             |
| **全局唯一标识、展示名自由** | 登录标识符（手机号/证件号/login\_account）全局唯一，displayName 仅供展示、可重名 |
| **统一入口、多方式登录**   | 门户提供统一认证入口，支持内外部多种登录方式                                 |
| **权限分层、状态联动**    | 门户全局开关优先，租户本地权限在门户框架内生效                                |
| **按需授权、模块化交付**   | 模块和功能由门户按需启用，租户在授权范围内配置                                |
| **平滑扩展、预留商业能力**  | 架构预留会员等级、充值付费等商业化能力                                    |

### 1.3 关键术语

| 术语                       | 定义                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------- |
| **门户（Portal）**           | SaaS 运营管理后台，由系统运营方使用，管理所有租户                                                             |
| **租户（Tenant）**           | 购买 ERPv3 服务的企业客户，拥有独立数据库                                                                |
| **PortalUser（门户用户/自然人）** | 门户层的统一身份，一个自然人对应一条 PortalUser 记录，通过全局唯一标识（phone/id\_card/login\_account）注册。可以同时是多个租户的成员 |
| **TenantMember（租户成员）**   | PortalUser 在某个租户内的成员关系记录。同一 PortalUser 在不同租户内各有独立的成员记录，携带各自的角色、组织、状态                    |
| **租户管理员**                | TenantMember 中被赋予 tenant\_admin 内置角色的成员，由初始创建或指定升级而来                                    |
| **门户管理员**                | PortalUser 中被赋予 portal\_admin 权限的用户，拥有最高全局权限                                            |
| **login\_account（登录账号）** | 用户注册时系统生成或用户选择的全局唯一登录标识（推荐手机号，也可身份证号/自定义账号），不可重复                                        |
| **displayName（展示名）**     | 用户的友好显示名称，**不保证唯一性**，允许重名。类似微信昵称                                                        |
| **模块（Module）**           | ERPv3 的功能模块，如财务、人事、库存等，可独立授权                                                            |
| **功能点（Feature）**         | 模块内的具体功能，粒度比模块更细                                                                        |
| **Sso**                  | Single Sign-On，单点登录                                                                     |
| **IdP**                  | Identity Provider，身份提供商                                                                 |

### 2.3 模块化单体与模块系统设计（实现基座）

ERPv3 采用**自研模块化单体（Modular Monolith）**：单进程、单部署单元，内部按业务边界切分为约 15 个模块（11 个业务模块 + 4 个支撑模块），每个模块一个独立 C# 项目（csproj）。设计目标是**用库不用框架**——以成熟类库组合替代重型框架（不采用 ABP / Orchard Core），保留"模块独立开发、按需启停"的能力，同时避免微服务与重型框架的复杂度。

#### 2.3.1 技术选型（锁定）

| 层    | 选型                                                   | 职责                                                     |
| ---- | ---------------------------------------------------- | ------------------------------------------------------ |
| 运行时  | **.NET 10 / C# 14**                                  | 单进程宿主（ASP.NET Core）                                    |
| 数据访问 | **EF Core 10 + SQL Server**                          | 每模块独立 DbContext 与 Migrations                           |
| 多租户  | **Finbuckle.MultiTenant**                            | 租户解析、按租户切换连接串（独立数据库）                                   |
| 身份认证 | **OpenIddict + ASP.NET Core Identity**               | OIDC Provider / OAuth2 Client / Resource Server（见 6.7） |
| 后台任务 | **Hangfire**                                         | 调度与队列（存储于对应数据库），插件化 IJobHandler                        |
| 前端   | **Vue 3 + Element Plus + Pinia + Vite + TypeScript** | 单壳应用，菜单/路由按许可动态下发                                      |

#### 2.3.2 模块引用铁律（架构守护）

| # | 规则                                                                                                      | 守护方式                                          |
| - | ------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 1 | 业务/支撑模块**只允许引用** `Qlx.Abstractions`（模块对外服务接口 + 事件契约 DTO）与 `Qlx.BuildingBlocks`（无业务共享内核：单据编号、状态机、审计、分页等） | CI：csproj 引用图静态检查                             |
| 2 | **禁止业务模块之间直接项目引用**                                                                                      | CI：引用图检查 + NetArchTest 断言（编译期即失败）             |
| 3 | 禁止跨模块 Join 他模块数据表                                                                                       | 代码评审 + NetArchTest（模块程序集不得引用他模块 DbContext/实体） |
| 4 | 宿主（Host）项目引用全部模块并负责装配，模块不得引用宿主                                                                          | CI 引用图检查                                      |

新增公共能力前必须先检索 BuildingBlocks/Abstractions 是否已有（DRY）；确需新增且 ≥3 个模块共用的，下沉到共享内核。

#### 2.3.3 模块间通信（仅三种方式）

| 方式                      | 适用场景                                    | 一致性                                                |
| ----------------------- | --------------------------------------- | -------------------------------------------------- |
| **进程内事件总线 + Outbox**    | 模块联动（如：采购入库 → 库存更新 → 财务暂估）              | 最终一致。事件先写本模块库的 Outbox 表（随业务事务提交），再由分发器投递订阅方；无分布式事务 |
| **Abstractions 同步查询接口** | 跨模块只读查询（如：销售下单查商品 `IGoodsQueryService`） | 强一致。接口定义在 Abstractions，属主模块实现并注册 DI，调用方注入接口、不感知实现  |
| **禁止项**                 | 跨模块 Join、直接 new 他模块实现、直接读他模块表           | 见 2.3.2 守护                                         |

事件订阅关系由模块 Manifest 声明（见 2.3.5）；模块许可停用后其事件订阅自动不激活。

#### 2.3.4 模块数据隔离与迁移

| 维度         | 规则                                                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DbContext  | 每模块独立 DbContext，禁止共享                                                                                                                                                 |
| 表前缀        | 每模块固定前缀（如 `bas_` 基础信息、`pur_` 采购、`sal_` 销售、`stk_` 商品库存、`hr_` 人员、`fin_` 财务、`inv_` 票据、`ctr_` 合同、`prj_` 项目、`eqp_` 设备租赁、`apr_` 审批、`msg_` 信息、`job_` 任务、`fil_` 文件），同库内按前缀隔离 |
| Migrations | 每模块独立 Migrations 历史；新租户建库 = 创建空库 + 按依赖序执行全部已许可模块迁移                                                                                                                   |
| 版本升级       | **租户迁移执行器**：门户发布新版本后，生成租户迁移计划，由后台任务按租户批量执行（灰度分批、单租户失败可重试/回滚），执行进度与结果门户可视                                                                                             |

#### 2.3.5 模块装载：Manifest（IModule）与许可启停

每个模块实现 `IModule` Manifest，启动时由宿主扫描装配，声明式注册：

```
IModule 声明内容
├── 模块标识/版本/依赖（module_code 与 tenant_modules 对应）
├── 路由与 API 端点（模块内 Controller/Minimal API）
├── 菜单与前端动态路由（按许可下发）
├── 权限点（菜单/按钮/数据/字段，见各模块详设⑤）
├── 后台任务（IJobHandler 实现，随模块注册，见 支撑功能/03）
├── 事件发布/订阅声明
└── 所需共享内核能力
```

**许可启停的运行时过滤**（门户操作 tenant\_modules 后实时生效）：

| 过滤点     | 停用效果                      |
| ------- | ------------------------- |
| 路由      | 模块端点返回 404（许可中间件统一拦截）     |
| 菜单/动态路由 | 前端不下发该模块入口                |
| 后台任务    | 该模块全部任务暂停调度（见 支撑功能/03 R2） |
| 事件订阅    | 订阅不激活；其发布的事件不再投递          |
| Token   | 重新签发时 module\_perms 剔除该模块 |

#### 2.3.6 前端模块化

| 维度    | 规则                                                                          |
| ----- | --------------------------------------------------------------------------- |
| 单壳应用  | 一个 Vue3 + Element Plus 壳工程，登录/企业选择/工作台框架在壳内                                 |
| 动态装载  | 菜单与动态路由由后端按租户许可+用户权限下发，模块前端代码分包（按模块目录独立 chunk）                              |
| 隔离    | 模块前端目录之间禁止互相 import；跨模块复用只允许引用公共组件层                                         |
| 公共组件层 | condition-builder（条件表达式）、cron-builder（调度计划）、审批操作区、文件上传/预览等，提前下沉复用（见各支撑功能详设） |

#### 2.3.7 演进路径

模块化单体的模块边界即未来微服务拆分边界：当某模块（如票据影像处理）出现独立伸缩需求时，可将 Outbox 分发器切换为外部消息队列（RabbitMQ / Azure Service Bus），把该模块独立为进程，其余模块零改动——事件契约与查询接口已在 Abstractions 层冻结。

#### 2.3.8 标识、映射与数据保护基础设施（BuildingBlocks 提供）

以下能力统一下沉到 `Qlx.BuildingBlocks`，全平台唯一实现，禁止模块重复造轮子：

| 能力          | 技术                           | 规则                                                                                                                                                                                                                                                                                                                                           |
| ----------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **主键生成**    | 雪花 ID（自研）                    | 全平台业务主键一律 bigint 雪花 ID：时间戳 + 机器位 + 序列位，趋势递增利于索引；机器位（workerId）经 Redis 租约/配置中心分配，多实例部署无冲突、无中心生成瓶颈                                                                                                                                                                                                                                              |
| **ID 混淆**   | Hashids 算法（自研）               | **对外 API 绝不暴露真实 ID**：URL、请求体、响应体中的业务 ID 字段一律为混淆字符串（可还原加密）；混淆 salt 参数化（系统管理维护），泄漏可换 salt 全局失效旧值。**收发自动加解密**：入站在模型绑定/反序列化层自动 decode 为 long，出站在 JSON 序列化层自动 encode，业务代码与数据库永远只接触真实 long                                                                                                                                                         |
| **ID 使用边界** | —                            | 进程内（事件契约 DTO、模块间查询接口、数据库）一律真实 long；只有跨越系统边界（前端、开放 API、导出文件）才出现混淆字符串。跨系统存储引用（如外部回传）存混淆值，入库前必须 decode                                                                                                                                                                                                                                          |
| **对象映射**    | Mapperly                     | DTO ↔ 实体映射全部编译期源生成；禁止运行时反射式映射器；映射配置集中在模块内 `Mappings` 目录                                                                                                                                                                                                                                                                                      |
| **数据保护**    | ASP.NET Core Data Protection | 密钥环存 Redis（多实例共享）并以证书/DPAPI 保护；用于租户库连接凭据加密（见 3.2）、外部 IdP 客户端密钥、OIDC 令牌加密、Cookie 保护等一切敏感数据加密场景；禁止自实现 AES 封装替代                                                                                                                                                                                                                                 |
| **缓存抽象**    | 统一缓存接口（BuildingBlocks）       | **缓存层独立、接口统一**：业务代码只依赖 `ICacheService`（Get/Set/Remove/Expire/批量/原子操作，String + Hash + Set 常用结构 + `GetOrCreateAsync` Cache-Aside 封装），默认实现为 Redis 提供方；提供方经 DI 与配置（`config/common/cache.json` 的 `provider` 节）整体替换（Redis / 内存 / 其他），**业务代码与调用方零改动**。键规范：`<租户码>:<模块前缀>:<业务键>`；序列化 JSON（System.Text.Json）；禁止业务代码直接引用 StackExchange.Redis 或任何提供方 SDK |

#### 2.3.9 配置体系（禁止硬编码）

## 3. 多租户隔离策略

### 3.1 隔离方案选择（混合模式）

| 方案 | 隔离级别 | 成本 | 安全性 | 扩展性 | ERPv3 选择 |
| --- | --- | --- | --- | --- | --- |
| **共享数据库 + `TenantId` 字段** | 中（应用层 + RLS 强制） | **低** | 中高 | 高 | **✓ 小租户默认（Shared）** |
| 共享数据库 + 独立 Schema | 中 | 中 | 中高 | 中 | ✗（跨库/跨 Schema 迁移与运维复杂，收益不明显） |
| **独立数据库实例/库** | **高** | 高 | **极高** | 高 | **✓ 按需升级（Isolated）** |

**结论：混合模式（D10）**

- 新建租户默认落**租户共享库**（`qlx_tenant_shared`），一个库承载 N 个租户，业务表全部含 `TenantId` 并建索引；平台公共数据另存**共享库** `qlx_shared`（`glb_*`，租户只读）。
- 有性能/合规/备份粒度诉求的租户，由**门户管理员人工确认**后升级为**独立租户库**（`qlx_tenant_*`）。
- **只允许 Shared → Isolated 单向升级**；不提供降级。
- 门户库（`qlx_portal`）永远是独立、唯一的控制面，不承载任何业务表（详见 [多租户数据库模式补充设计.md](多租户数据库模式补充设计.md)）。
- **动态表前缀方案已否决**：EF 模型需按前缀缓存、每租户每模块各迁一次、表数量按「租户×模块」膨胀，隔离效果与 `TenantId` 相同但成本翻倍。

### 3.2 数据库路由机制

```
请求 → 接入层 → 认证中间件解析 tenant_id
                        │
                        ▼
         ITenantDatabaseResolver.Resolve(tenant_id)
                        │
                        ▼
            门户库 por_tenant_databases 路由行
            ┌────────────────────────────────────┐
            │ tenant_id → database_mode /        │
            │ db_host / db_port / db_name /      │
            │ credentials(加密) / status         │
            └───────────────┬────────────────────┘
                            │
          ┌─────────────────┴──────────────────┐
          │ mode = Shared                      │ mode = Isolated
          ▼                                    ▼
  共享库统一连接                        解密凭据 → 独立库连接
  Qlx:Tenancy:SharedDatabase             TenantConnectionInfo
          │                                    │
          └─────────────────┬──────────────────┘
                            ▼
                 执行查询（TenantId 全局过滤 + 写入守卫
                 + SQL Server RLS 会话上下文）
```

**路由表存储位置**：门户库 `por_tenant_databases`（共享与独立共用一张表，靠字段区分）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint | 主键 |
| tenant\_id | bigint | 租户 ID（外键 → por\_tenants，一对一唯一） |
| database\_mode | enum | `SHARED` / `ISOLATED` |
| pool\_code | varchar | 共享池编码，默认 `default`（预留多池） |
| db\_host | varchar | 数据库主机（共享行可冗余存共享库主机便于排障） |
| db\_port | int | 数据库端口 |
| db\_name | varchar | 数据库名称（共享行=共享库名） |
| db\_user | varchar | 数据库用户名；**共享行为空**，独立行经 Data Protection 加密（见 2.3.8） |
| db\_password | varchar | 数据库密码；**共享行为空**，独立行经 Data Protection 加密 |
| db\_status | enum | `ACTIVE` / `MIGRATING` / `ARCHIVED` |
| created\_at | datetime | 创建时间 |
| updated\_at | datetime | 更新时间 |

> 共享租户也保留一条路由行（凭据为空），使解析器、详情页、升级任务无需两套查询逻辑；解析器未命中缓存时快速失败，不放宽为默认库。

### 3.3 Schema 版本管理

| 维度 | 策略 |
| --- | --- |
| **Schema 模板** | EF Core Migrations 即模板：每模块独立 DbContext + 独立 Migrations 历史（见 2.3.4），同库内按模块表前缀隔离 |
| **共享库初始化** | 共享库只建一次、只迁一次；迁移包在**数据库级应用锁**（SQL Server `sp_getapplock`，其他库等价机制）内执行，多实例并发启动时后者等待 |
| **共享库历史表** | 每个模块（每个迁移流）独立 `__EFMigrationsHistory_{module}`（如 `__EFMigrationsHistory_bas`），避免模块间版本互相污染 |
| **独立库初始化** | 创建租户时建空库，按依赖拓扑执行全部已许可模块的 Migrations |
| **版本迁移** | 租户迁移执行器：共享库去重执行一次；独立库按租户批量 `Database.MigrateAsync()`，进度与结果门户可视 |
| **灰度发布** | 独立库支持按租户分批灰度、失败单租户重试；共享库为全共享租户同版本，需整体发布 |
| **安全护栏** | 共享库禁止 `DROP DATABASE` / `EnsureDeleted` / 重建库；迁移失败保留已成功模块，从断点继续 |
| **一致性校验** | 定期扫描各库 `__EFMigrationsHistory*` 版本，发现与模型不一致自动告警 |

### 3.4 租户数据库生命周期

```
租户开通（门户管理员选择模式）
   │
   ├─ Shared ──────────────────────────────────────────────┐
   │   写 por_tenant_databases 路由行（凭据空）             │
   │   共享库已存在且已迁移 → 直接 Active                   │
   └────────────────────────────────────────────────────────┘
   │
   └─ Isolated ────────────────────────────────────────────┐
       创建空库 → 按模块初始化 Schema → 导入基础数据        │
       → 激活可用                                          │
       └───────────────────────────────────────────────────┘
                            │
                            ▼
                   正常运行（Schema 随门户升级）
                            │
             ┌──────────────┼──────────────────┐
             ▼              ▼                  ▼
      Shared→Isolated   租户到期/注销      租户停用
      人工升级任务        │                  │
      (复制→校验→切换)    ▼                  ▼
                    数据归档备份        数据保留，不可登录
                         │
                         ▼
                  宽限期（如 30 天）
                    │            │
                    ▼            ▼
                续费恢复      宽限期结束
                               ├─ 共享租户：仅删除该租户业务行（按 TenantId），不删库
                               └─ 独立租户：库标记 ARCHIVED → 备份后物理删除
```

> 共享库内单个租户的删除**永远不删物理库**；独立库的物理删除必须备份 + 双重确认 + 审计留痕。

### 3.5 连接池管理

混合模式下连接池分两类：**共享库统一池**（所有共享租户共用）与**独立库按租户池**。共享租户数量增长不增加池数量，只增加共享池的并发压力，因此必须设置全局预算与租户级闸门。

#### 3.5.1 池化架构

```
┌─────────────────────────────────────────────────────────────────┐
│                     Global Connection Budget                     │
│                (SQL Server 全局连接预算，如 500)                 │
└───────────────────────────┬─────────────────────────────────────┘
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
┌───────────────────────────┐        ┌───────────────────────────┐
│ 租户共享库池 qlx_tenant_shared │    │  独立库池 qlx_tenant_*     │
│  min: 5                   │        │  每租户池 min: 2 / max: 20  │
│  max: 100（按实例容量）    │        │  idle_timeout: 5min        │
│  每租户闸门: 20 连接       │        │  （租户停用即释放）         │
└───────────────────────────┘        └───────────────────────────┘
```

#### 3.5.2 池配置策略

| 配置项 | 说明 | 默认值 |
| --- | --- | --- |
| `shared_pool.max_active` | 共享库池最大活跃连接数 | 100（按共享库实例容量上调） |
| `shared_pool.per_tenant_gate` | 单共享租户并发连接闸门 | 20（`ITenantConnectionPool` 按 tenantId 信号量） |
| `isolated_pool.min_idle` | 每个独立库池保持的最小空闲连接数 | 2 |
| `isolated_pool.max_active` | 每个独立库池最大活跃连接数 | 20（企业版可上调至 50） |
| `idle_timeout_ms` | 空闲连接回收时间 | 300,000（5 分钟） |
| `pool_warmup` | 活跃池预热 | 共享池启动预热；独立池首次活跃请求预热 |
| `pool_eviction` | 空闲驱逐定时器 | 每分钟扫描，超过 idle_timeout 的连接释放 |
| `total_budget_cap` | 全局连接预算上限 | 数据库服务器 max_connections 的 70% |
| `overflow_behavior` | 预算耗尽时的行为 | 排队等待（带超时）+ 共享租户按配额降级 |

#### 3.5.3 动态池生命周期

| 事件 | 动作 |
| --- | --- |
| 共享租户创建 | **不创建新池**；仅占路由行与租户级连接闸门 |
| 独立租户创建 | 初始化该租户连接池（min_idle），不预热 |
| 租户首次活跃请求 | 共享池已在启动期预热；独立池触发预热 |
| Shared → Isolated 升级 | 目标库建池 → 切换路由 → `resolver.Invalidate` → 旧共享连接按租户闸门回收 |
| 租户停用 | 共享租户释放其租户级闸门；独立租户释放整个池 |
| 连接泄漏检测 | 请求结束后连接未归还超过 30 秒告警；超过 60 秒强制回收 |
| 总预算告警 | 达到预算 80% 预警；95% 拒绝低优先级请求 |

### 3.6 跨租户数据聚合策略

门户管理员需要在全局维度查看"所有租户的汇总数据"，但数据分散在共享库与各独立租户库中。ERPv3 采用**实时扇出 + 异步 ETL 双轨策略**。

#### 3.6.1 策略总览

| 场景          | 数据时效 | 数据量 | 策略                                                   |
| ----------- | ---- | --- | ---------------------------------------------------- |
| 租户列表、健康状态   | 实时   | 少   | 直接查询 Portal Database 的 tenants 表                     |
| 平台登录审计      | 准实时  | 少   | 仅门户侧登录事件写入门户库 `plog_operation`；**租户登录日志留在租户库 `log_login`，平台不汇总**（D13） |
| 模块使用率概览     | T+1  | 中   | **ETL 管道**：每日凌晨从活跃租户抽取核心指标写入门户分析库                    |
| 财务汇总 / 收入分析 | T+1  | 大   | **ETL + 分析仓库**：按租户异步抽取聚合数据，写入独立的 Portal Analytics DB |
| 租户业务数据导出    | 实时   | 单租户 | 直接路由到对应租户数据库查询                                       |
| 异常检测 / 实时告警 | 实时   | 流   | **变更数据捕获**（SQL Server CDC）：捕获关键表变更事件，实时写入门户告警流       |

#### 3.6.2 ETL 管道设计

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  Tenant DB #1 │    │  Tenant DB #2 │    │  Tenant DB #N │
│  (CDC /       │    │  (CDC /       │    │  (CDC /       │
│   Batch Pull) │    │   Batch Pull) │    │   Batch Pull) │
└──────┬───────┘    └──────┬───────┘    └──────┬───────┘
       │                   │                   │
       ▼                   ▼                   ▼
┌──────────────────────────────────────────────────────┐
│            事件总线（Outbox 持久化 + 分发器）         │
│           (事件流: 指标快照、CDC；审计日志不汇总)       │
└──────────────────────────┬───────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────┐
│            Portal Analytics DB (SQL Server            │
│              分析库 / 可选 ClickHouse)                 │
│                                                       │
│  • portal_login_summary (门户侧登录汇总, 不含租户)      │
│  • portal_module_usage (模块使用率)                    │
│  • portal_finance_aggregate (各租户财务聚合)            │
└──────────────────────────┬───────────────────────────┘
                           │
                           ▼
               门户仪表盘 / 运营报表查询
```

> **审计不进分析库**：平台审计只覆盖「平台对租户的管理动作」，存门户库 `plog_audit`；租户内部日志存租户库 `log_*`，平台不抽、不汇总、不直查（D13）。

#### 3.6.3 实时扇出（紧急场景）

对于极少量需要实时跨租户查询的场景（如"查找某手机号关联的所有租户成员"），采用**受控扇出模式**：

```
门户发起跨租户查询
       │
       ▼
查询 Portal Database 获取活跃租户列表
       │
       ▼
并行查询（限制并发度, 如最多 10 个租户同时查询）
       │
       ▼
合并结果集, 返回给门户
```

| 保护措施 | 说明                           |
| ---- | ---------------------------- |
| 并发限流 | 同时查询的租户数 ≤ 10                |
| 超时控制 | 单租户查询超时 500ms，整体超时 3s        |
| 降级策略 | 超时租户跳过，返回部分结果 + 提示"部分数据可能延迟" |
| 结果缓存 | 相同查询条件 60 秒内缓存结果             |

### 3.7 跨数据库引用一致性策略

#### 3.7.1 问题背景

ERPv3 采用"成员基础信息在 Portal DB、角色/权限/组织在各 Tenant DB"的分层架构，必然产生**双向跨数据库引用**，且数据库隔离环境下无法使用外键约束。

```
Portal Database                          Tenant Database
┌────────────────────────┐              ┌─────────────────────────┐
│ tenant_members          │              │ organizations            │
│ ├── id          ──┐     │              │ ├── manager_member_id ──┼──┐
│ ├── org_id (可空) │─────┼──────────────┼──→ organizations.id     │  │
│ └── ...          │     │              │ └── ...                  │  │
│                  │     │              │                          │  │
│                  │     │              │ member_roles             │  │
│                  │     │              │ ├── tenant_member_id ───┼──┘
│                  │     │              │ │   (→ tenant_members.id)│
│                  │     │              │ ├── role_id              │
│                  │     │              │ └── ...                  │
└────────────────────────┘              └─────────────────────────┘
```

#### 3.7.2 同步机制：事件驱动 + 镜像缓存表

ERPv3 采用 **"事件驱动同步 + Tenant DB 内镜像缓存表"** 的组合策略，兼顾最终一致性和运行时查询性能：

```
┌─────────────────────────────────────────────────────────────────┐
│  Portal DB 变更事件源                                            │
│                                                                 │
│  • 成员加入/退出租户 → 写 tenant_members 表                      │
│  • 成员停用/启用 → 更新 tenant_members.member_status              │
│  • 成员部门变更 → 更新 tenant_members.org_id                      │
│  • 认证通过/密码修改 → 更新 portal_users                          │
│                                                                 │
│  每次变更 → 写 Outbox 事件 (tenant_member_changed)     │
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  事件流: member-events（Outbox 表持久化 + 进程内分发器投递）      │
│                                                                 │
│  {                                                              │
│    "event_type": "MEMBER_STATUS_CHANGED",                       │
│    "tenant_id": 123,                                            │
│    "tenant_member_id": 456,                                     │
│    "portal_user_id": 789,                                       │
│    "member_status": "DISABLED",                                  │
│    "display_name_in_tenant": "张三",                            │
│    "sync_timestamp": "2026-10-20T10:30:00Z"                    │
│  }                                                              │
└───────────────────────────┬─────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  Tenant DB 消费端 — 镜像缓存表 (member_profiles)                 │
│                                                                 │
│  ⚠️ 这是一个**只读镜像表**，由事件驱动自动同步，不应直接写入       │
│                                                                 │
│  member_profiles (每个 Tenant DB 自动创建, Schema 模板内置)       │
│  ├── tenant_member_id (bigint, PK) ← 对应 portal DB 主键         │
│  ├── portal_user_id (bigint)                                    │
│  ├── display_name_in_tenant (varchar(64), **非唯一**)           │
│  ├── login_account (varchar(64))                                │
│  ├── org_id (bigint, 可空)                                      │
│  ├── member_status (enum)                                       │
│  ├── sync_version (bigint, 同步版本号)                          │
│  ├── sync_at (datetime, 最后同步时间)                            │
│  └── INDEX(org_id), INDEX(member_status)                        │
│                                                                 │
│  运行时查询示例:                                                  │
│  "查询某个成员的姓名" → SELECT display_name_in_tenant             │
│                       FROM member_profiles                       │
│                       WHERE tenant_member_id = ?                 │
│                       ✅ 单库查询, 无跨库依赖                     │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.7.3 事件类型与触发时机

| Event Type                | 触发时机        | 携带数据                                                                         | Tenant DB 侧处理                                        |
| ------------------------- | ----------- | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| `MEMBER_ADDED`            | 成员加入租户      | tenant\_member\_id, portal\_user\_id, display\_name, org\_id, member\_status | INSERT 到 member\_profiles                            |
| `MEMBER_REMOVED`          | 成员退出/被移除    | tenant\_member\_id                                                           | DELETE FROM member\_profiles; 清理 member\_roles 中关联记录 |
| `MEMBER_STATUS_CHANGED`   | 成员在租户内停用/启用 | tenant\_member\_id, member\_status                                           | UPDATE member\_profiles.member\_status               |
| `MEMBER_ORG_CHANGED`      | 成员部门变更      | tenant\_member\_id, new\_org\_id                                             | UPDATE member\_profiles.org\_id                      |
| `MEMBER_RENAME_IN_TENANT` | 租户内修改成员展示名  | tenant\_member\_id, new\_display\_name                                       | UPDATE member\_profiles.display\_name\_in\_tenant    |
| `ORG_MANAGER_CHANGED`     | 组织负责人变更     | org\_id, new\_manager\_member\_id                                            | UPDATE organizations.manager\_member\_id             |
| `TENANT_CREATED`          | 新租户创建       | tenant\_id, initial\_member\_id                                              | 触发 Tenant DB 初始化 + member\_profiles 预置               |

#### 3.7.4 一致性保障

| 场景          | 处理方式                                                                            |
| ----------- | ------------------------------------------------------------------------------- |
| **正常运行**    | 事件驱动异步同步，延迟 < 5s（Outbox 轮询分发 + 幂等消费）                                            |
| **同步中断恢复**  | 消费者重启后从 `sync_version` 断点续传；Portal DB 维护事件日志表支持重放                               |
| **删除成员的级联** | 事件 `MEMBER_REMOVED` → Tenant DB 消费者负责清理 member\_roles 等关联记录                     |
| **孤儿记录检测**  | 定时任务（每日凌晨）扫描：member\_roles 中的 tenant\_member\_id 在 member\_profiles 中是否存在，存在则清理 |
| **写入保护**    | Tenant DB 的 member\_profiles 表设置 REVOKE INSERT/UPDATE 权限，仅事件消费者角色有写入权限          |
| **新租户初始化**  | 创建 Tenant DB 时基于 Schema 模板自动创建 member\_profiles 表 + 预置初始管理员镜像记录                 |

#### 3.7.5 运行时查询的两种模式

| 查询场景         | 示例                        | 推荐方案                                                        |
| ------------ | ------------------------- | ----------------------------------------------------------- |
| **业务操作高频查询** | "凭证创建者姓名"、"部门成员列表"        | ✅ **走镜像表**：Tenant DB 的 member\_profiles，单库查询                |
| **认证/鉴权查询**  | "该 Token 对应用户是否在租户 B 有效？" | ✅ **直接查 Portal DB**：通过 Identity Service 统一查询（可走 Redis 缓存加速） |

```
业务请求: GET /api/v1/tenants/123/finance/vouchers
       │
       ▼
业务服务路由到 Tenant DB #123
       │
       ▼
查询凭证表 → 返回 voucher.created_by_member_id = 456
       │
       ▼
查询 Tenant DB 内的 member_profiles:
SELECT display_name_in_tenant, login_account
FROM member_profiles WHERE tenant_member_id = 456
       │
       ▼
✅ 单库完成, 无需跨 Portal DB 查询
```

### 3.8 数据库模式判定、切换与三层隔离

#### 3.8.1 四库边界（固定不变量）

| 库 | 角色 | 存什么 | 约束 |
| --- | --- | --- | --- |
| ① 共享库 `qlx_shared`（`glb_*`） | 平台公共数据面 | 全局公告/任务/消息、消息模板、任务定义、公共字典 + Hangfire 队列表 | 平台写、租户**只读**；租户侧账号仅 `SELECT` |
| ② 门户库 `qlx_portal`（`por_*` + `plog_*`） | 唯一控制面 | 租户/用户/成员/许可/参数/路由行/加密凭据/OpenIddict + 平台日志/审计/回执 | 不承载业务表；账号不得用于租户连接 |
| ③ 租户共享库 `qlx_tenant_shared` | 数据面 | 业务表 + `*_global_state`，含 `TenantId`，N 个租户共用 | 禁止 `DROP DATABASE`；迁移只执行一次 |
| ④ 独立租户库 `qlx_tenant_*` | 数据面 | 同③表结构，单租户独占 | 仍需保留 `TenantId` 与全局过滤 |

- **始终只有以上四类库，禁止新增第五个库**（不设独立日志库、任务库、总日志库）。
- 四库**禁止跨库 JOIN、跨库事务；禁止共用数据库账号**；全局项与本地项在应用层合并。
- 租户共享库与独立库都只是门户路由行指向的数据面；解析、预配、迁移、启停、升级、隔离巡检全部由门户库驱动。
- 日志归属：平台侧 `plog_*` 只在门户库，租户侧 `log_*` 只在租户库，**互不复制**。
- 全局数据归属：平台发布只写共享库 `glb_*` **一份**；租户只写本租户库 `*_global_state`，**不复制正文**；读取顺序为「先共享库全局项，再本租户库自建项」。

#### 3.8.2 模式判定（本期：门户人工）

| 优先级 | 来源 | 本期是否生效 |
| --- | --- | --- |
| 1 | 门户管理员人工选择（新建租户 / 详情页升级） | ✅ 唯一来源 |
| 2 | 系统默认 `Shared` | ✅ 未指定时生效 |
| 3 | 会员/套餐推荐（`ITenantDatabaseModePolicy`） | ⏳ 预留，只产生建议，不改变实际模式 |

- 会员（付费）体系只用于**推荐**：门户详情页展示「建议升级为独立库」，**必须由管理员人工确认并触发升级**，系统永不自动切换。
- 本期不实现会员映射逻辑，只保留扩展点与空配置。

#### 3.8.3 Shared → Isolated 升级（单向）

```
Preparing → Copying → Verifying → Cutover → Done
   │           │          │          │
   │           │          │          └─ 停写 → 补增量 → 切路由 → Invalidate → 恢复
   │           │          └─ 行数/抽样 hash/唯一索引一致性校验
   │           └─ 按模块、按主键区间分批复制 + 断点续传
   └─ 校验租户/目标库、建库、全模块迁移
```

- 任一步失败：路由仍指向共享库，租户无感；目标库保留供重试。
- 切换后 `tenantId` 不变，用户无需重新登录；解析器缓存必须失效。
- **不提供 Isolated → Shared 降级**；需要时导出 + 归档 + 重建租户。

#### 3.8.4 三层隔离

| 层 | 措施 | 共享库 | 独立库 |
| --- | --- | --- | --- |
| L1 应用层 | EF 全局查询过滤（`TenantId`） | 必须 | 必须 |
| L1 应用层 | 写入守卫：新增自动填租户、禁改租户、拒绝跨租户 Update/Delete | 必须 | 必须 |
| L1 应用层 | 缓存键统一 `tenant:{id}:` 前缀 | 必须 | 必须 |
| L2 数据库层 | SQL Server `SESSION_CONTEXT` + Security Policy（RLS） | 必须 | 建议开启 |
| L2 数据库层 | PostgreSQL `set_config`+RLS / Oracle VPD；MySQL 无原生 RLS → 降级 L1+L3 | 按主库能力 | 按主库能力 |
| L3 检测层 | 隔离巡检任务 + 架构测试 + 越权回归用例 | 必须 | 必须 |

#### 3.8.5 日志、全局消息与任务归属

| 项 | 位置 | 内容 | 租户可见 | 可管理 |
| --- | --- | --- | --- | --- |
| 平台日志 | 门户库 `plog_operation` | 门户管理员操作、身份认证、许可/租户生命周期 | 否 | 否（平台运维） |
| 平台审计 | 门户库 `plog_audit` | **只审计平台对租户的管理动作**（开通/升级/停用/许可/敏感查看） | 否 | 否 |
| 下发回执 | 门户库 `plog_push_receipt` | 租户对全局项的 ack 回传（不存正文） | 否 | 否 |
| 全局消息/模板/任务定义/公共字典 | 共享库 `glb_*` | 平台发布，**只存一份** | 是（只读） | 否 |
| Hangfire 队列 | 共享库 `hangfire_*` | 队列/重试/看板，可重建 | 否 | 否（平台运维） |
| 租户日志 | 租户库 `log_*`（租户共享库/独立库） | 租户内操作与登录日志，**无平台副本** | 是 | 是（租户自管） |
| 租户全局状态 | 租户库 `*_global_state` | `GlobalId` + 已读/完成/回执，**只状态、无正文** | 是 | 是 |

- 日志写入**不得阻塞主业务**：租户日志异步批量写；平台日志同步落门户库。
- **不复制、不出站箱、不下沉**：平台日志不入租户库，租户日志不上报门户库；无死信重放。
- 平台**不直查**租户 `log_*`，租户**不直查**门户库 `plog_*`；平台审计仅平台侧可见。
- 全局项 `ForceAccept=1`；租户端无删除/拒收入口，只能标记已读/完成；平台撤回（`Revoked`）是唯一例外。
- 租户读取顺序：①共享库 `glb_*`（`Published` 且 `Scope=GLOBAL` 或 `TargetTenantIds` 含本租户）→ ②本租户库自建项 + `*_global_state` → ③应用层合并（去重键 `GlobalId`）。

> 完整流程、字段语义、账号权限矩阵、改造清单与验收标准见 [多租户数据库模式补充设计.md](多租户数据库模式补充设计.md)。

> 1. **Phase 3 请求形态变更**：`grant_type=urn:qlx:grant:tenant_context` 改为凭 **Bearer 身份级

>    参数，且 access token 短时效（2h）内换租户足够安全，身份 refresh token 仍由 Phase 1 签发。
> 2. **Phase 3 仅签发租户级 access token，无 refresh token**：租户过期后走标准 refresh 流程重登
>    身份再选租户，规格原"Phase 3 同时签发身份级 Refresh Token"由 Phase 1 承担（1 的天然结果）。
> 3. **qlx_tenants 响应参数**：Phase 1 Token 响应中新增 `qlx_tenants` 字符串参数（JSON 数组，
>    前端 JSON.parse 还原），内容为可进入租户摘要 `[{tenantId(混淆), tenantCode, displayName,
>    role, lastLoginAt}]`；PendingInvite 与停用成员/租户不出现。
> 4. **OpenIddict 表**：por_oidc_applications / por_oidc_authorizations / por_oidc_tokens /
>    por_oidc_scopes 四张表并入 PortalDbContext（por_ 前缀），一个迁移体系管理。
> 5. **Token 签名/加密证书（阶段 1C 落地骨架）**：开发期自动生成开发证书；生产环境必须配置
>    `Qlx:Portal:Auth:Certificate`（`Source=File` 走 PFX 路径+密码 / `Source=Store` 走 Windows 证书存储指纹），
>    经 X509CertificateLoader 加载，未配置或加载失败**启动即失败**，杜绝以开发证书上线；
>    证书密码生产经部署密钥注入，禁止明文入库版本管理。

### 6.2 Token 模型

Token 采用 **JWT (JSON Web Token)**。ERPv3 有**两种 Token**：

#### 6.2.1 租户上下文 Access Token（常规 API 使用）

```json
{
  "sub": "portal_user_id",
  "member_id": 456,
  "tenant_id": 123,
  "tenant_code": "SHENZHEN_A",
  "member_role": "TENANT_ADMIN",
  "roles_in_tenant": ["finance_manager", "hr_manager"],
  "modules": ["finance", "hr", "inventory"],
  "permissions": ["finance.voucher.create", "finance.voucher.view", "hr.employee.manage"],
  "token_version": 3,
  "iss": "erp-identity-service",
  "aud": "erp-api-gateway",
  "exp": 1735689600,
  "iat": 1735686000,
  "jti": "uuid-for-blacklist-check"
}
```

| 声明                | 说明                                                                    |
| ----------------- | --------------------------------------------------------------------- |
| `sub`             | PortalUser.id（全局身份）                                                   |
| `member_id`       | TenantMember.id（当前租户内的成员记录 ID）                                        |
| `tenant_id`       | 当前操作上下文的租户 ID                                                         |
| `member_role`     | 在本租户内的主要成员角色（TENANT\_ADMIN / ORDINARY\_MEMBER）                        |
| `roles_in_tenant` | 在本租户内分配的全部角色编码列表                                                      |
| `modules`         | 门户为该租户授权的模块列表                                                         |
| `permissions`     | 该成员在当前租户上下文中拥有的完整权限编码列表                                               |
| `token_version`   | PortalUser.token\_version + TenantMember.token\_version 的合并版本号，用于失效校验 |
| `jti`             | JWT ID，用于 Redis 黑名单                                                   |

> ⚙️ **实现备注（阶段 1B 已落地）**：`sub` / `tenant_id` / `member_id` 实际为 **Hashids 混淆字符串**
> （对外边界自动加解密，进程内仍用真实 long）；`token_version` 实际拆为 `tv_u`（PortalUser）与
> `tv_m`（TenantMember）两个声明，刷新/换租户时实时校验，任一不匹配即拒绝；Access Token 为
> **JWE 加密格式**（OpenIddict 默认），外部无法直接解码 claims，功能性验证经 /api/portal/me。

#### 6.2.2 身份级 Refresh Token（跨租户通用）

```json
{
  "sub": "portal_user_id",
  "scope": "identity",
  "iss": "erp-identity-service",
  "aud": "erp-api-gateway",
  "exp": 1736294400,
  "iat": 1735686000
}
```

> Refresh Token 不绑定具体租户，这样用户在租户 A 过期后可以选择切换到租户 B 而无需重新登录门户。

### 6.6 Token 失效机制

当门户或租户管理员执行"停用"、"权限变更"等操作时，需要**立即**使已签发的 Token 失效，而不必等待其自然过期（2 小时）。

#### 6.6.1 双重保障设计

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  Layer 1: Token Version （持久、精准）                          │
│  ──────────────────────────────                                  │
│  在 portal_users / tenant_members 表中维护一个 token_version 字段   │
│  每次 Token 签发时，将当前 version 写入 Token payload              │
│  每次刷新 Token 时，比对 Token 中的 version 与数据库中的 version    │
│  不一致则拒绝刷新 → 强制重新登录                                    │
│                                                                 │
│  ✅ 优点：持久化、跨实例生效、不依赖 Redis                          │
│  ✅ 缺点：仅在刷新 Token 时校验，已签发的 access_token 在过期前    │
│          仍可使用（最多 2 小时窗口）                               │
│                                                                 │
│  ──────────────────────────────────────────────────────────────  │
│                                                                 │
│  Layer 2: Redis Blacklist （即时、短窗口）                        │
│  ──────────────────────────────                                  │
│  认证中间件维护 Redis Token 黑名单：                                    │
│    Key:   token:blacklist:{jti}                                  │
│    Value: reason (DISABLED / PASSWORD_CHANGE / LOGOUT)           │
│    TTL:   与 access_token 剩余有效期一致（不超过 2 小时）          │
│                                                                 │
│  每次 API 请求，网关先检查 JWT 的 jti 是否在黑名单中               │
│                                                                 │
│  ✅ 优点：即时生效、完全拦截                                        │
│  ✅ 缺点：依赖 Redis、内存占用与活跃 Token 数成正比                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 6.6.2 校验流程

```
请求到达网关
       │
       ▼
① 解析 JWT → 提取 jti (JWT ID), exp, token_version, sub
       │
       ▼
② Redis 黑名单查询：EXISTS token:blacklist:{jti}
       │
  ┌────┴─────┐
  │ 命中      │ 未命中
  ▼           ▼
立即拒绝    ③ 检查 exp 是否已过期
│           │
│      ┌────┴─────┐
│      │ 已过期    │ 未过期
│      ▼           ▼
│   拒绝，        ④ 放行到后端服务
│   提示过期           │
│                      ▼
│              刷新 Token 时额外校验：
│              Redis GET user:token_version:{sub}
│              比对 Token 中的 token_version
│              ┌────┴─────┐
│              │ 不一致    │ 一致
│              ▼           ▼
│           拒绝刷新，    签发新 Token
│           强制登录
```

#### 6.6.3 触发失效的操作场景

| 操作       | 失效范围                   | 实现方式                                                        |
| -------- | ---------------------- | ----------------------------------------------------------- |
| 门户停用租户   | 该租户下所有用户的所有 Token      | Redis 批量拉黑该租户下活跃 Token + 版本号递增                              |
| 门户全局停用用户 | 该用户的所有 Token（跨租户）      | Redis 拉黑 + portal\_users.token\_version++                   |
| 租户内停用成员  | 该成员在本租户上下文的 Token      | Redis 拉黑该租户下该成员的 Token + tenant\_members.token\_version++   |
| 用户主动登出   | 当前设备 Token             | Redis 拉黑当前 jti                                              |
| 密码修改     | 该自然人所有 Token（强制所有设备下线） | Redis 批量拉黑 + portal\_users.token\_version++（影响该自然人的所有租户上下文） |
| 模块授权变更   | 租户下所有用户（需权限重新签发）       | Redis 批量拉黑 + 重新登录时自动签发含新模块的 Token                           |
| 角色权限变更   | 该角色下所有用户（即时生效）         | Redis 批量拉黑该角色下活跃用户的 Token                                   |
| IP 白名单变更 | 超出白名单的 Token           | Redis 拉黑 + 认证中间件增加 IP 校验                                    |

#### 6.6.4 Redis Key 设计

| Key 模式                                | 用途                      | TTL               |
| ------------------------------------- | ----------------------- | ----------------- |
| `token:blacklist:{jti}`               | 单个 Token 拉黑             | Token 剩余有效期（≤ 2h） |
| `user:active_tokens:{portal_user_id}` | 用户活跃 Token 集合（用于批量拉黑）   | 跟随最长 Token 有效期    |
| `user:token_version:{portal_user_id}` | 用户 Token 版本缓存（减少 DB 查询） | 版本变更时主动失效         |
| `tenant:active_users:{tenant_id}`     | 租户活跃用户集合                | 跟随活跃 Token 有效期    |

> ⚙️ **实现备注（阶段 1C 已落地，2026-10-21）**：
> ① 主动登出端点 `/api/portal/logout`（身份级/租户级 Token 通用）已实现——将当前 access token 的 jti 写入
> `token:blacklist:{jti}`（TTL=exp 剩余有效期，缺失时退化为配置生命周期），由 TokenBlacklistMiddleware 即时拦截；
> 客户端应同时调用 `/connect/revoke` 吊销 refresh token（Layer 1 双保障）。
> ② `user:active_tokens` / `tenant:active_users` 批量拉黑集合尚未建（门户停用租户/批量踢线属门户管理端范围，随管理功能落地），
> 当前单 Token 场景（登出/吊销）已闭环。
> ③ 租户级 Token 静默续期端点已实现（2026-10-21）——grant `urn:qlx:grant:tenant_silent`，
> 从 Bearer 头取旧租户 access token → 手动 JWT 校验（签名+iss+aud+有效期，含 `TenantTokenRenewalGraceMinutes` 宽限期）→ 校验用户/成员/租户状态与双 Token 版本 → 重签新租户级 access token。
> **关键坑**：OpenIddict 内部对 Issuer 做 `new Uri(issuer).AbsoluteUri` 归一化（自动补尾斜杠），手动校验 `ValidIssuer` 必须使用归一化值，否则 `IDX10205 Issuer validation failed`。

### 6.7 SSO 与 OAuth2 集成方案

ERPv3 在 SSO/OAuth2 体系中同时扮演三种角色，需分别设计集成方案：

```
┌──────────────────────────────────────────────────────────────────────┐
│ 角色 1: ERPv3 作为 OAuth2/OIDC Provider（对外提供身份）                │
│   场景：客户已有自研系统/第三方应用，希望"用 ERPv3 账号登录"            │
│   即：ERPv3 是 IdP，外部应用是 Client                                  │
│                                                                      │
│ 角色 2: ERPv3 作为 OAuth2 Client / SAML SP（接入外部身份）             │
│   场景：企业已有统一身份源（企业微信/钉钉/AD/Okta/Keycloak）           │
│   即：外部 IdP 是身份源，ERPv3 是业务应用（SP/RP）                     │
│                                                                      │
│ 角色 3: ERPv3 作为 Resource Server（资源服务器）                       │
│   场景：开放 API 供第三方系统调用（如 BI 报表工具拉取数据）              │
│   即：校验 Client Credentials / Access Token，按 scope 授权           │
└──────────────────────────────────────────────────────────────────────┘
```

#### 6.7.1 角色 1：ERPv3 作为 OIDC Provider（对外 SSO）

##### 6.7.1.1 支持的授权模式

| 授权模式                      | 适用场景                          | 是否支持     | 说明                       |
| ------------------------- | ----------------------------- | -------- | ------------------------ |
| Authorization Code + PKCE | Web SPA / 移动 App / 第三方 Web 应用 | ✅ **推荐** | 强制 PKCE，禁止 implicit      |
| Authorization Code（机密客户端） | 有安全后端的传统 Web 应用               | ✅        | client\_secret 存储于服务端    |
| Client Credentials        | 服务端到服务端（M2M）开放 API            | ✅        | 不签发 Refresh Token，无用户上下文 |
| Refresh Token             | 上述模式的令牌续期                     | ✅        | 配合轮换策略（Rotation）         |
| Implicit                  | -                             | ❌ 禁用     | 已被 OAuth2.1 废弃，安全风险高     |
| Resource Owner Password   | -                             | ❌ 禁用（默认） | 仅私有化部署白名单可开启             |

##### 6.7.1.2 标准 OIDC 端点

| 端点   | URL                                             | 说明                           |
| ---- | ----------------------------------------------- | ---------------------------- |
| 服务发现 | `GET {issuer}/.well-known/openid-configuration` | 公开全部端点与支持能力                  |
| JWKS | `GET {issuer}/.well-known/jwks.json`            | 公钥集，供 Client 校验 ID Token 签名  |
| 授权   | `GET {issuer}/oauth2/authorize`                 | 授权码模式入口                      |
| 令牌   | `POST {issuer}/oauth2/token`                    | 换发/刷新 Token                  |
| 用户信息 | `GET {issuer}/oauth2/userinfo`                  | 返回 OIDC 标准 Claims            |
| 令牌撤销 | `POST {issuer}/oauth2/revoke`                   | RFC 7009                     |
| 令牌内省 | `POST {issuer}/oauth2/introspect`               | RFC 7662，供资源服务器校验            |
| 登出   | `GET {issuer}/oauth2/logout`                    | RP-Initiated Logout（OIDC 扩展） |

```
第三方应用 (Client)                ERPv3 Identity Service (Provider)

##### 6.7.1.5 Scope 设计

| Scope            | 返回内容                                | 授权方式          |
| ---------------- | ----------------------------------- | ------------- |
| `openid`         | sub（必需，OIDC 基础）                     | 默认            |
| `profile`        | display\_name、avatar、login\_account | 用户授权页确认       |
| `profile:full`   | 手机号/邮箱明文                            | 用户显式授权 + 高亮提示 |
| `email`          | email                               | 用户授权页确认       |
| `tenant`         | 关联租户列表 + 当前租户上下文                    | 用户授权页确认       |
| `erp:api`        | 开放 API 调用权限（M2M）                    | 门户管理员审批       |
| `offline_access` | 签发 Refresh Token                    | 用户授权页确认       |

##### 6.7.1.6 客户端注册管理

第三方应用须先在门户注册为 OAuth2 Client，由门户管理员审批：

```
oauth_clients (OAuth2 客户端注册表, Portal DB)
├── id (bigint, PK)
├── client_id (varchar(64), UNIQUE, 系统生成)
├── client_secret_hash (varchar(256), 机密客户端才有, BCrypt)
├── client_name (varchar(128))
├── client_type (enum: CONFIDENTIAL / PUBLIC)  — PUBLIC 强制 PKCE
├── redirect_uris (JSON 数组, 精确匹配, 禁止通配符)
├── allowed_scopes (JSON 数组)
├── allowed_grant_types (JSON 数组)
├── owner_tenant_id (bigint, 可空, 归属租户; NULL=平台级应用)
├── owner_portal_user_id (bigint, 应用负责人)

├── access_token_ttl, refresh_token_ttl (可定制)
├── created_by, approved_by, approved_at
├── created_at, updated_at

oauth_authorization_codes (授权码表, 短生命周期)
├── code (varchar(128), PK)

#### 6.7.2 角色 2：接入外部 IdP（企业 SSO 登录）

ERPv3 作为 SP/RP，对接企业已有身份源。统一抽象为 `external_identity_providers` 配置（见 4.3 节），按协议类型分别处理：

##### 6.7.2.1 OIDC / OAuth2 通用对接（Okta、Keycloak、Authing、Azure AD）

```
配置项 (external_identity_providers.config JSON):
{
  "issuer": "https://login.partner.com",
  "client_id": "erpv3-client",
  "client_secret": "***加密存储***",
  "authorization_endpoint": ".../authorize",
  "token_endpoint": ".../token",
  "userinfo_endpoint": ".../userinfo",
  "jwks_uri": ".../jwks.json",
  "scopes": "openid profile email",
  "user_id_claim": "sub",              // 用哪个 Claim 做 external_user_id
  "phone_claim": "phone_number",       // 用于自动匹配 PortalUser
  "display_name_claim": "name",
  "auto_provision": true               // 未匹配时是否自动创建 PortalUser
}
```

对接流程：授权码模式回调 → 校验 ID Token 签名（JWKS）→ 提取 `user_id_claim` → 查 `external_identity_mappings` → 命中则进入 6.1 Phase 2（租户选择）；未命中则按 `phone_claim` 匹配现有 PortalUser 或按 `auto_provision` 策略创建。

##### 6.7.2.2 企业微信 / 钉钉（扫码 + 免登）

| 项        | 企业微信                                       | 钉钉                                      |
| -------- | ------------------------------------------ | --------------------------------------- |
| 协议       | 自有 OAuth2                                  | 自有 OAuth2                               |
| 门户配置     | corpid + agentid + secret（加密）              | AppKey + AppSecret（加密）                  |
| 登录方式     | 构造扫码链接 → 回调带 code → `getuserinfo` 换 UserID | 扫码/免登 → 回调带 authCode → 换 unionId/userId |
| 用户标识     | `UserID`（企业内唯一）                            | `unionId`（跨企业唯一，**推荐**）                 |
| 匹配策略     | UserID 查映射表；未命中用手机号匹配                      | unionId 查映射表；未命中用手机号匹配                  |
| 组织同步（可选） | 定时拉取通讯录 → 同步 TenantMember 与部门              | 同左                                      |
| 配置粒度     | **门户统一配置**；各租户可在租户后台选择是否对本租户启用             | 同左                                      |

##### 6.7.2.3 SAML 2.0（传统企业 IdP，如 ADFS）

```
配置项:
{
  "sp_entity_id": "https://id.erpv3.example.com/saml/metadata",
  "sp_acs_url": "https://id.erpv3.example.com/saml/acs/{idp_id}",
  "idp_metadata_url": "https://adfs.partner.com/federationmetadata/2007-06/...xml",
  "idp_sso_url": "...",
  "idp_certificate": "PEM 公钥 (验证 Assertion 签名)",
  "name_id_format": "urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress",
  "attribute_mapping": {
    "user_id": "http://schemas.xmlsoap.org/.../name",
    "display_name": ".../displayName",
    "phone": ".../mobile"
  },
  "sign_authn_request": true
}
```

处理要点：ACS 端点接收 SAMLResponse → 验签（IdP 证书）→ 校验条件（Audience/NotOnOrAfter）→ Attribute 映射 → 同 OIDC 流程进入映射/匹配/开户 → 三阶段登录 Phase 2。

##### 6.7.2.4 LDAP / AD（账号口令直连，私有化部署常见）

| 项  | 说明                                                                     |
| -- | ---------------------------------------------------------------------- |
| 配置 | ldap\_url、base\_dn、bind\_dn（加密）、user\_filter（如 `(sAMAccountName={0})`） |
| 流程 | 用户输入域账号口令 → Identity Service 执行 LDAP bind 校验 → 查映射/匹配/开户 → 进入 Phase 2  |
| 安全 | 强制 LDAPS 或 StartTLS；口令不落地存储                                            |
| 适用 | 私有化部署 / 企业内网场景；SaaS 云端默认不开放                                            |

##### 6.7.2.5 首次登录的账号绑定策略

外部身份首次登录且无法自动匹配时，提供两种绑定路径（门户可配置默认策略）：

| 策略             | 流程                                                                              | 适用          |
| -------------- | ------------------------------------------------------------------------------- | ----------- |
| **自动匹配**（推荐默认） | 按手机号/邮箱匹配已有 PortalUser → 匹配成功自动建立映射，无需用户操作                                      | 大多数 SaaS 场景 |
| **手动绑定**       | 展示绑定页：输入 login\_account + 密码/验证码 → 校验通过建立映射                                     | 高安全要求租户     |
| **自动开户**       | `auto_provision=true` 时直接创建 PortalUser（display\_name 取 IdP 昵称）→ 进入"无租户"空状态页等待邀请 | 开放注册场景      |

#### 6.7.3 角色 3：开放 API 的 OAuth2 保护（Resource Server）

```
第三方系统 (M2M)                     ERPv3 认证中间件
      │                                  │
      │ ① POST /oauth2/token             │
      │    grant_type=client_credentials │
      │    &client_id=xxx                │
      │    &client_secret=xxx            │
      │    &scope=erp:api tenant:123     │
      │ ────────────────────────────────►│ ② 校验 client + scope + 租户授权
      │ ◄────────────────────────────────│ ③ access_token (JWT, 1h, 无 refresh)
      │                                  │
      │ ④ GET /api/v1/open/tenants/123/  │
      │    finance/vouchers              │
      │    Authorization: Bearer {token} │
      │ ────────────────────────────────►│ ⑤ 网关校验: 签名 + exp + jti 黑名单
      │                                  │    + scope 覆盖 + tenant 匹配
      │ ◄────────────────────────────────│ ⑥ 返回数据 (受 scope 与数据权限约束)
```

| 安全要求      | 说明                                                        |
| --------- | --------------------------------------------------------- |
| scope 最小化 | M2M Token 只能申请门户管理员显式授予的 scope                            |
| 租户绑定      | M2M Client 必须绑定到具体 tenant\_id，Token 中固化，不可跨租户             |
| 限流独立      | M2M Client 独立限流配额，与交互式用户隔离                                |
| 调用审计      | 全部 M2M 调用写入门户库 `plog_audit`（`platform_audit_logs`），actor\_type=OAUTH\_CLIENT |
| 密钥轮换      | client\_secret 支持双密钥并行（旧密钥 7 天宽限期），轮换不中断                  |

#### 6.7.4 单点登出（SLO）

| 方向            | 机制                                                                                             | 说明                                 |
| ------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------- |
| ERPv3 主动登出    | 吊销本地 Session + Refresh Token + jti 入黑名单（见 6.6）；若经外部 IdP 登录，可选重定向到 IdP 的 end\_session\_endpoint | OIDC RP-Initiated Logout           |
| 外部 IdP 发起登出   | 实现 Back-Channel Logout 端点 `POST /oidc/backchannel-logout`，校验 logout\_token 后吊销对应用户全部会话         | OIDC Back-Channel Logout 规范        |
| SAML SLO      | 实现 `POST /saml/slo` 端点，处理 IdP 的 LogoutRequest                                                  | SAML2 Single Logout Profile        |
| 第三方 Client 登出 | Client 调 `/oauth2/logout?id_token_hint=...&post_logout_redirect_uri=...`，校验后清除会话并回调            | post\_logout\_redirect\_uri 必须预先注册 |

#### 6.7.5 安全基线清单

| #  | 项              | 要求                                                       |
| -- | -------------- | -------------------------------------------------------- |
| 1  | redirect\_uri  | 精确匹配，禁止通配符与开放重定向；localhost 仅开发环境                         |
| 2  | state / nonce  | 强制生成与校验，防 CSRF 与重放                                       |
| 3  | PKCE           | 所有 Public Client 强制 S256，禁用 plain                        |
| 4  | Token 签名       | RS256 非对称，密钥对 90 天轮换，JWKS 提供平滑过渡                         |
| 5  | 授权码            | 一次性使用、10 分钟过期、与 client\_id+redirect\_uri 绑定              |
| 6  | Refresh Token  | 轮换策略：每次使用签发新 Token 并吊销旧 Token；检测到旧 Token 重用 → 整链吊销（盗用检测） |
| 7  | client\_secret | 仅 BCrypt 哈希存储，不明文落库、不出现在日志                               |
| 8  | TLS            | 全部端点强制 HTTPS，回调地址仅允许 https\://                           |
| 9  | 授权页            | 明示应用名、Logo、申请 Scope 清单与隐私政策链接                            |
| 10 | 速率限制           | token 端点按 client\_id 限流；authorize 端点按 IP+用户限流，防爆破        |

## 8. 账户状态控制模型

### 8.1 状态联动规则（核心设计）

这是 ERPv3 最核心的状态控制机制，**门户层面的状态是全局硬开关，租户层面的状态在门户允许的范围内生效**。

#### 8.1.1 三层状态模型

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  Layer 1: PortalUser.status  (全局身份开关)                          │
│  ──────────────────────────────────────────────                      │
│  • 控制粒度：整个自然人，跨所有租户                                   │
│  • 操作方：门户管理员                                                 │
│  • DISABLED 时：该自然人在任何租户都无法登录（阶段 1 即被拦截）         │
│                                                                     │
│  Layer 2: Tenant.status  (租户开关)                                 │
│  ──────────────────────────────────────────────                      │
│  • 控制粒度：整个租户，租户内所有成员                                  │
│  • 操作方：门户管理员                                                 │
│  • DISABLED 时：该租户下所有成员都无法使用（阶段 2 显示租户不可选）      │
│                                                                     │
│  Layer 3: TenantMember.member_status  (成员本地开关)                  │
│  ──────────────────────────────────────────────                      │
│  • 控制粒度：单个自然人在某个租户内的成员关系                           │
│  • 操作方：租户管理员                                                 │
│  • DISABLED 时：该自然人**仅在本租户**无法使用，不影响在其他租户的身份   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 8.1.2 有效访问决策真值表

> 访问某个租户上下文时的三层 AND 校验：

| # | 租户状态 (Tenant) | 身份状态 (PortalUser) | 成员状态 (TenantMember) | 有效访问 | 说明                                  |
| - | ------------- | ----------------- | ------------------- | ---- | ----------------------------------- |
| 1 | ENABLED       | ENABLED           | ENABLED             | ✅ 允许 | 正常使用                                |
| 2 | ENABLED       | ENABLED           | DISABLED            | ❌ 拒绝 | **租户内本地停用**，仅影响本租户，该自然人在租户 B 仍可正常使用 |
| 3 | ENABLED       | DISABLED          | ENABLED             | ❌ 拒绝 | **门户全局停用优先**，该自然人无法进入任何租户           |
| 4 | ENABLED       | DISABLED          | DISABLED            | ❌ 拒绝 | 门户全局停用优先                            |
| 5 | DISABLED      | ENABLED           | ENABLED             | ❌ 拒绝 | **门户租户停用优先**，该租户下所有成员全部无法使用         |
| 6 | DISABLED      | ENABLED           | DISABLED            | ❌ 拒绝 | 门户租户停用优先                            |
| 7 | DISABLED      | DISABLED          | ENABLED             | ❌ 拒绝 | 双重禁用                                |
| 8 | DISABLED      | DISABLED          | DISABLED            | ❌ 拒绝 | 双重禁用                                |

#### 8.1.3 多租户场景示例

> 自然人张三（PortalUser ID=1001）同时是"深圳公司"和"北京公司"两个租户的成员：

| 操作                     | 操作方   | 影响范围       | 张三在深圳公司            | 张三在北京公司    |
| ---------------------- | ----- | ---------- | ------------------ | ---------- |
| 门户停用 PortalUser 1001   | 门户管理员 | **全局**     | ❌ 无法登录             | ❌ 无法登录     |
| 门户停用租户"深圳公司"           | 门户管理员 | **深圳公司全体** | ❌ 无法进入             | ✅ 正常       |
| 深圳公司管理员停用张三            | 租户管理员 | **仅深圳公司**  | ❌ 无法进入             | ✅ 正常       |
| 门户重新启用 PortalUser 1001 | 门户管理员 | **全局恢复**   | 需同时租户和成员都是 ENABLED | ✅ 正常       |
| 北京公司管理员解除张三的成员关系       | 租户管理员 | **仅北京公司**  | ✅ 正常               | 张三不再是该租户成员 |

#### 8.1.4 状态控制真值表（简化公式）

```
访问某租户上下文时:

有效访问 = Tenant.status.ENABLED 
       AND PortalUser.status.ENABLED 
       AND TenantMember.member_status.ENABLED

等价于：三个开关必须同时为 ENABLED 才允许访问该租户上下文
```

### 8.2 状态切换规则

```
门户管理员操作：
├── 停用/启用租户 → Tenant.status
│   └── 影响：该租户下**所有 TenantMember**，无论各成员状态如何，全部无法访问
│   └── 跨租户：不影响任何其他租户
│
├── 全局停用/启用自然人 → PortalUser.status
│   └── 影响：该 PortalUser 关联的**所有 TenantMember 记录**，在所有租户都无法登录
│   └── 实现：Redis 批量拉黑该自然人的所有活跃 Token + portal_users.token_version++
│
└── 启用/停用模块 → tenant_modules.status
    └── 影响：该租户下所有 TenantMember 对该模块的访问

租户管理员操作（仅在门户层 Tenant.status=ENABLED 时生效）：
├── 租户内停用/启用成员 → TenantMember.member_status
│   └── 影响：**仅本租户内的该自然人**
│   └── 不影响：该自然人在其他租户的成员关系和访问权限
│   └── 实现：Redis 拉黑该成员在本租户的 Token + tenant_members.token_version++
│
└── 角色分配/移除 → 成员-角色关联变更
    └── 影响：该角色下成员的功能权限
    └── 实现：Redis 批量拉黑 + 重发 Token
```

### 8.3 状态校验时机

| 时机         | 校验点                                         | 说明                                                                    |
| ---------- | ------------------------------------------- | --------------------------------------------------------------------- |
| 登录 Phase 1 | PortalUser.status                           | 前置拦截，快速拒绝全局停用的自然人                                                     |
| 登录 Phase 2 | Tenant.status + TenantMember.member\_status | 只展示有效租户                                                               |
| Token 签发   | 全部三层状态                                      | 确保签发的 Token 对应的是有效访问                                                  |
| 每次 API 请求  | 认证中间件校验 Token 中携带的状态标记                      | Token 中嵌入 tenant\_status / user\_status / member\_status 摘要，避免每次查询数据库 |
| 状态变更时      | 主动推送失效事件                                    | 通过 Redis 黑名单 + token\_version 立即使旧 Token 失效                           |

### 8.4 权限的状态控制

权限控制遵循与账户状态**相同的分层联动逻辑**：

```
功能可用 = 租户级模块许可 (module_code in tenant_modules)   ← 门户控制
        AND 租户级功能开关 (feature enabled in tenant_modules.features)  ← 门户控制
        AND 成员角色权限分配 (permission_code in member.role_permissions) ← 租户控制
        AND 数据权限范围覆盖 (data_scope 过滤)              ← 租户控制
```

| # | 门户模块许可 | 门户功能开关 | 租户角色权限 | 数据权限 | 功能可用            |
| - | ------ | ------ | ------ | ---- | --------------- |

| 2 | ✅      | ✅      | ✅      | ❌    | 部分可用（只能看到权限内数据） |
| 3 | ✅      | ✅      | ❌      | -    | ❌               |
| 4 | ✅      | ❌      | ✅      | -    | ❌               |
| 5 | ❌      | -      | ✅      | -    | ❌               |

逻辑层的"模块/功能点许可"与物理层的"模块 csproj"通过 **module\_code** 一一对应，落地机制见 2.3.5（IModule Manifest 装配）：

| 逻辑概念（本章）             | 物理实现（模块化单体）                                          |
| -------------------- | ---------------------------------------------------- |
| module\_catalog 中的模块 | 一个实现 `IModule` 的独立 csproj，Manifest 声明路由/菜单/权限点/任务/事件 |

| 许可停用                 | 许可中间件拦截端点（404）、菜单不下发、任务暂停调度、事件订阅不激活、Token 重签剔除       |
| features\_json 功能点   | Manifest 声明的权限点子集，租户角色分配后进入用户权限判定                    |

新增业务模块 = 新增一个 csproj + 门户 module\_catalog 登记，门户与宿主零改动（开闭原则）。

## 11. 审计与安全

### 11.1 审计体系

```
┌─────────────────────────────────────────────────────────────────────┐
│        平台日志与审计（门户库 qlx_portal 的 plog_* 表，唯一）          │
├─────────────────────────────────────────────────────────────────────┤
│ • 门户管理员的所有操作（租户管理、模块授权、IdP 配置等）               │
│ • 平台登录日志 / 安全事件（暴力破解、异常 IP）                         │
│ • 平台对租户的管理审计（开通、升级、停用、许可、敏感查看）              │
│ • 全局发布回执（plog_push_receipt，不存消息正文）                      │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│        全局数据（共享库 qlx_shared 的 glb_*，只存一份，租户只读）      │
├─────────────────────────────────────────────────────────────────────┤
│ • 全局公告/任务/消息、消息模板、任务定义、公共字典                    │
│ • 租户库仅存 *_global_state（已读/完成/回执），不复制正文              │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                 租户日志（Tenant Database 的 log_* 表）               │
├─────────────────────────────────────────────────────────────────────┤
│ • 租户管理员与成员的操作日志（用户管理、角色变更、业务操作）            │
│ • 本租户的登录日志                                                    │
│ • 租户任务执行与消息收发记录                                          │
│ • 无平台日志副本（平台不复制、不下沉）                                 │
└─────────────────────────────────────────────────────────────────────┘
```

> **边界**：平台审计只记录「平台对租户做过什么」，租户内部操作**不进平台审计**；租户日志由租户自管，平台不直查。**日志两侧互不复制**（无出站箱、无下沉任务）；**全局数据只存一份**，租户用只读连接优先读取 `glb_*` 再合并本地状态。详见 [多租户数据库模式补充设计.md](多租户数据库模式补充设计.md) §3.4/§5.10/§5.11。

### 11.2 安全规范

| 领域       | 要求                                                         |
| -------- | ---------------------------------------------------------- |
| **密码安全** | 最小长度 8 位，含大小写 + 数字 + 特殊字符；BCrypt 加密；密码不重复历史 5 次            |
| **传输安全** | 全站 HTTPS；生产环境强制 TLS 1.2+                                   |
| **会话安全** | JWT 使用 RS256 非对称签名；Refresh Token 存储在 HttpOnly Cookie       |
| **接口安全** | 所有 API 强制鉴权；敏感接口（删除/导出）需额外二次确认；接口限流                        |
| **数据安全** | 租户数据库连接凭据加密存储；定期密钥轮换；敏感字段（手机号/邮箱）脱敏显示                      |
| **访问控制** | SQL 注入防护（参数化查询）；XSS 防护（输出编码）；CSRF 防护（Double Submit Cookie） |
| **日志安全** | 日志分层存储：门户库 `plog_*`（平台日志/审计/回执）+ 租户库 `log_*`（租户自管）；两侧互不复制、不跨库直查；平台审计不可篡改；敏感操作告警 |
| **合规**   | 支持数据导出（GDPR/个人信息保护法要求）；数据删除请求处理流程                          |

### 11.3 多因素认证（MFA）

| 场景              | 是否强制     | 支持方式                                |
| --------------- | -------- | ----------------------------------- |
| 门户管理员登录         | ✅ 强制     | TOTP (Google Authenticator) / 短信验证码 |
| 租户管理员登录         | 可选（租户配置） | TOTP / 短信 / 邮箱                      |
| 普通租户成员          | 可选       | 短信 / 邮箱                             |
| 敏感操作（数据导出、用户删除） | ✅ 强制     | 已配置的 MFA 方式                         |

## 13. API 设计约定

### 13.1 URL 结构

```
/api/v1/portal/*          → 门户级 API (需门户管理员 Token)
/api/v1/tenants/{id}/*   → 租户级 API (需对应租户上下文 Token)
/api/v1/auth/*           → 认证相关 (无需 Token)
/api/v1/admin/*          → 超级系统 API (最高权限，审计严格)
```

**ID 约定**：URL 路径参数与请求/响应体中的业务 ID 一律为 Hashids 混淆字符串（见 2.3.8），由框架在收发边界自动加解密；API 文档与客户端永远不感知真实数值 ID。

### 13.2 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": { ... },
  "request_id": "uuid-for-tracing",
  "timestamp": 1735689600000
}
```

## 14. 部署拓扑

### 14.1 物理部署（推荐）

模块化单体为**单部署单元**：身份认证、门户管理、租户业务模块、支撑模块、Hangfire 调度全部运行在同一应用进程内，应用无状态、按负载水平扩展 Pod 数即可。

> ⚙️ **前后端分离部署（2026-10-21 已落地）**：
> 前端 Vue 单壳与后端 API 可分域部署。后端 CORS 配置（`Qlx.BuildingBlocks.Web.QlxCorsOptions`，配置节 `Qlx:Cors`，文件 `config/common/cors.json`）控制允许的前端源，禁止硬编码。
> `UseQlxCors()` 中间件位置**必须在 `UseRouting()` 之前**，否则 OpenIddict `/connect/*` 端点会拦截 OPTIONS 预检返回 400。
> 前端 `.env.production` 设 `VITE_API_BASE_URL` 为后端 API 绝对地址；OpenIddict Issuer（`Qlx:Portal:Auth:Issuer`）须为生产正式域名（手动 JWT 校验时自动做 Uri.AbsoluteUri 归一化）。

**多实例下的一致性要点**：

| 事项           | 机制                                                                    |
| ------------ | --------------------------------------------------------------------- |
| Hangfire 多实例 | 同一数据库存储天然支持多 Server 竞争取任务；同 task\_code 单实例防并发用分布式锁（租户维度，见 支撑功能/03 R5） |
| Outbox 分发    | 分发器以数据库行锁/租约保证同一 Outbox 消息仅被一个实例投递                                    |
| 会话与黑名单       | 全部存 Redis，应用实例无状态                                                     |
| SSE 实时推送     | 用户连接固定在某一 Pod，事件经 Redis Pub/Sub 扇出到各 Pod 推送（见 支撑功能/02）                |
