## 二、逐项整改详情

### V-01 Redis 无认证 + 绑定全网（严重）

**问题**：6379 端口无密码对外开放，任意主机可直连读写缓存（含权限、登录计数、会话数据）。

**修复**：
1. Redis 运行时通过 `CONFIG SET requirepass <40位随机口令>` 立即启用认证，并经 `CONFIG REWRITE` 持久化到 `redis.windows-service.conf`。
2. 配置文件追加 `bind 127.0.0.1`（下次 Redis 服务重启后生效，彻底关闭对外监听）。
3. Windows 防火墙新增入站阻断规则（6379 端口），立即切断外部访问路径。
4. 应用侧更新 [config/common/cache.json](../config/common/cache.json) 连接串，注入 `password=` 段。

**关键文件**：
- [config/common/cache.json](../config/common/cache.json)（连接串 + 安全提示注释）

**复测**：
- 无密码 `PING` → `-NOAUTH Authentication required.`
- 带密码 `AUTH` → `+OK`
- 防火墙规则在 6379 入站阻断生效。

---

### V-02 缓存提权面（高危）

**问题**：旧系统（v1/v2）将用户权限以 `auth:permission:user:{userId}` 形式写入 Redis，若被篡改即提权。

**根因分析**：当前 v3 系统的权限判定**完全内嵌在 RS256 签名 JWT** 中（不落 Redis），旧键属于历史残留。一旦 V-01 的认证与网络面收敛，外部篡改路径即被切断。

**整改**：通过 V-01 的 requirepass + 防火墙 + bind 三项组合，从根上关闭篡改入口。当前系统不再有"Redis 即权限"的攻击面；同时 `ICacheService` 唯一入口（C-1）保证未来业务也不会将安全判定值写入缓存。

**复测**：未授权直连 Redis 已不可能；带密码访问下未发现 v3 权限相关键。

---

### V-03 登录响应消息枚举 + 账号锁定 DoS + 无 IP 限流（高危）

**问题**：
1. 错误密码返回"账号或密码错误"，已锁定账号返回"账号已锁定"——攻击者可枚举有效账号。
2. 锁定仅按账号维度计数，攻击者可故意反复触发他人锁定实现 DoS。
3. 单一 IP 可无限尝试，无源端限流。

**修复**（[PortalAuthenticationService.cs](../src/Qlx.Modules.Portal/Services/PortalAuthenticationService.cs)）：

1. 新增统一失败文案常量 `CredentialFailureMessage = "账号或密码错误，或账号已被锁定"`，所有密码错误、账号锁定、IP 封禁场景均返回此消息，HTTP 状态码统一 400 + `invalid_grant`。
2. 新增 IP 维度计数与封禁（阈值 `MaxIpFailuresPerWindow = 20`），超限后写入 `ipblock` 键，后续该 IP 上任何账号的登录尝试都被前置拒绝。
3. 失败计数、锁定、IP 计数、IP 封禁四类键统一走 `AuthSecurityCacheKeys`（见 V-04），符合 C-1-2 键规范。
4. 新增 LoggerMessage 部分方法 `LogAccountLocked`、`LogIpBlocked`（Warning 级），保留审计线索供安全运营回溯。

**关键文件**：
- [src/Qlx.Modules.Portal/Services/PortalAuthenticationService.cs](../src/Qlx.Modules.Portal/Services/PortalAuthenticationService.cs)
- [src/Qlx.Modules.Portal/Auth/QlxAuthConstants.cs](../src/Qlx.Modules.Portal/Auth/QlxAuthConstants.cs)（删除旧 `AuthCacheKeys` 嵌套类）

**复测**：
- 同一不存在账号连续 7 次失败：消息全部统一为"账号或密码错误，或账号已被锁定"，无法据此区分账号存在性。
- 同一真实账号 `enumtest` 连续 7 次失败（含触发锁定后）：消息同样统一，锁定状态不外泄。
- 累计 20 次失败后：IP 被封禁，**从未见过的新账号** `freshuser1/2/3` 也直接返回统一消息被拒。

---

### V-04 登录账号原样拼 Redis 键（中危）

**问题**：旧实现将 `loginAccount` 原样拼入 Redis 键（如 `qlx:_portal:auth:pwfail:admin'--`），攻击者可通过构造包含特殊字符的账号实现键空间污染，且明文账号泄露在键名中。

**修复**：

新建 [src/Qlx.Modules.Portal/Auth/AuthSecurityCacheKeys.cs](../src/Qlx.Modules.Portal/Auth/AuthSecurityCacheKeys.cs)，统一通过 `QlxCacheKey.BuildPortalKey("auth", ...)` 构建（C-1-2 合规），账号/IP 一律 SHA256 哈希后取前 16 字节小写十六进制入键，输入 Trim + 小写归一化：

```csharp
public static class AuthSecurityCacheKeys
{
    private const string ModulePrefix = "auth";
    public static string PasswordFail(string loginAccount) => Build("pwfail", loginAccount);
    public static string Lockout(string loginAccount)      => Build("lockout", loginAccount);
    public static string IpFail(string ipAddress)          => Build("ipfail", ipAddress);
    public static string IpBlock(string ipAddress)         => Build("ipblock", ipAddress);
    private static string Build(string category, string rawValue)
        => QlxCacheKey.BuildPortalKey(ModulePrefix, $"{category}:{Hash(rawValue)}");
    private static string Hash(string rawValue)
    {
        var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(rawValue.Trim().ToLowerInvariant()));
        return Convert.ToHexString(bytes[..16]).ToLowerInvariant();
    }
}
```

调用点同步替换：
- [PortalAuthenticationService.cs](../src/Qlx.Modules.Portal/Services/PortalAuthenticationService.cs)：失败计数、锁定检查、IP 计数、IP 封禁。
- [PortalUserAdminService.cs](../src/Qlx.Modules.Portal/Services/PortalUserAdminService.cs)：管理员密码重置后清理失败计数与锁定。

**复测**：通过 `KEYS qlx:_portal:auth:*` 列出 17 个测试期间产生的键，**全部为 32 位小写十六进制哈希**，无任何明文 loginAccount / IP 泄露。

---

### V-05 超长表单触发 500 暴露框架细节（中危）

**问题**：5MB 表单触发 ASP.NET Core `BadHttpRequestException`，未被业务异常映射捕获，最终返回 500 并泄露 `FormOptions` 内部限制细节。

**修复**：

1. **前置长度校验**（[PortalAuthenticationService.cs](../src/Qlx.Modules.Portal/Services/PortalAuthenticationService.cs)）：登录入参增加 `MaxCredentialLength = 128` 常量，超过即返回 400 `invalid_request` + "login_account 或 password 长度超出限制"，**在到达模型绑定/表单解析前提前短路**。
2. **统一异常映射**（[ExceptionHandlerMiddleware.cs](../src/Qlx.BuildingBlocks/Api/ExceptionHandlerMiddleware.cs)）：新增映射——

   ```csharp
   BadHttpRequestException or InvalidDataException
       => ((int)HttpStatusCode.BadRequest,
           ApiResponse<object>.Fail("BAD_REQUEST", "请求格式非法或超出大小限制", HttpStatusCode.BadRequest)),
   ```

   任何绕过前置校验抵达框架层的大请求统一以 400 + 通用错误码 `BAD_REQUEST` 应答，不暴露框架内部细节。

**关键文件**：
- [src/Qlx.Modules.Portal/Services/PortalAuthenticationService.cs](../src/Qlx.Modules.Portal/Services/PortalAuthenticationService.cs)
- [src/Qlx.BuildingBlocks/Api/ExceptionHandlerMiddleware.cs](../src/Qlx.BuildingBlocks/Api/ExceptionHandlerMiddleware.cs)

**复测**：
- 5000 字符超长 `login_account` → 400 `invalid_request` "login_account 或 password 长度超出限制"。
- 5 MB（5,242,968 字节）表单 payload → 400 `{ "success": false, "code": "BAD_REQUEST", "message": "请求格式非法或超出大小限制" }`，无堆栈、无框架内部信息。

### V-06 HTTP 明文传输（中危）

**性质**：部署基线事项，不在代码修复范围。

**遗留动作**：生产部署时必须由运维启用 HTTPS（Kestrel 证书 / 反向代理 TLS 终结），并通过 HSTS、HTTP→HTTPS 重定向强制加密。当前开发环境暂不启用，避免本地证书管理复杂度。

---

### V-08 缺安全响应头（低危）

**问题**：响应缺少 `X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` 等基线安全头。

**修复**（[Program.cs](../src/Qlx.Host/Program.cs)）：在 `UseExceptionHandlerMiddleware` 之后追加安全响应头中间件——

```csharp
_ = app.Use(async (context, next) =>
{
    context.Response.Headers["X-Content-Type-Options"] = "nosniff";
    context.Response.Headers["X-Frame-Options"] = "DENY";
    context.Response.Headers["Referrer-Policy"] = "no-referrer";
    await next(context).ConfigureAwait(false);
});
```

**复测**：`curl -I http://127.0.0.1:5002/health` 返回——

```
HTTP/1.1 200 OK
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
```

## 五、遗留与建议

1. **V-06 HTTPS**：列入运维部署基线，需在反向代理或 Kestrel 启用 TLS 并配置 HSTS。
2. **Redis bind**：`bind 127.0.0.1` 已写入配置文件，待下次 Redis 服务重启后由防火墙（已生效）升级为网络栈级别收敛。
3. **旧系统共存**：若旧版 ERP（v1/v2）与本机共用此 Redis，必须同步升级连接配置以携带新密码。
4. **审计跟进**：`LogAccountLocked`、`LogIpBlocked` 已落 Warning 级日志，建议接入安全运营平台做阈值告警。
5. **下一轮渗透**：建议过 1 个版本周期后再做黑盒复测，重点验证 V-06 启用 HTTPS 后的整体姿态与新增业务接口的越权矩阵。
