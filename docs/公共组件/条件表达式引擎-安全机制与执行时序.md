## 一、全链路输入安全校验实现方案

### 1.1 分层校验模型（前端 → API → 业务 Service → 引擎内部）

```
前端表单输入 → ① Schema 校验 + RC → API 层参数校验 → ② FluentValidation + Model 绑定 → 业务 Service 聚合 → ③ 条件表达式引擎内部边界校验 → 表达式求值 / 数据库查询
```

| 分层 | 本项目实现 | 技术约束 |
|---|---|---|
| **前端** | `src/Qlx.Web/src/core/http.ts` axios 拦截器自动注入身份/租户 Token；RC 机制约束变更路径；TypeScript 表单组件内置字段类型/长度校验 | 前端校验仅为 UX 优化，**不视为安全边界** |
| **API 层** | 已有 `ValidationException`（422）统一收敛 FluentValidation 结果；Model 禁用 `[AllowAnonymous]` + 强制 `[Authorize]` | 禁止自行绕过 Model 绑定手动解析 JSON；所有外部输入（含 `expr_json`）经 `FromBody` / `FromQuery` 强制类型化 |
| **业务 Service** | 参数化 EF Core 查询（禁止原生 SQL，项目规则明确）；多租户 RLS 自动过滤（`TenantDbContextConnectionFallback`） | 必须在 Service 层完成**变量聚合 + 权限过滤**后再组装 `DictionaryVariableResolver` 传入引擎 |
| **表达式引擎内部** | `ConditionExpressionEngine.Parse` 强制校验：`MaxExpressionLength=8192`（防超长 DoS）、`MaxDepth=64`（防深递归栈溢出）、词法器拒绝非法字符/未闭合字符串/歧义数字（`123abc` 报 Parse 错误）、解析器拒绝未注册函数 | 引擎不做业务级权限判断，仅做**语法边界防护** |

### 1.2 常见攻击防护

| 攻击类型 | 本项目防护手段 | 待落地补全 |
|---|---|---|
| **SQL 注入** | EF Core 全程参数化查询 + 项目规则禁止原生 SQL + 条件表达式引擎**不生成任何 SQL**（输入是已聚合的变量字典，不是 SQL 片段） | 若业务方自定义表达式函数（经 DI 拿 DbContext），必须强制使用 `FormattableString` / `ExecuteInterpolated` |
| **XSS** | Blazor/Razor 默认 HTML 转义；条件表达式引擎 `ReadableText` / `ToJson` 输出纯文本 + STJ 默认对 `>` `<` `&` 做 `\uXXXX` 转义（经平台 `QlxJsonDefaults`）；`SensitiveDataMasker` 输出等长全星串（防泄露） | **缺失**：全局 CSP 头（`Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'`）需在 `Program.cs` 统一配置 |
| **CSRF** | OpenIddict Bearer Token 认证（Cookie 场景仅 Razor Pages 自带 AntiForgery Token）；CORS 经 `QlxCorsOptions` 做**严格白名单**（禁止 `*`） | 若启用 Cookie 认证分支，需强制 `SameSite=Lax` + AntiForgery Token 全量覆盖 |
| **表达式注入** | 条件表达式引擎内部词法器对**扩展数字词素**（如 `0x1F`）仅送达自定义解析器，内置解析失败即报 Parse 错误；注册表快照不可变（运行期无法注入新运算符/函数） | 若允许前端自定义表达式片段（审批 condition-builder 已对接），必须对**表达式变量名**做白名单过滤（见第二部分） |
| **参数篡改** | 多租户 RLS 自动注入 `TenantId` 过滤条件；Hashids 混淆实体 ID（`src/Qlx.BuildingBlocks/Ids/HashidsObfuscator`）防止 IDOR | — |

### 1.3 输入约束规则清单（引擎侧硬编码，不可绕过）

```csharp
// ConditionEngineOptions 组合期一次性固化，运行期不可变
public sealed class ConditionEngineOptions
{
    public int MaxExpressionLength { get; set; } = 8192;  // 防超长 DoS
    public int MaxDepth { get; set; } = 64;              // 防深递归栈溢出
    public bool ThrowOnUnresolvedVariable { get; set; } = true;  // 严格模式：缺变量显式失败
}
```

词法器/解析器硬编码校验规则（见 `ConditionLexer` / `ConditionParser`）：

| 规则 | 违反后果 |
|---|---|
| 数字后紧跟字母/下划线但自定义解析器未命中 | 抛 Parse 异常（`123abc` → 非法数字字面量） |
| 字符串未闭合 | 抛 Parse 异常（带位置） |
| 含 `$` 但非 `${name}` 格式 | 抛 Parse 异常（参数变量语法错误） |
| 含未注册函数调用 | 抛 Parse 异常（函数未注册） |
| 括号不配对 | 抛 Parse 异常（括号不配对） |
| 出现 `;` 等分隔符 | 抛 Parse 异常（意外词素） |
| 超出 `MaxExpressionLength` | 抛 Parse 异常（长度超限，片段截取安全） |
| 超出 `MaxDepth` | 抛 Parse 异常（深度超限，栈溢出防护） |

## 二、模板变量不可篡改保障机制

模板变量指审批模板、业务模板中引用的表达式变量（如 `${amount}`、`${creator.role}`），核心风险包括：**越权访问敏感变量**、**运行时被外部修改**、**模板定义被篡改（注入非法变量引用）**。

### 2.1 变量作用域隔离 + 只读属性

| 实现层 | 本项目落地 | 防篡改原理 |
|---|---|---|
| **变量解析器** | `IVariableResolver` 提供两种只读实现：<br>① `DictionaryVariableResolver`：内部用 `FrozenDictionary<string, object?>`（不可变快照，构造后零修改可能）<br>② `CompositeVariableResolver`：组合多个只读 resolver，本身也是只读聚合 | `FrozenDictionary` 是 .NET 不可变集合，**无 Add/Remove 方法**；引擎求值时仅调用 `TryResolve`（只读接口），不可能写回 |
| **表达式制品** | `ConditionExpression` 是 `sealed record`，`Root` / `Variables` / `SourceText` 全为 init-only；AST 节点（`LiteralNode` / `BinaryNode` 等）同样是 sealed record | 编译后的表达式制品可跨线程共享、可缓存、不可变 |
| **注册表快照** | `ConditionRegistry` 构造期一次性构建 `FrozenDictionary`，引擎创建后**零锁零修改** | 运行期不可能新增/替换运算符/函数，杜绝「表达式执行到一半被注入恶意函数」的可能 |

### 2.2 模板变量白名单（越权防护）

当前 `DictionaryVariableResolver` 可扩展为**带白名单的变量解析器**，防止模板表达式引用越权变量（如 `${user.password}`）：

```csharp
/// <summary>带变量白名单的安全 resolver（审批模板场景专用）。</summary>
public sealed class WhitelistedVariableResolver : IVariableResolver
{
    private readonly FrozenDictionary<string, object?> _values;
    private readonly FrozenSet<string> _allowedNames;

    public WhitelistedVariableResolver(
        IEnumerable<KeyValuePair<string, object?>> values,
        IEnumerable<string> allowedNames)
    {
        _values = values.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);
        _allowedNames = allowedNames.ToFrozenSet(StringComparer.OrdinalIgnoreCase);
    }

    public bool TryResolve(string name, out object? value)
    {
        // 变量名不在白名单 → 视为未解析，严格模式抛 Evaluate 异常
        if (!_allowedNames.Contains(name))
        {
            value = null;
            return false;
        }

        return _values.TryGetValue(name, out value);
    }
}
```

**白名单来源**：审批模板创建时 `condition-builder` 前端根据当前表单字段定义自动生成，持久化在模板元数据中（与 `expr_json` 一起存），加载时一并取回用于构造 `WhitelistedVariableResolver`。

### 2.3 签名校验（模板定义防篡改）

审批模板的 `expr_json` 持久化时追加**签名字段**（HMACSHA256，密钥由宿主服务持有的对称密钥），加载时校验签名完整性：

```csharp
/// <summary>审批模板表达式元数据（持久化结构）。</summary>
public sealed class TemplateCondition
{
    public string ExprJson { get; init; } = string.Empty;  // 表达式 AST JSON
    public string ExprText { get; init; } = string.Empty;  // 可读文本（自动生成）
    public string? Variables { get; init; }                 // 预提取的变量清单（JSON 数组）
    public string Signature { get; init; } = string.Empty; // HMACSHA256（ExprJson + Variables）
    public Guid TenantId { get; init; }
}
```

签名算法：

```csharp
using var hmac = new HMACSHA256(secretKey);
var data = Encoding.UTF8.GetBytes(exprJson + "\0" + variablesJson);
var signature = Convert.ToHexString(hmac.ComputeHash(data));
```

校验时签名不匹配 → 模板被篡改 → 拒绝加载并记录审计日志。

### 2.4 运行时变量监控（审计日志）

复用项目已有的 `IAuditService`，每次表达式求值追加 `ExpressionEvaluation` 审计项：

```csharp
/// <summary>表达式求值审计事件（扩展 IAuditService）。</summary>
public sealed class ExpressionEvaluationEntry
{
    public long TenantId { get; init; }
    public long UserId { get; init; }
    public string TemplateCode { get; init; } = string.Empty;
    public string ExprText { get; init; } = string.Empty;        // 可读文本
    public IReadOnlyDictionary<string, object?> Variables { get; init; } = [];  // 变量快照
    public bool Result { get; init; }                            // 求值结果
    public bool IsSuccess { get; init; }                         // 是否成功（false 时 ErrorCode/Message 有值）
    public string? ErrorCode { get; init; }                      // CONDITION_EXPR_PARSE/EVAL_ERROR
    public string? ErrorMessage { get; init; }
    public int DurationMs { get; init; }                         // 执行耗时
    public DateTimeOffset EvaluatedAt { get; init; }
}
```

审计项自动记录**变量快照 + 错误码 + 耗时**，是排查变量篡改/越权访问的核心取证依据。

## 三、数据查询与条件表达式执行时序

### 3.1 核心前提：条件表达式引擎是「变量求值器」而非「查询构建器」

引擎**不直接操作数据库**，输入是调用方（业务 Service）传入的 `IVariableResolver` 只读字典。因此时序由**变量组装时机**决定。

### 3.2 两种时序模式

#### 模式 A：先查数据 → 再执行表达式（**当前项目默认、推荐**）

```
客户端 → Controller → 业务Service
  业务Service:
    ① 聚合查询变量（多表 + 权限过滤 + 缓存）
    ② 组装 DictionaryVariableResolver
    ③ 调用 Engine.Evaluate(expr_json, resolver)
       → Parse（语法校验）
       → Evaluate（变量求值）
    ④ 执行业务流程（审批流转等）
  返回结果
```

| 维度 | 说明 |
|---|---|
| **执行阶段** | 表达式**解析**（Parse）在求值前 → 表达式**校验**（语法+边界）在解析时 → 表达式**执行**（Evaluate）在变量组装后 |
| **适用场景** | 变量来自多个表、需要预聚合、需要权限过滤、需要缓存（热路径） |
| **风险** | 若变量由外部输入构造（如前端传入），**必须加白名单过滤**（见 §2.2）；变量预取开销需评估（可缓存） |
| **本项目现状** | 审批中心 `condition-builder` 生成的表达式模板，审批实例创建时 Service 先查表单数据 → 组装 resolver → 引擎求值，完全符合此模式 |

#### 模式 B：表达式内嵌查询函数（按需查询，谨慎使用）

```
业务Service → Engine.Evaluate(expr_json, resolver=空)
  引擎执行过程中：
    ① 调用自定义函数 GetUserDepartment(creatorId)
    ② 函数内部经 DI 拿 DbContext 查库
    ③ 返回部门值给引擎继续求值
```

| 维度 | 说明 |
|---|---|
| **执行阶段** | 表达式执行时触发查询（解析阶段必须校验函数已注册，解析时不查数据） |
| **适用场景** | 变量是按需查询的、业务逻辑需要动态决定查什么（如「审批人部门是否在允许列表」，部门值依赖 creatorId） |
| **风险** | ① N+1 查询（循环求值时函数内部反复查库）② 查询性能不可控③ 函数内部必须做权限过滤（禁止跨租户查数据）④ 难以缓存 |
| **技术约束** | 自定义函数经 `context.Services?.GetService<DbContext>()` 访问，**必须在函数内部强制 `AsNoTracking` + `TenantId` 过滤**；禁止在函数内部写库 |

### 3.3 解析/校验/执行的时序边界

```
① Parse（解析）：expr_text → AST，仅做语法校验，零数据库访问
② 校验（边界）：Parse 时同步完成（长度/深度/未注册函数），失败抛 Parse 异常
③ Evaluate（执行）：AST + 变量 resolver → 布尔/值，此时才触发数据库访问（若用模式 B）
```

**关键约束**：Parse 和 Evaluate 是两次独立调用——`ConditionExpressionEngine.Parse` 返回的 `ConditionExpression` 制品可缓存复用，避免重复解析开销。

### 3.4 两种模式对比

| 对比项 | 模式 A（先查后评） | 模式 B（内嵌查询） |
|---|---|---|
| 安全可控性 | 高（变量在 Service 层统一聚合、权限过滤） | 低（函数内部需独立做权限过滤，易遗漏） |
| 性能可预测性 | 高（查询在 Service 层集中，可缓存） | 低（可能产生 N+1，查询分散在各函数） |
| 可测试性 | 高（变量 resolver 可 Mock） | 低（函数内部查库需集成测试） |
| 缓存友好度 | 高（变量预取结果可缓存） | 低（查询时机不确定） |
| 适用频率 | 默认、绝大多数场景 | 仅需动态查询的特殊场景 |
| 本项目现状 | ✅ 审批中心完全符合 | ❌ 未落地（Code Review 规则禁止直接写库的函数） |

### 4.3 安全纵深防御总结

条件表达式引擎本身是安全基座：FrozenDictionary 注册表快照、不可变 AST、边界校验、统一异常处理——**引擎核心零安全漏洞**。安全闭环依赖多层协同：

```
┌─────────────────────────────────────────────────────────┐
│  ① 前端 UX 校验（TypeScript 类型 + RC 变更约束）          │
│  ② API 类型化绑定 + FluentValidation 后端校验              │
│  ③ Service 层变量聚合 + RLS 权限过滤 + 白名单              │
│  ④ 条件表达式引擎内部语法边界校验（长度/深度/未注册函数）    │
│  ⑤ 模板签名校验 + 表达式求值审计日志                        │
└─────────────────────────────────────────────────────────┘
```

每一层各司其职、互不重叠；任意一层被绕过，下一层仍能拦截。这是「扩展无副作用」承诺能成立的前提——业务扩展代码不可能在运行期修改引擎核心状态，所有安全约束都在组合期固化。
