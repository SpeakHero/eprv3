## 1. 改造背景与目标

### 1.1 背景
DTO 的静态校验规则（`[Required]` / `[StringLength]` / `[CnUscc]` / `[RegularExpression]` / `IValidatableObject`）此前仅在 **MVC 模型绑定层**自动触发。以下入口会绕过 MVC 自动校验：

- 后台任务（JobHandler）直接调用服务
- 种子数据（Seed）直接调用服务
- 服务内部相互调用（非 Controller 入口）
- 集成测试 / 冒烟脚本直接调用服务

一旦调用方传入未经验证的 DTO，服务层的后续逻辑（编码生成、税号查询、数据库预配等）可能在深层抛出难以定位的异常，甚至产生脏数据。

### 1.2 目标
在**服务边界**用 `ObjectValidator.ValidateOrThrow(request)` 做静态规则兜底，使 DTO 的全部验证规则（特性 + `IValidatableObject`）在非 HTTP 入口同样生效；失败时统一抛出项目约定的 `Qlx.Abstractions.Exceptions.ValidationException`（携带 `FieldErrors`，字段名驼峰），与 MVC `ValidationProblemDetails` 行为对齐。

约束：
- 保持原有功能逻辑兼容，不删除任何有状态校验
- 改动最小化，不引入不必要的 DI 依赖

## 5. 遇到的问题与解决方案

本次改造改动量小，未遇到阻塞性问题。记录两个决策点：

### 5.1 是否需要注入 `IServiceProvider`？

**问题**：`ObjectValidator.ValidateOrThrow` 支持传入 `IServiceProvider`，供 `IValidatableObject.Validate` 内通过 `validationContext.GetService` 解析 DI 服务（如 `IOptions<QlxAuthOptions>`）。

**分析**：
- `CreateTenantRequest`、`SaveTenantLicenseRequest` 的校验规则全部为纯静态注解，`IValidatableObject.Validate` 中不调用任何 DI 服务。
- `ResetPortalUserPasswordRequest`（同文件内的另一个 DTO）的 `Validate` 会解析 `IOptions<QlxAuthOptions>`，但它由 `PortalUserAdminService` 使用，不在本次改造范围内。

**决策**：本次改造不向 `PortalTenantAdminService` 注入 `IServiceProvider`，调用 `ObjectValidator.ValidateOrThrow(request)` 不传 `serviceProvider` 参数，保持改动最小。若后续在该服务内接入 `ResetPortalUserPasswordRequest` 校验，再按需注入。

### 5.2 是否删除 `ResolveDatabaseMode` 的兜底抛出？

**问题**：`CreateTenantRequest.DatabaseMode` 已加 `[RegularExpression(PortalConstants.Validation.DatabaseModePattern)]`，理论上非法字面量在 `ObjectValidator` 阶段就被拦截，`ResolveDatabaseMode` 内的 `throw new ValidationException("databaseMode", ...)` 成为死代码。

**决策**：**保留**。作为纵深防御，且 `ResolveDatabaseMode` 是 `private static` 方法，可能被未来的内部调用绕过 DTO 校验直接传入字符串。删除收益低、风险不对称。

## 6. 后续优化建议

### 6.1 优先级 P1：`PortalUserAdminService.ResetPasswordAsync` 接入校验

`ResetPortalUserPasswordRequest` 实现了 `IValidatableObject`，其密码复杂度校验依赖 `IOptions<QlxAuthOptions>`。当前仅在 MVC 模型绑定层生效。建议：

1. 向 `PortalUserAdminService` 构造函数注入 `IServiceProvider`（或直接注入 `IServiceProvider`，避免与现有 `IOptions<QlxAuthOptions>` 重复）。
2. 在 `ResetPasswordAsync` 的 `ArgumentNullException.ThrowIfNull(request)` 之后插入：
   ```csharp
   this.ValidateOrThrow(request);  // 扩展方法，内部传入 serviceProvider
   ```
3. 验证：构造一个不满足密码策略的 `ResetPortalUserPasswordRequest` 直接调用 `ResetPasswordAsync`，应抛出 `ValidationException` 且 `FieldErrors[0].FieldName == "newPassword"`。

### 6.2 优先级 P2：其他模块服务层排查

排查 `Qlx.Modules.Bas`、`Qlx.Modules.Stk`、`Qlx.Modules.Wms` 等模块的 Service，凡接受带 DataAnnotations 的 DTO 且存在非 HTTP 入口（Job / Seed / 内部调用）的，均可按本次模式接入 `ObjectValidator.ValidateOrThrow`。

### 6.3 优先级 P3：测试补充

为 `PortalTenantAdminService` 新增负向单测：直接调用 `CreateAsync` / `SaveLicenseAsync` 并传入非法 DTO，断言抛出 `ValidationException` 且 `FieldErrors` 字段名驼峰。目前 `TenantAdminServiceTests` 主要覆盖正向流程。

### 6.4 优先级 P4：考虑统一拦截层（可选）

若服务层校验调用点增多，可考虑用装饰器 / 拦截器在服务方法入口自动校验 `[Validate]` 标记的 DTO 参数，避免每个方法手写 `ValidateOrThrow`。**已于第二阶段落地**——采用 BCL 自带 `DispatchProxy` 实现（零第三方依赖），见第 8 节。

## 7. 经验总结

1. **静态规则放 DTO，有状态规则放服务**：`ObjectValidator` 只做静态规则兜底，唯一性/存在性等需查库的校验保留在服务内，职责清晰。
2. **是否传 `serviceProvider` 取决于 DTO 是否在 `IValidatableObject.Validate` 内调用 `GetService`**：本次两个 DTO 都不需要，因此零 DI 依赖；密码重置 DTO 需要，接入时必须传。
3. **纵深防御优于死代码清理**：`ResolveDatabaseMode` 的兜底抛出看似冗余，但防御成本极低、误删风险高，保留更稳妥。
4. **备份必须在构建树外**：`E:\ERPv2\eprv3\backup\` 不在任何 `.csproj` 编译范围内，备份文件不会被误编译，回滚只需覆盖。
5. **验证由 Agent 主动完成**：构建 + 单测 + 全量测试全部由 Agent 执行并读取结果，不把验证动作推回给用户。

## 8. 第二阶段：DispatchProxy 方法入口自动校验（2026-10-26 深夜）

> 触发：第一阶段落地后，用户要求「服务方法入口自动校验 `[Validate]` 标记的 DTO 参数，不使用第三方插件」，
> 并补充「同时能不能通过接口判断，本身 DTO 带有验证接口」。

### 8.1 方案选型

| 候选 | 结论 |
| --- | --- |
| Castle DynamicProxy / MediatR Behavior | **否决**：引入第三方 AOP 依赖，违背约束 |
| 源生成器（Source Generator）织入 | 否决：编译期织入复杂度高、调试体验差 |
| **BCL `DispatchProxy`（System.Reflection）** | **采纳**：运行时接口代理，零第三方依赖，天然适配「Controller→接口→实现」分层 |

### 8.2 新增组件（Qlx.BuildingBlocks.Validation）

1. **`ValidateAttribute`**（参数级标记）：标在**接口方法参数**上，适用于仅含 DataAnnotations 特性的 DTO。
2. **`ValidationDispatchProxy<T>`**：拦截接口方法调用，入口自动校验。触发规则双轨制（满足其一即校验）：
   - 参数标注 `[Validate]`；
   - 参数运行时实例实现 `IValidatableObject`（**接口自动识别，无需标记**）；
   - 参数实现 `IAsyncValidatableObject`：先 `await` 异步校验再调实现（包装 `Task` / `Task<TResult>` 返回值；方法参数中的 `CancellationToken` 原样透传；同步返回类型遇异步可验证参数抛 `NotSupportedException`）。
   - 校验上下文服务容器 = 创建代理时传入的 `IServiceProvider`（DTO 内 `GetService` 可解析 `IOptions<>` 等 DI 服务）；
   - 实现方法异常经 `ExceptionDispatchInfo` 原样透传，不包装。
3. **`AddValidatedScoped<TService, TImpl>()` DI 扩展**：一行完成「实现注册 + 接口代理包装」。

### 8.6 遇到的问题与解决方案

1. **CA1711 命名规则**：测试桩类 `ProxyValidatedServiceImpl` 的 `Impl` 后缀触发分析器错误 → 改名为 `ProxyValidatedServiceCore`。
2. **DispatchProxy 可见性**：运行时动态程序集访问不到 internal 接口 → 代理测试中的接口与 DTO 桩一律声明为 `public`（生产代码的服务接口本就是 public，无影响）。
3. **异步校验无法同步拦截**：`DispatchProxy.Invoke` 是同步方法，`IAsyncValidatableObject` 必须 `await` → 对 `Task` / `Task<TResult>` 返回值做异步包装（先校验后调实现），同步返回类型显式拒绝，不静默漏验。

### 8.7 经验补充

1. **标记与接口识别互补**：纯特性 DTO（`CreateTenantRequest` 等）标 `[Validate]`；带对象级规则的 DTO（实现 `IValidatableObject` / `IAsyncValidatableObject`）零标记自动接入——新增此类 DTO 的服务方法**无需任何改动**即获得入口校验。
2. **`[Validate]` 必须标在接口参数上**：DispatchProxy 拦截到的是接口方法的 `MethodInfo`，实现类上的标注不可见。
3. **实现类仍可被直接解析绕过代理**：`AddValidatedScoped` 同时注册实现自身，直接解析实现类型（非接口）不走校验——约束团队只依赖接口消费服务即可。
4. **单测直接构造具体实现时不经过代理**：既有 `TenantAdminServiceTests` 不受影响；代理行为由独立的 `ValidationDispatchProxyTests` 覆盖，职责分离。
