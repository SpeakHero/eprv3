## 0. 重构动因与核心结论

### 0.1 重构动因

原方案（见《开发推进计划.md》阶段二章节）基于"从零开始"的假设编写。但实际开发过程中，**条件表达式引擎**已提前在 `Qlx.BuildingBlocks/Expressions/` 目录落地，同时**多租户隔离基线（B-0）** 也提前交付了大半。

现状 vs 原方案存在三处结构性偏离：

| # | 偏离点 | 原方案预期 | 实际落地 | 影响 |
|---|--------|-----------|---------|------|
| A | 条件表达式实现位置 | `Qlx.Abstractions/Conditions/`（契约）+ `Qlx.BuildingBlocks/Conditions/`（实现） | `Qlx.BuildingBlocks/Expressions/` 24 个文件，完整表达式引擎（文本解析 + AST 多态节点 + 函数系统 + 访问者 + JSON 序列化），契约层未下沉 | 实现远超原计划 AND/OR 嵌套 5 层的范围，但缺 Abstractions 契约；需要**提炼契约下沉**而非重写 |
| B | B-0 多租户隔离基线 | 放在 2B 第一步 | TenantDbContext/WriteGuardInterceptor/RLS/IsolationAuditor/升级管线/租户日志**全部已落地**；缺失的是 SupportTenantDbContext 的 `[TenantTablePrefix]` 特性和对应架构测试断言 | B-0 不再作为 2B 的前置依赖，可**直接进入 Support 工程创建 + 文件中心** |
| C | 2A 状态机 / Messaging | 与条件表达式同批在 2A 交付 | 完全未落地 | 2A 必须包含状态机 + Messaging 适配（SMTP / SMS 桩），补齐后才能冻结契约 |

### 0.2 重构后的整体判断

- **规模判断**：6 子阶段（2A~2F）体量较大，但 B-0 已完成 80%、条件表达式引擎已完成 90%，剩余可编码工作量约为原方案的 **65%**。
- **节奏调整**：保持严格顺序推进，但每子阶段内部进一步拆分"契约冻结 → 公共层 → 模块骨架 → 领域实体 → 服务 → API → 冒烟 → 代码审查"的线性流程，杜绝跨子阶段并行。
- **命名修正**：条件表达式目录已固定为 `Expressions/`（引擎实现）而非原计划的 `Conditions/`，本文档同步采用 `Expressions` 命名，契约下沉时保持 Abstractions 侧命名一致。

### 1.2 实施顺序

```
2A 条件引擎+契约下沉+状态机+Messaging   →   2B Support工程+文件中心
     → 2C 后台任务中心
     → 2D 信息中心+SSE+D13日志两层
     → 2E 审批中心
     → 2F-后端 导入导出+打印+审计过滤
     → 阶段二总验收（含 2F-前端 联调冒烟）
```

**后端子阶段（2A~2E + 2F-后端）严格顺序推进、不并行**。

**前端开发工具集插件（2F-前端）与后端并行**——2A 契约冻结后即可启动，全程用 Mock 数据开发，后端完成后统一联调冒烟。并行范围仅限前端公共组件，**不影响后端子阶段的严格时序**：

| 并行项 | 启动条件 | 依赖（仅契约） | 开发方式 | 联调时机 |
|--------|---------|---------------|---------|---------|

每后端子阶段完成 8 个门禁才算通过：
1. `dotnet restore` 通过（依赖预检）
2. `dotnet build Qlx.Erpv3.slnx` **0 警告 0 错误**
3. 新增单测**全绿**，总测试数满足门禁
4. 架构测试新增断言**全绿**
5. Host `/health` 200 + 主链路冒烟通过
6. 代码审查通过（至少 2 个交叉审查点）
7. 配置 `ValidateOnStart` 全量覆盖，缺关键配置启动即失败
8. 文档与 `por_parameters` 种子同步更新

| **S13（红线·强制）** | **所有耗时操作经任务中心** | 任何预估执行时间 ≥1s 的操作（含大文件分片上传、批量导入导出、格式转换、定期清理、跨租户数据操作、第三方 API 调用）必须经 `IJobScheduler.SubmitAsync` 统一提交；Controller/Service 方法中**禁止**直接执行 `await Task.Run(...)` / 长循环 / 大文件 IO；违规即为架构缺陷 |
| **S14（红线·强制）** | **Messaging 数据库持久化** | `IMessageService.SendAsync` 必须先事务性写入 `msg_messages` + `msg_message_inboxes`（数据库持久化保证零丢失），**再**经 `ISseConnectionManager.PushAsync` 推送 SSE；数据库是持久化真源（write-through），SSE 是实时推送层；离线用户登录后从数据库补拉；`msg_messages` 全量字段包含消息状态机（见 D17） |
| **S15（红线·强制）** | **任务中心任务全生命周期管控** | 所有经 `IJobScheduler.SubmitAsync` 提交的任务必须有完整状态机（见 D19）；默认重试策略（MaxRetries=3, Interval=1min, Backoff=Exponential）；超时阈值（默认 30min，可按 TaskDefinition 覆盖）；执行日志全量持久化到 `job_logs`（只增，不可删） |
| **S16（红线·强制）** | **统一任务提交接口** | 所有模块（Support/Bas/Portal + 未来业务模块）提交耗时任务**只能**经 `IJobScheduler.SubmitAsync(TaskSubmitRequest)` 一个入口，禁止各模块直接 `BackgroundJob.Enqueue` 或自定义入队方式；`TaskSubmitRequest` 必须含 ExecutionMode/TaskCode/TenantId/Parameters/TimeoutSeconds/RetryPolicyOverride 等字段（见 D20） |
| **S17（红线·强制）** | **任务完成后统一通知** | 所有任务（SYNC/ASYNC）完成后：① **ASYNC 模式**必须经 `IMessageService.PushAsync` → `ISseConnectionManager.PushAsync` 推 `TASK_COMPLETED` / `TASK_FAILED` 事件，前端 SSE 监听获取结果；② **SYNC 模式**直接在 HTTP 响应中返回任务结果（`file_id`/元数据等），任务实例同步落 `job_executions`；**禁止**各任务自行调用 `ISseConnectionManager.PushAsync` |
| **S18（红线·强制）** | **文件存储中心全任务化** | 文件中心**所有**操作场景（大文件分片上传/秒传命中/小文件实时上传/下载/预览/格式转换/定期清理）**必须**经任务中心统一调度；SYNC 模式覆盖小文件上传/秒传命中（<3s，直接返回 file_id + 元数据）；ASYNC 模式覆盖大文件分片/格式转换/批量清理（经 SSE 推送完成通知） |

| **D18（新增·已落地）** | **任务执行模式分层：SYNC vs ASYNC** | **这是解决"全部后台化 vs 同步 UX 反馈"矛盾的核心设计**。统一 `IJobScheduler.SubmitAsync(TaskSubmitRequest)` 接受 `ExecutionMode` 参数：① **SYNC 模式**：任务在任务中心登记实例（`job_executions` 行插入 PENDING）→ Hangfire **不**入队，`JobExecutionRunner` 直接在当前 HTTP 请求内同步执行 → 完成后更新实例状态（SUCCESS/FAILED）→ 返回 `TaskSubmitResponse` 包含任务执行结果（`file_id`/元数据/导入校验结果等）。边界条件：预估执行时间 **<3s 且无外部 IO 等待**（数据库查询算内部门槛，文件 hash 计算算外部）。② **ASYNC 模式**：任务登记实例（PENDING）→ 入 Hangfire 队列 → HTTP 立即返回 `TaskSubmitResponse`（含 ExecutionId）→ 执行完成后经 `IMessageService.PushAsync` → `ISseConnectionManager.PushAsync` 推 `TASK_COMPLETED`/`TASK_FAILED` 事件。边界条件：**≥3s 或涉及大文件/批量/格式转换/第三方 API** | 2A 契约、2C 任务中心、2B 文件中心、2D 信息中心、2F 前端 | ✅ 已落地 |
| **D19（新增·已落地）** | **任务中心核心能力：完整状态机 + 可配置重试 + 超时 + 执行日志** | 任务全生命周期状态机：`PENDING → QUEUED → RUNNING → SUCCESS / FAILED / TIMEOUT / CANCELED`；重试：默认 `RetryPolicy { MaxRetries=3, Interval=1min, Backoff=Exponential(2^n), MaxDelay=1h }`，可按 `TaskDefinition` 或 `TaskSubmitRequest` 覆盖；超时：默认 `TimeoutSeconds=1800`（30min），超时后任务置 TIMEOUT + 可配置是否自动重试一次；执行日志：全量写入 `job_logs`（只增），字段含 ExecutionId/TenantId/Loglevel/Message/Detail/StackTrace/LogAt，提供 API 按 ExecutionId/TaskCode/TenantId/时间范围查询 | 2C 任务中心、job_ 实体 | ✅ 已落地 |
| **D20（新增·已落地）** | **统一任务提交接口 `IJobScheduler.SubmitAsync(TaskSubmitRequest)`** | 所有模块**只能**通过这一个入口提交耗时任务，禁止各模块直接 `BackgroundJob.Enqueue`。`TaskSubmitRequest` 字段：`ExecutionMode`（SYNC/ASYNC）、`TaskCode`（必须在 `job_definitions` 注册）、`TenantId`、`InitiatorUserId`（可选）、`Parameters`（Dictionary）、`TimeoutSeconds`（可选覆盖）、`RetryPolicyOverride`（可选覆盖）、`DependsOnExecutionIds`（可选前置依赖，前置成功才执行）、`IdempotencyKey`（可选，防重复提交，Redis 缓存 5min）。返回 `TaskSubmitResponse`：`ExecutionId`、`ExecutionMode`、`InitialStatus`、`ScheduledAt`（ASYNC）或 `CompletedResult`（SYNC 含 ResultJson/Stdout/Stderr/ExecutionDurationMs） | 2A Jobs/ 契约、2C 实现、2E/2F/未来所有模块 | ✅ 已落地 |
| **D21（新增·已落地）** | **通知推送统一经 `IMessageService → ISseConnectionManager`，禁止绕过** | 所有任务完成后（SYNC/ASYNC）、审批完成后（APPROVAL_COMPLETED/REJECTED）、系统告警后，**必须**统一经 `IMessageService.PushAsync` → `ISseConnectionManager.PushAsync` 链路推送，**禁止**各调用方直接 `ISseConnectionManager.PushAsync`（绕过消息持久化层）。`IMessageService.PushAsync` 内部：① 先 `msg_messages` 插入 DRAFT/QUEUED；② 再推 SSE（在线用户即时收到）；③ 异步（Hangfire 后台）更新 `SendLog`（PushDeliveryStatus）。**SYNC 模式结果反馈**：SYNC 任务的 HTTP 响应直接包含结果 JSON（`file_id`/元数据/导入校验结果），**同时** `IMessageService.PushAsync` 发送一条事件通知（SSE 通道）——这让前端可以选择「同步拿结果 + SSE 更新任务状态」的双重模式 | 2D IMessageService/ISseConnectionManager、2C/2E/2F 所有调用方 | ✅ 已落地 |
| **D22（新增·已落地）** | **文件存储中心任务调度规则：SYNC/ASYNC 边界明确** | 文件中心**所有**操作的任务调度规则：① **小文件上传（≤100MB，hash 计算 + DB 写入 + 落盘预估 <3s）** → SYNC 模式：HTTP 同步返回 `file_id` + 元数据 + SHA-256 + Mime + ACL 计算结果；`job_executions` 记录 SUCCESS。② **秒传命中（hash 已存在）** → SYNC 模式：极快，返回引用计数 + file_id + 元数据。③ **大文件分片上传（>100MB 或用户指定分片）** → ASYNC 模式：分片提交后立即返回 `execution_id`，后台组装 hash + 落盘 + DB 写入，完成后经 SSE 推 `TASK_COMPLETED` + `OBJECT_ID`；前端 SSE 监听拿到 file_id。④ **文件下载/预览** → SYNC 模式：流式下载本身不耗时（<1s），不需要任务中心。⑤ **格式转换（PDF/OFD/Office → 预览格式）** → ASYNC 模式。⑥ **定期清理（回收站/临时区）** → ASYNC 模式（Hangfire recurring）。⑦ **ACL 批量变更（跨目录）** → ASYNC 模式 | 2B 文件中心、2C 任务中心、2F 前端文件组件 | ✅ 已落地 |

**C-4 核心实现补充（D19~D21·强制）**

> 以下为 D19 任务状态机、D20 统一提交接口、D21 通知链路的**强制落地要求**，任何模块提交耗时任务都必须遵循。`IJobScheduler.SubmitAsync(TaskSubmitRequest)` 是 **2A 已冻结契约**，此处仅补充实现细节。

| 子项 | 实现要点 | 所在层 |
|------|---------|--------|
| **任务状态机（完整定义）** | `JobExecutionStatus` 枚举：`PENDING（登记成功）→ QUEUED（入 Hangfire 队列）→ RUNNING（Worker 开始执行）→ SUCCESS（执行成功）/ FAILED（业务异常）/ TIMEOUT（超时强制终止）/ CANCELED（用户取消或依赖失败）`；状态转换不可跳过（如 PENDING 不能直接 SUCCESS，必须经过 QUEUED 或 SYNC 模式下 PENDING→RUNNING→SUCCESS/FAILED） | `Qlx.Abstractions/Jobs/`（状态机定义，2A 已冻结） |
| **重试策略** | 默认 `RetryPolicy { MaxRetries=3, Interval=1min, Backoff=Exponential(2^n), MaxDelay=1h }`，可按 `TaskDefinition` 或 `TaskSubmitRequest` 覆盖；重试计数写入 `job_executions.retry_count`；超过 MaxRetries 置 FAILED + 推送 `TASK_FAILED` SSE 事件 | 同上 |
| **超时控制** | 默认 `TimeoutSeconds=1800`（30min）；执行超时后：① Worker CancellationToken 触发 `JobExecutionRunner` 终止执行；② 状态置 TIMEOUT；③ 可配置 `RetryOnTimeout=true`（默认 false）重试一次；④ 推送 `TASK_TIMEOUT` SSE 事件 | 同上 |
| **执行日志持久化** | `job_logs` 表全量持久化（只增），字段 ExecutionId/TenantId/LogLevel(DEBUG/INFO/WARN/ERROR)/Message/Detail/StackTrace/LogAt；`IJobExecutionLogQuery` 提供 API：按 ExecutionId / TaskCode / TenantId / 时间范围查询；禁止删除历史日志 | 同上 |
| **统一提交接口实现（D20）** | `SupportJobScheduler.SubmitAsync(TaskSubmitRequest)`：① 校验 TaskCode 已注册 + IdempotencyKey（防重 5min）；② 插入 `job_executions`（status=PENDING）；③ 按 ExecutionMode 分支：SYNC → JobExecutionRunner.ExecuteDirectAsync（当前 HTTP 内直接执行）→ 更新状态 + 返回 CompletedResult；ASYNC → Hangfire.Enqueue（状态→QUEUED）→ 返回 execution_id | `Qlx.Modules.Support/Services/Jobs/` |
| **SYNC 模式直接执行（D18）** | `JobExecutionRunner.ExecuteDirectAsync(execution)`：用执行上下文（TenantId CancellationToken scope）调用 `IJobHandler.ExecuteAsync` → 捕获结果/异常 → 更新 job_executions 状态/ResultJson/ExecutionDurationMs → 返回 `TaskSubmitResponse.CompletedResult`（SYNC 模式 HTTP 直接返回此结果 JSON） | 同上 |
| **ASYNC 模式 Worker 执行（D18）** | `JobExecutionRunner.ExecuteAsync`（Hangfire Worker 内）：① 状态 PENDING→QUEUED；② 入执行上下文；③ 状态 RUNNING；④ 执行 handler（含 CancellationToken 传播）；⑤ 状态 SUCCESS/FAILED/TIMEOUT；⑥ 推送 SSE 通知（`TASK_COMPLETED`/`TASK_FAILED`/`TASK_TIMEOUT`） | 同上 |
| **通知链路统一（D21）** | SYNC/ASYNC 模式任务完成后**必须**经 `IMessageService.PushAsync` → `ISseConnectionManager.PushAsync` 推事件；**禁止**任务 Handler 内部直接调 `ISseConnectionManager.PushAsync`（绕过消息持久化层）；SYNC 模式除 HTTP 直接返回外，**同时**经 `IMessageService.PushAsync` 发一条 SSE 事件（前端可选双重模式） | 同上 |
| **并发/熔断** | 同租户同 TaskCode 串行锁 `tenant:job:{code}`；连续失败 N 次（参数 `job.failure_threshold`，默认 5）自动暂停 + 经 `IMessageService.PushAsync` 推 `SYSTEM_ALERT` | 同上 |

#### 4.16 任务拆解

**D-1 SSE 基座**
- `Qlx.BuildingBlocks/Sse/ISseConnectionManager.cs` + `SseConnectionManager.cs`：user→连接字典 + 每租户 1000 条环形缓冲 + Last-Event-ID 补发 + 30s 心跳
- `GET /api/support/messages/stream`（text/event-stream，租户 Token 强制）

**D-2 消息服务（D17·write-through 模式）**

> **核心变更（D17 + S14 红线）**：`SupportMessageService.SendAsync/PushAsync` 严格遵循「先持久化、再推送」的 write-through 流程。`msg_messages` 是持久化真源，SSE 只是实时推送层——任何场景下数据库写入优先级最高，SSE 推送失败**不回滚**数据库。

- `TemplateRenderer.cs`：`${var}` 占位符 + var_schema 必填/类型校验 + HTML 转义 + 未知变量报错 + 版本/渠道匹配
- **SupportMessageService（write-through 三步走流程）**：
  - **① 事务性持久化（零丢失保证）**：单 DbContext 事务写 `msg_messages`（Status=QUEUED）+ `msg_message_inboxes`（各收件人批量插入）；任何后续步骤失败都不回滚此事务
  - **② 即时推送**：事务提交成功后再调 `ISseConnectionManager.PushAsync`（在线用户即时收到）；此步失败仅记录日志 + `msg_send_logs` 标记 FAILED，**不影响已持久化的 `msg_messages`/`msg_message_inboxes`**
  - **③ 异步投递**：Hangfire 后台队列写 `msg_send_logs`（记录 PushDeliveryStatus + FAILED 重试计数）+ 渠道分发（见下）
  - **去重窗口**：`message.dedup_minutes`（默认 5）**在数据库写入层做**——查询近窗口内同 `BizRef` 消息已存在则跳过，不进入推送流程
- **离线补拉（真源读数据库）**：`IMessageService.GetUnreadAsync/GetInboxAsync/GetMessageAsync` **只读 `msg_messages` + `msg_message_inboxes`**（数据库持久化真源），不依赖 SSE；SSE 只做实时增量通知，历史/未读状态以数据库为准；用户离线期间推送的消息，登录后不经 SSE 重连也能从数据库拉到
- **消息状态机全链路（D17 强制）**：`msg_messages.status` 枚举完整覆盖：`DRAFT（草稿模板）→ QUEUED（已落库待推送）→ SENT（SSE 已推）→ DELIVERED（至少一个收件人收到推送确认）→ READ（收件人标记已读）→ ARCHIVED（保留期到期自动归档）`；失败分支：`QUEUED→FAILED（Push 重试耗尽）`，FAILED 状态可人工重试回 QUEUED
- **渠道分发**：
  - 邮件：`IMessageService.PushAsync` 写库 → Hangfire 队列调 `ISmtpSender.SendAsync`（指数退避 + 上限 `message.email_retry_limit`）→ 更新 `PushDeliveryStatus`
  - 短信：**只降级站内**——`msg_messages.channel_mask` 置 `SMS_ENABLED | PUSH_DEGRADED_TO_INAPP` + `msg_send_logs` 记录原因；**严禁**外部 SMS 供应商接入时绕过 `IMessageService` 直接发（必须走 `IMessageService.PushAsync` 以保证持久化）
- `/api/support/messages/*`：列表/未读数/已读/全部已读/详情（只读 `msg_messages`/`msg_message_inboxes`）、模板 CRUD、订阅偏好、发送记录（只读 `msg_send_logs`）、人工重试 FAILED 消息

**D-3 D13 日志两层 + 全局数据只存一份**
- **审计路由改造**：`IAuditService` 实现分流——平台操作（开通/升级/许可/敏感查看/发布公告）→ 门户库 `plog_*`；租户内部操作 → 本租户库 `log_*`；**两侧不复制**
- **全局项发布**：门户发布写共享库 `glb_*`（**一份**）+ 平台审计
- **全局项读取器**：`IPlatformSharedReader` 租户侧只读连接 + 短缓存 + 共享库故障降级本地项
- **本地状态叠加**：`msg_global_state` / `job_global_state` 只存 GlobalId + 已读/完成/回执，**不复制正文**；收件箱列表应用层合并，去重键 GlobalId，**禁止跨库 JOIN**
- **强制接受**：全局项 `ForceAccept=1`；租户无删除/拒收入口，仅可标记已读/完成；平台撤回（`Revoked`）是唯一例外
- **回执 API**：`POST /api/support/push/receipts` → 门户库 `plog_push_receipt`；禁止租户直连门户库

**D-4 种子**：审批待办/结果/催办、任务进度/完成/失败、系统通知、预警模板 + 默认渠道矩阵 + 强制订阅项

| 文件上传/预览（任务模式） | **双模式支持（D22 + S18）**：① **SYNC 小文件**（≤100MB）：直接 HTTP `POST /api/support/files/upload` → 后端 `SupportFileStorageService` 内部 `IJobScheduler.SubmitAsync(ExecutionMode=SYNC)` → Controller 返回 HTTP 200 body 含 `file_id` + 元数据 + SHA-256 + ACL 计算结果（JSON 体）；前端立即显示上传成功状态 + 文件卡片。② **ASYNC 大文件**（>100MB 或用户点"分片上传"）：`POST /api/support/files/chunks` → 分片提交 → 立即返回 `execution_id` → 前端 SSE 监听 `TASK_COMPLETED` 事件（`data.task_code=file.chunk.assemble`）→ 事件 `data.result` 含 `file_id` + 元数据 + ACL。③ **上传进度**：SYNC 模式用 XHR progress event；ASYNC 模式用 SSE `TASK_PROGRESS` 事件（`data.percent`）。④ **秒传命中**：上传前/后后端返回 hash 重复检测结果 + 引用计数。**文件预览**：SYNC 流式下载 + 图片/PDF 内嵌预览；OFD/Office 占位跳转（接口预留） | `src/Qlx.Web/src/components/file/` | SYNC 模式 HTTP 直接返回 file_id；ASYNC 模式 SSE 推送联调（见 4.25 验收 6） |

#### 4.25 验收

1. ✅ 后端：模板生成 → 导入（含错误行）→ 导出 → 下载全链路
2. ✅ 打印：模板渲染 HTML 可浏览器打印，二维码内容可扫
3. ✅ 前端 `npm run build` 0 错误；组件以契约 mock 演示可用（condition-builder 输出 AST 与服务端求值结果一致）
4. ✅ 审计过滤器单测确认成功/异常分支均按预期留痕
5. ✅ **前端 SSE 客户端 ↔ 后端 SSE 端点联调验收（3 标签页 + 断点测试）**：
   - SharedWorker 单连接：打开 3 标签页 → 后端 `ISseConnectionManager.GetConnectionCountAsync` 应为 1（SharedWorker 合并）
   - BroadcastChannel 多标签分发：后端推 1 条 `TASK_PROGRESS` → 3 标签页同时收到
   - 指数重连：手动断网 30s 后恢复 → 前端按 1s→2s→4s 指数重连，重连成功
   - Last-Event-ID 补发：断线期间后端推 5 条事件 → 重连后前端携带 `Last-Event-ID`，后端补发全部 5 条
   - 心跳：30s 无事件时仍有后端 ping 事件到达
   - 事件过滤正确性：后端推 `APPROVAL_PENDING` / `TASK_COMPLETED` / `SYSTEM_ALERT` → 前端按 `SseEventType` 路由到各自 handler，无遗漏无串类
6. ✅ **文件上传双模式联调（D22 + S18·强制）**：
   - SYNC 模式：上传 5MB 文件 → HTTP 200 响应 body 含 `file_id` + 元数据 + SHA-256 + ACL 计算结果 → 前端立即显示文件卡片 + SHA-256 校验
   - SYNC 秒传命中：上传与已有 hash 重复的 5MB 文件 → HTTP 200 返回同一 `file_id` + 引用计数（预期 +1）+ 秒传标记提示
   - ASYNC 模式：上传 500MB 文件 → 分片提交返回 `execution_id` → Hangfire 执行中 → SSE 推 `TASK_PROGRESS(percent=30/70/100)` → SSE 推 `TASK_COMPLETED` + `data.task_code=file.chunk.assemble` + `data.result.file_id` → 前端 SSE 事件处理器拿到 `file_id` 显示文件卡片
   - ASYNC 中途断网：分片提交后执行中断网 → 恢复后 SSE 重连携带 `Last-Event-ID` 补发 → 拿到最终 `TASK_COMPLETED` 事件 + `file_id`
   - SYNC ↔ ASYNC 自动切换：≤100MB 自动走 SYNC，≥100MB 自动走 ASYNC；用户手动选择"分片上传"则强制 ASYNC
7. ✅ **主业务接口不被文件操作阻塞（S13 红线）**：主业务接口（如审批发起/单据保存）在执行时如果触发大文件操作 → 自动走 ASYNC 模式 → 主业务接口立即返回 → 不阻塞主业务链路
8. ✅ `dotnet build` 0 警告 + 总测试数 ≥ 242（202 + 40）
